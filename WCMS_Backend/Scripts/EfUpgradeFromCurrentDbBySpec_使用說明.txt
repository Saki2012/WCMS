EfUpgradeFromCurrentDbBySpec.ps1 使用說明

用途：
自動處理 WCMS 後端 EF Migration 升級流程，包含：
1. 讀取 appsettings.Development.json 的 SpecCode 與 SqlConnection
2. 依 SpecCode 進行條件編譯
3. 備份並清空 Migrations 資料夾
4. 產生空 Baseline migration
5. Scaffold 目前舊 DB
6. 產生 TempSnap_1_1
7. 將舊 DB TempSnap 植入 ApplicationDbContextModelSnapshot
8. 產生 Upgrade migration
9. 產生 Upgrade SQL
10. 自動分析 ALTER COLUMN 的 Foreign Key Dependency
11. 自動補上 FK DROP / ALTER COLUMN / FK Restore
12. 自動加入 SET XACT_ABORT ON
13. 依參數只輸出 SQL，或執行同一份 Hardened SQL

============================================================
參數列表
============================================================

1. -Configuration

範例：
-Configuration "Debug"

用途：
指定 dotnet build / dotnet ef 使用的組態。

預設值：
Debug

------------------------------------------------------------

2. -BaselineName

範例：
-BaselineName "Baseline"

用途：
指定空 Baseline migration 的名稱。

預設值：
Baseline

------------------------------------------------------------

3. -TempSnapName

範例：
-TempSnapName "TempSnap_1_1"

用途：
指定暫存 Scaffold DbContext 的 snapshot migration 名稱。

預設值：
TempSnap_1_1

產生位置：
Migrations/_BaselineScaffold/__TempMigrations

------------------------------------------------------------

4. -UpgradeName

範例：
-UpgradeName "Upgrade_1_1_to_Latest"

用途：
指定真正差異升級 migration 與 SQL 檔名稱。

預設值：
Upgrade_1_1_to_Latest

產生 SQL：
Migrations/Sql/{UpgradeName}.sql

------------------------------------------------------------

5. -GenerateSqlOnly

範例：
-GenerateSqlOnly

用途：
只產生 Hardened SQL script，不更新目標 DB Schema。

行為：
- 不執行 Baseline database update
- Scaffold 僅讀取目前 DB Schema
- 產生 Upgrade migration
- SQL 從 0 產生到 Upgrade，包含空 Baseline 的 Migration History
- 自動補 FK Dependency Guard
- 不執行最終 SQL

建議：
正式環境、DBA 審查、第一次驗證升級時優先使用此模式。

------------------------------------------------------------

6. -SkipDbSpecCodeCheck

用途：
跳過 DB 內 SysDbProfile.SpecCode 與 appsettings.Development.json 的 SpecCode 比對。

只建議：
第一次升級舊 DB，且舊 DB 尚未建立 SysDbProfile / SpecCode 時使用。

============================================================
Foreign Key Dependency Guard
============================================================

EF Core 在只修改被 Foreign Key 參照欄位的長度/型別時，
可能只產生 ALTER COLUMN，而沒有自動 DROP / CREATE 未變更的 FK。

例如：
Account.AccountId nvarchar(20) -> nvarchar(64)

若 Material.CreateUserId / ModifyUserId / InvalidUserId 等欄位仍存在 FK：
SQL Server 會以 5074 / 4922 阻擋 ALTER COLUMN。

本 Script 會：

1. 從 EF SQL 找出所有 ALTER TABLE ... ALTER COLUMN
2. 從目前 DB 的 sys.foreign_keys / sys.foreign_key_columns 取得 FK Metadata
3. 找出父欄位或被參照欄位命中 ALTER COLUMN 的 FK
4. 若 EF 已有 DROP CONSTRAINT，則不重複處理
5. 在 ALTER COLUMN 前自動 DROP 相關 FK
6. 完成 Schema 變更後重建 FK
7. 保留：
   - Schema / Table / Constraint Name
   - 複合 Foreign Key 欄位順序
   - ON DELETE
   - ON UPDATE
   - NOT FOR REPLICATION
   - Trusted / Untrusted
   - Enabled / Disabled
8. SQL 開頭加入 SET XACT_ABORT ON，避免 DDL 發生錯誤後仍提交半套 Schema

============================================================
一般更新 DB
============================================================

powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\Scripts\EfUpgradeFromCurrentDbBySpec.ps1"

流程：
1. 驗證 SpecCode
2. 產生空 Baseline
3. 將 Baseline 記錄到 DB Migration History
4. Scaffold 目前 DB
5. 產生 Upgrade
6. 產生並 Harden Upgrade SQL
7. 使用同一份 Hardened SQL 更新 DB

注意：
最終 DB 更新不再直接走 dotnet ef database update Upgrade，
而是執行已通過 FK Guard 的 Migrations/Sql/{UpgradeName}.sql，
避免「人工 SQL」與「自動 DB Update」走不同升級路徑。

============================================================
只產 SQL
============================================================

powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\Scripts\EfUpgradeFromCurrentDbBySpec.ps1" -GenerateSqlOnly

此模式不修改目標 DB Schema。

產生後建議先人工確認：
1. SQL 開頭包含 SET XACT_ABORT ON
2. 若 AccountId 等被 FK 參照欄位有 ALTER COLUMN：
   - 前方有 WCMS FK Guard DROP
   - 子欄位與主欄位長度都有正確 ALTER
   - 後方有 WCMS FK Guard Restore
3. __EFMigrationsHistory 最後才寫入 Upgrade
4. SQL 可在測試 DB 完整執行後再交正式環境

============================================================
第一次升級舊 DB
============================================================

如果尚未有 SysDbProfile / SpecCode：

powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\Scripts\EfUpgradeFromCurrentDbBySpec.ps1" -SkipDbSpecCodeCheck -GenerateSqlOnly

建議先使用 GenerateSqlOnly：
1. 產 SQL
2. 人工檢查 FK / ALTER COLUMN
3. 在測試 DB 執行
4. 啟動系統初始化 SysDbProfile.SpecCode
5. 後續升級不再使用 SkipDbSpecCodeCheck

============================================================
注意事項
============================================================

1. 本 Script 讀取 appsettings.Development.json。
2. 執行前確認 SpecCode 與 SqlConnection 指向正確目標 DB。
3. Script 會備份並清空 Migrations。
   備份位置：
   obj/MigrationBackups/Migrations_yyyyMMddHHmmss
4. Script 會使用：
   /p:SpecCode={SpecCode}
   /p:UseSpecCodeCompile=true
5. GenerateSqlOnly 仍會讀 DB Schema 與 FK Metadata，但不更新 Schema。
6. 若 DB SpecCode 不一致，預設直接中止。
7. FK Guard 只補 EF 沒有自行 DROP 的現有 FK；EF 已處理的 FK 不重複插入。
8. 正式升級前仍應保留 DB Backup。
9. Hardened SQL 通過測試 DB 不等於正式 DB 一定一致；正式環境仍須確認 DB 版本與 Schema 基準。

============================================================
版本備註
============================================================

目前設計方向：
- EF / Migration 使用 appsettings.Development.json。
- Publish / 正式打包使用 appsettings.production.json。
- 舊 DB 透過 Reverse Scaffold 建立 Migration Diff 基準。
- Model 與 DB 欄位差異交由 EF Migration 產生。
- SQL Server FK Dependency 由 WCMS Script 額外補強。
- GenerateSqlOnly 為純 Schema Read + SQL Generate，不直接更新 DB。
- 自動更新與人工更新共用同一份 Hardened SQL。
