# WCMS Docs

本目錄為 WCMS 的技術基準、專案交付與品質驗證文件入口，並與程式碼一同納入 GitHub 版本控管。

文件依用途分為三大領域，不以閱讀者職稱或副檔名作為唯一分類標準。

> [!NOTE]
> AI 進入專案、切換大型任務或進行整體 Review 前，先閱讀 [`WCMS_AI資料讀取入口.md`](./WCMS_AI資料讀取入口.md)，再使用 [`AI_INDEX.yml`](./AI_INDEX.yml) 快速定位程式與正式文件入口。

## 1. 目錄結構

```text
Docs/
├─ WCMS_AI資料讀取入口.md
├─ AI_INDEX.yml
├─ 01_研發與技術文件/
│  ├─ 01_系統架構/
│  ├─ 02_開發規範/
│  └─ 03_開發歷程與版本紀錄/
├─ 02_專案與交付文件/
│  ├─ 01_專案簡介/
│  ├─ 02_專案規格書/
│  └─ 03_其他/
├─ 03_品質與驗證文件/
│  ├─ 01_AI白箱檢測/
│  ├─ 02_QA測試/
│  └─ 03_弱掃報告/
└─ README.md
```

### [`AI_INDEX.yml`](./AI_INDEX.yml)

提供 AI 與自動化工具使用的快速定位索引，集中列出正式文件入口、前後端核心路徑、Feature／Spec 路徑模式與建議搜尋順序；只負責導航，不取代架構與開發規範。

### [`01_研發與技術文件`](./01_研發與技術文件/)

保存系統架構、前後端開發規範、Git／Commit 規則，以及 RD／PR 階段使用的開發歷程資料，主要回答「系統如何設計、開發與維護」。

### [`02_專案與交付文件`](./02_專案與交付文件/)

保存專案介紹、規格、操作說明及正式交付資料，主要回答「系統提供什麼，以及本次要溝通或交付什麼」。

### [`03_品質與驗證文件`](./03_品質與驗證文件/)

保存 AI 白箱、QA、AA、SSR／Freego、弱點掃描與 Release 驗證資料，主要回答「系統是否符合規範、需求與品質要求」。

其中弱點掃描正式入口為 [`03_弱掃報告/README.md`](./03_品質與驗證文件/03_弱掃報告/README.md)，跨版本修正模式與 Commit 追蹤統一由該目錄的 `修改歷史與方針.md` 維護。

## 2. 正式資料來源

文件與實作發生差異時，依內容責任判斷：

1. 程式實作以 GitHub `iteasygo/WCMS` 的指定分支為準。
2. 架構與開發規則以 `01_研發與技術文件` 內有效的 Markdown 為準。
3. 待辦、複驗與收斂狀態以 Google Sheet「WCMS_整合收斂管理表」最新內容為準。
4. 某次修改的原因與範圍以 Git Commit、PR、Issue 及相關決策紀錄為準。
5. Word、Excel、PowerPoint、PDF 與 ZIP 主要作為正式交付、發布快照、歷史版本或輔助閱讀資料。

> [!NOTE]
> Office 與 PDF 文件即使納入 GitHub，也較難進行逐行差異檢查。重要技術結論、來源版本與驗證依據應能回溯至 Markdown、Git Commit、PR、Issue 或 Google Sheet。

## 3. 建議閱讀入口

### RD／Code Review

1. [`WCMS AI 資料讀取入口`](./WCMS_AI資料讀取入口.md)
2. [`AI 快速定位索引`](./AI_INDEX.yml)
3. [`整體專案架構`](./01_研發與技術文件/01_系統架構/01_整體專案架構.md)
4. 依端別閱讀前端或後端架構
5. [`共通開發規範`](./01_研發與技術文件/02_開發規範/01_共通開發規範.md)
6. 依端別閱讀前端或後端規範
7. [`Git 與 Commit 規範`](./01_研發與技術文件/02_開發規範/04_Git與Commit規範.md)

若任務涉及弱點掃描、可重現 500、AppScan／Nessus、ErrorHandling 或人工覆核，需再讀取 [`弱掃正式入口`](./03_品質與驗證文件/03_弱掃報告/README.md) 與對應版本追蹤文件。

### PM／客服／主管／客戶

由 [`02_專案與交付文件`](./02_專案與交付文件/) 進入，閱讀專案介紹、規格與正式交付文件。

### RD 白箱／QA／驗證人員

由 [`03_品質與驗證文件`](./03_品質與驗證文件/) 進入，依檢測類型使用 AI 白箱、QA、AA、資安或 Release 驗證資料。

## 4. 文件維護原則

- 已完成、處理中、草稿與規劃中內容必須明確區分。
- 不將討論中的構想寫成已落地功能或正式流程。
- 同一項規則只保留一份主要來源，其他文件使用相對連結引用。
- 平常開發可優先解決問題；每完成一輪功能或架構收斂後，進行一次 Docs 大範圍檢視。
- 合併 `Feature/Release` 前，再核對程式、Markdown、Google Sheet、品質驗證與交付文件的一致性。
- 非 Markdown 正式文件若引用技術或驗證內容，應標示適用版本、核對日期或來源 Commit。

## 5. 開發歷程與發布說明

[`01_開發歷程優化表.csv`](./01_研發與技術文件/03_開發歷程與版本紀錄/01_開發歷程優化表.csv) 是 RD 與 PR 階段累積改善內容的資料來源。

- 一般開發階段可先新增改善項目，版本號暫時留空。
- 準備合併至 `Feature/Release` 時，再依實際發布版本補上版本號並核對 PR、Issue 與 Commit。
- 面向 PM、客服、主管或客戶的版本說明，應由該 CSV 與實際 Release 資料整理後，輸出為 Word、Excel、PowerPoint 或 PDF。
- 同目錄的 `02_WCMS_整合收斂管理表.xlsx` 僅作為 GitHub 內的特定時間點快照；最新收斂狀態仍以 Google Sheet 為準。
