# 一些異常事件

本文件用於記錄會影響 WCMS 專案管理、需求交付、資源安排、開發排程、系統維運或交接的異常事件。

> [!NOTE]
> - 僅記錄可觀察事件與專案影響，不評論個人動機、人格或責任歸屬。
> - 公開文件以「管理端」「PM」「主要 RD」「支援 RD」等角色代稱，避免不必要的個人識別。
> - 本文件不取代正式需求規格、Issue、PR、Commit 或「WCMS_整合收斂管理表」；若事件後續形成正式決策、需求變更或待辦，仍應同步回正式管理來源。
> - 若與後續正式會議紀錄、Issue、PR 或其他正式文件不一致，以後續正式紀錄為準。

---

## 2025/08/11～2025/08/24｜上線／檢測時程壓縮，開發與驗證延伸至非一般工時

### 事件類型
時程壓縮／驗證順序風險

### 事件說明
此期間 WCMS 尚有登入、Menu、前端整合、SSR／AA 相容、弱掃與壓力測試等工作待完成，同時已有接近檢測與上線的時程期待。為追趕時程，開發、整合與驗證多次延伸至晚間及假日。

### 專案影響
- 開發、功能驗證、弱掃與壓力測試時程高度重疊。
- 驗證窗口不足時，上線後修正風險提高。
- 排程缺乏足夠緩衝，需依賴非一般工時完成收斂。

### 後續建議
上線日前應預留 code freeze、功能驗證、弱掃、壓測與修正窗口，避免最後一輪功能開發與正式驗證完全重疊。

## 2026/05/08～2026/07/09｜WCMS 支援 RD 可用產能不足

### 事件類型
人力配置／資源競爭／單點依賴

### 事件說明
主要 RD 同期需處理開發、維護、新案、AA 與 Code Review；原先規劃支援 WCMS 的 RD 亦持續受到其他維護案、既有系統與新案占用。已明確提及會與 WCMS 競爭支援 RD 產能的工作包含「金岳」案及「合約系統」增修。

至 2026/07/09，PM 估計原預期支援 WCMS 的 RD 實際可投入時間約僅剩每週 1.5 天，PM 端本身亦有多案並行狀況。

### 專案影響
- 名義上有支援人力，但無法形成穩定、可預測的第二開發產能。
- 任務切分、Code Review、Bug 分派與知識移轉仍高度依賴主要 RD。
- 新功能與底層重構容易受其他案務插入影響。

### 後續建議
Backup 應以固定可投入工時、持續跟版及實際負責模組作為判定基準，而非僅以「有人可支援」認定已完成人力配置。

## 2026/07/29｜需求尚未完成確認即要求 PM／RD 同步推進

### 事件類型
需求流程／排程前置不足

### 事件說明
當日部分新案仍停留在初步方向與開案層級，尚未完成完整需求訪談與細節確認，但已出現 PM 與 RD 同步往前執行的時程要求。

### 專案影響
- RD 在需求範圍尚未穩定時投入，可能產生重工。
- 工時估算與排程缺乏完整前置資訊。
- PM／RD 反覆確認與切換，增加額外協作成本。

### 後續建議
至少先確認需求範圍、優先級、驗收標準與主要風險，再進入正式開發；若需提前研究，應標示為 Spike／PoC。

## 2026/08/28｜未先與既有 PM／技術 Owner 對齊即新增交辦

### 事件類型
資訊不同步／重工風險

### 事件說明
當日下午新增一項 Demo 製作交辦，但既有 PM 已完成對應 Demo，且交辦前未先與既有 PM／技術 Owner 對齊目前進度。

### 專案影響
- 同一工作可能被重複執行。
- 團隊成員無法即時確認最新優先順序與 Owner。
- 後續仍需額外投入時間進行版本與內容收斂。

### 後續建議
新增或調整任務時，先確認「是否已有人處理、目前版本、優先級與交付內容」，再進行人員指派。

## 2026/09/07｜WCMS 上版與問題判斷仍高度依賴單一主要 RD

### 事件類型
知識集中／交接風險／維運單點

### 事件說明
當日專案討論顯示，WCMS 的調整與上版仍主要依賴單一主要 RD；其他人員雖已開始參與 Bug 追蹤、前後台修改與教育訓練，但尚未完全具備獨立判斷修改影響範圍與任務切分的能力。

### 專案影響
- Bug 分派、架構判斷、版本調整與上版風險集中。
- 主要 RD 不可用時，短期內可能出現決策與維運斷點。
- 文件與教育訓練已建立，但尚不能等同 backup 已可完全獨立接手。

### 已有緩解措施
- 持續補充專案文件。
- 已安排系統架構與開發教育訓練。
- 逐步讓其他成員參與前後台修改與 Bug 處理。

## 2026/09/08｜辦公環境施工造成開發／部署作業中斷

### 事件類型
工作環境／人員可用性／部署中斷

### 事件說明
當日下午辦公環境進行施工，現場狀況使部分人員提前離開工作區。當時仍有弱掃與部署相關工作待處理，原先評估改以遠端方式進行，但主要工作站已登出鎖定，當下無法繼續部署。

### 專案影響
- 當日下午原定開發／弱掃／部署工作受到中斷。
- 專案部署流程當時仍依賴特定實體工作站。
- 工作環境事件直接轉化為人員可用性與交付風險。

### 後續建議
施工或其他可能影響辦公環境的作業應提前通知並準備替代工作區／遠端方案；部署流程亦應避免完全依賴單一實體工作站。

## 2026/09/09｜主要即時通訊管道一度不可用

### 事件類型
聯絡備援／緊急溝通

### 事件說明
當日上午主要即時通訊管道出現帳號／聊天室異常，原本的直接聯絡方式一度無法使用，相關工作通知需經第三人轉達。同時間「招生交叉查榜」案正在進行資安檢測追蹤，且接近評選時程。

### 專案影響
- 緊急聯絡與工作狀態回報受到延遲。
- 高度依賴單一即時通訊工具時，帳號異常會直接影響資訊傳遞。
- 外部期限接近時，缺乏第二正式聯絡管道會放大協作風險。

### 後續建議
重要專案至少保有第二正式聯絡管道（例如公司 Email、Teams 或其他組織帳號），並建立緊急事件 escalation 與代理機制。

## 2026/09/09～2026/09/11｜PM 被臨時調派處理其他案務，WCMS 規格交付受影響

### 事件類型
臨時插單／PM 資源排程異動

### 事件說明
2026/09/09～2026/09/11 期間，PM 因管理端直接調派，被安排處理卡務等其他案務，造成原定 WCMS 專案工作受到影響。

截至 2026/09/11，RD 仍未取得「主子網站規格」及「招生交叉查榜規格」。

### 專案影響
- 需求規格未能依原排程交付。
- RD 無法完整確認需求、評估工時及安排後續開發。
- 若後續發生開發排程、需求確認或工時評估延後，不宜將等待規格期間直接視為 RD 開發延誤。

### 目前狀態
截至 2026/09/11：相關規格仍待 PM 提供。

## 2026/09/11｜Server2 更新期間多個測試站同時無法連線

### 事件類型
測試環境／基礎設施可用性

### 事件說明
當日上午約 09:42 於「新化林場」相關測試作業中發現 WCMS 測試站無法連線，進一步確認其他測試站亦同時不可用；09:48 確認 Server2 正在更新，約 10:04 恢復連線。

### 專案影響
- 更新期間多個測試站無法進行功能驗證。
- 若未事前公告維護窗口，RD／QA 容易先以系統故障方向進行排查，增加無效診斷時間。
- 同一主機承載多個測試站時，主機級操作會同時影響多個專案驗證工作。

### 後續建議
Server2 或共用測試主機進行更新、重啟或維護前，應公告預計時間與影響範圍；維護結束後再通知團隊恢復測試。

## 2026/09/14｜Bug／報修資訊暫時分散於 GitHub Issues 與 Mantis

### 事件類型
追蹤工具並行／資訊同步風險

### 事件說明
當日上午確認部分修正與報修紀錄同時存在於 GitHub Issues 與 Mantis，團隊暫時採兩邊個別回覆與同步說明的方式維持追蹤。

### 專案影響
- 同一問題可能存在兩套狀態與更新紀錄。
- 若其中一邊未同步，可能出現「已修正但另一系統仍顯示未處理」或重複派工。
- 新接手人員需要額外確認哪一套系統才是最新狀態來源。

### 後續建議
應明確指定單一 Source of Truth；若因客戶流程必須保留 Mantis，可建立固定同步規則，例如 GitHub Issue 保存技術處理、Mantis 保存對客回覆，並互相附上對應編號。

## 2026/09/14｜臨時確認主要 RD 僅可投入至 2026/09/30，交接窗口縮短

### 事件類型
臨時人力異動通知／關鍵人力異動／交接風險／排程重整

### 事件說明
2026/09/14 當日，管理端於工作場合臨時確認主要 RD 可投入 WCMS 的期間僅至 2026/09/30。此人力異動並非依既定交接排程提前通知；PM 於事後表示，事前未收到完整的人力異動討論資訊。

因此 WCMS 自當日起需在剩餘約半個月的期間內，重新安排必要交接、教育訓練、技術 Owner 與責任轉移。

### 已知交接基礎
- 系統架構與主要模組文件已持續整理於專案中。
- 已產出教育訓練文件，並進行部分系統架構與開發說明。
- 其他成員已開始參與部分前後台修改與 Bug 處理。

### 專案風險
- 架構判斷、版本調整、Code Review 與系統脈絡仍有部分尚未形成可獨立接手的 backup。
- 原本預計持續進行的教育訓練與實戰移轉需於較短時間內完成或重新安排 Owner。
- 新需求、弱掃、上版與既有 Bug 若同時進行，將與交接工作競爭人力。

### 後續建議
1. 確認 2026/09/30 後的 WCMS 技術 Owner 與上版責任人。
2. 將未完成交接項目拆成清單，區分「需優先完成」與「可由文件後續補足」。
3. 交接期間降低非必要新功能插單，優先處理系統穩定性、權限、部署、常見問題與核心架構。
4. 由接手人實際完成至少一次 Bug 修正、測試、版控與上版流程，以驗證交接成果。
5. 後續排程與外部承諾應反映實際人力變更，不維持原先產能假設。
