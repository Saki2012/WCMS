# WCMS AI 專案資料讀取入口

本文件是 AI 進入 WCMS 專案時的資料導向 Prompt。
主要用途是指定 GitHub、Docs 與管理資料的讀取順序，以及資料不一致時的判斷原則。

本文件只負責「導向與學習順序」，不取代 Docs 內的正式架構、開發規範、Git／Commit 規範或品質驗證文件。

---

## 1. GitHub Repository

Repository：
https://github.com/Saki2012/WCMS

目前主要分支用途：

- `main`：Repository 預設分支，不可直接視為最新開發進度。
- `Feature/Dev`：共用功能與架構開發的主要核對分支。
- `Feature/Release`：版本發布前的整合與發布整理分支。
- `Spec####`：個別專案或客製站台分支，依本次任務確認。

開始分析或修改前，先確認：

1. 本次 Repository。
2. 來源分支與目標分支。
3. 任務屬於共用 Feature、特定 Spec、Release、QA、文件或歷史整理。
4. 使用者是否指定某個 ZIP 或附件作為本次基準。

若無法存取 GitHub，必須明確說明，並請使用者提供指定 Branch 的 ZIP 或必要檔案；不得假裝已核對最新版。

## 2. Docs 正式入口

WCMS 的 `Docs` 資料夾會放在同一個 GitHub Repository 中進行版本控管。

每次新對話、開始新的大型功能或進行整體 Review 時，先閱讀：

`Docs/README.md`

再依任務閱讀對應文件。

### 2.1 系統架構

共通入口：

`Docs/01_研發與技術文件/01_系統架構/01_整體專案架構.md`

前端任務：

`Docs/01_研發與技術文件/01_系統架構/02_前端專案架構.md`

後端任務：

`Docs/01_研發與技術文件/01_系統架構/03_後端專案架構.md`

### 2.2 開發規範

所有程式修改先閱讀：

`Docs/01_研發與技術文件/02_開發規範/01_共通開發規範.md`

前端任務追加閱讀：

`Docs/01_研發與技術文件/02_開發規範/02_前端開發規範.md`

後端任務追加閱讀：

`Docs/01_研發與技術文件/02_開發規範/03_後端開發規範.md`

涉及 Commit、Branch、Issue、PR 或 Release 時追加閱讀：

`Docs/01_研發與技術文件/02_開發規範/04_Git與Commit規範.md`

不得用舊對話、舊 Word、舊 Prompt 或 Legacy Code 取代目前有效的 Markdown 規範。

### 2.3 開發歷程與版本紀錄

涉及歷史優化、Release 內容或對外版本說明時閱讀：

`Docs/01_研發與技術文件/03_開發歷程與版本紀錄/01_開發歷程優化表.csv`

此 CSV 是 RD 與 PR 階段累積改善內容的來源；正式版本號於進入 `Feature/Release` 後依實際發布版本補入。

### 2.4 品質與驗證

涉及 AI 白箱、QA、AA、SSR／Freego、弱點掃描、複驗或 Release 驗證時先閱讀：

`Docs/03_品質與驗證文件/README.md`

再依任務進入：

- `Docs/03_品質與驗證文件/01_AI白箱檢測/`
- `Docs/03_品質與驗證文件/02_QA測試/`

尚在討論、草稿或未正式落地的流程，不得描述成目前已全面執行的正式規則。

### 2.5 專案與交付文件

面向 PM、客服、主管、QA 或客戶的 Word、Excel、PowerPoint、PDF，主要位於：

`Docs/02_專案與交付文件/`

這些文件主要用於閱讀、簡報、溝通與交付；其中的技術事實仍須回頭核對 GitHub 程式碼與 Markdown。

## 3. 資料來源責任

資料不一致時，依內容責任判斷：

1. 程式目前如何運作：GitHub 指定分支的程式碼與設定。
2. 系統應如何設計與開發：Docs 內有效的 Markdown 架構與開發規範。
3. 某次修改的原因與範圍：Git Commit、PR、Issue 與相關決策紀錄。
4. 待辦、收斂與複驗狀態：Google Sheet「WCMS_整合收斂管理表」最新版本。
5. 發布改善素材：開發歷程優化表、Release PR、Issue 與 Commit。
6. Word、Excel、PowerPoint、PDF：人工閱讀、報告、交付或歷史快照。
7. ZIP：使用者指定時間點的專案快照；未特別指定時仍應與 GitHub 核對。

發現不一致時，必須分別指出：

- 目前程式實況。
- 現行文件規範。
- 管理或複驗狀態。
- 建議更新哪一份資料。

不得自行把不同來源解讀成一致。

## 4. 每次開始任務的學習順序

1. 確認 Repository、Branch、任務範圍與附件基準。
2. 閱讀 `Docs/README.md`。
3. 閱讀相關架構文件。
4. 閱讀共通開發規範。
5. 閱讀本次端別的前端或後端規範。
6. 視任務閱讀 Git／Commit、品質驗證或開發歷程文件。
7. 核對 GitHub 指定分支的實際程式碼。
8. 搜尋 SysCore、Library、Helper、Hook、Component、Template、Adapter、FeatureDriver、Service、Repository、Feature 與相近 Spec 的既有實作。
9. 搜尋相關 Issue、PR、Commit 與歷史修正。
10. 再提出問題判斷與修改方案。

不得在未確認既有能力前，直接建立重複 Helper、平行流程或新的架構層。

---

## 5. 分析與修改原則

- 明確區分「已實作」、「正式規範」、「已知但未整改」、「規劃中」與「無法確認」。
- 不把規劃中或未來考慮的內容寫成已完成功能。
- 優先沿用 WCMS 現有框架、共用能力、命名與資料流。
- 遇到 Legacy Code 與新規範不一致時，指出差異，不反向修改規範迎合舊程式。
- 修改範圍聚焦本次需求，不順手大幅改動無關檔案。
- 涉及 AA、SSR／CSR、弱點掃描、多語系、Cache、JWT、API 契約或 Spec 客製行為時，必須說明影響範圍。
- 複雜需求分階段處理，每次提供可驗證的一小步。
- 未實際執行 Build、測試、Freego、弱點掃描或部署時，不得聲稱已通過。

詳細 Code Style、Function、Region、註解、Hook、FeatureDriver、Commit 與 PR 格式，直接遵循 Docs 對應規範，不在本 Prompt 重複維護。

## 6. 文件同步與稽核

Docs 由 GitHub 版控。

進行架構、規範、流程、資料契約或責任邊界調整時，必須判斷是否影響現有 Markdown。

每完成一輪功能或架構收斂後，協助檢查：

- 架構說明與程式實作是否一致。
- 共通、前端、後端規範是否互相矛盾。
- 檔名、路徑與相對連結是否有效。
- 已完成、處理中、風險與規劃中的描述是否正確。
- Office／PDF 是否仍引用過期內容。

合併 `Feature/Release` 前，再進行一次大範圍文件一致性檢查。

若本次只要求修程式，不一定要直接重寫所有 Docs；但應列出可能受影響的文件，避免文件差異被遺忘。

---

## 7. 附件與外部資料

- 使用者要求參閱附件時，必須實際解析內容，不得只依檔名或舊對話推測。
- Office、PDF 與 ZIP 應核對版本、日期及適用範圍。
- 同一主題同時存在 Markdown 與 Office 文件時，Markdown 通常作為可版控來源，Office／PDF 作為閱讀、簡報或固定版輸出。
- 公司專案管理、合約或其他非 WCMS 資料，不得視為 WCMS 技術規範。
- 修改 Google Sheet 前，先讀取目前欄位與選單值，不依舊文件自行建立重複欄位。

---

## 8. 回覆與交付

- 使用繁體中文。
- 先說明問題與判斷依據，再提出修改方向。
- 清楚列出異動檔案、修改原因、影響範圍與驗證方式。
- 資料不足、權限不足或無法存取指定來源時，必須誠實說明。

本 Prompt 的核心責任是將 AI 導向正確的 GitHub、Docs 與管理資料。
正式規則更新時，應優先更新 Docs；本 Prompt 只調整導向路徑與閱讀順序，避免再次形成重複且容易過期的規範副本。
