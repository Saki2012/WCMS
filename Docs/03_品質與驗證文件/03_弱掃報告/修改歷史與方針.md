## 1. 文件定位

弱掃資料分成三層：

```text
原始 AppScan / Nessus 報告
→ 當次 Scanner Finding

版本 README
→ 該次掃描的修正、複驗與 False Positive 證據

修改歷史與方針（本文件）
→ 跨版本累積「問題是什麼、怎麼改、為什麼這樣改、Commit 在哪裡」
```

本文件放在 `03_弱掃報告` 根目錄，目的是讓後續 RD／AI 在遇到相同 Finding 時，先確認 WCMS 是否已有共用修正與架構決策，再決定是否新增處理。

---

## 2. Commit SHA 記錄規則

GitHub 目前 WCMS Repository 的 Commit ID 為 40 碼 Git Object ID，因此本文件統一欄位名稱為：

> **Commit SHA（完整）**

不使用「SHA256」作為欄位名稱，避免把 GitHub 現行 Commit ID 的雜湊格式寫錯。

紀錄時不得只保留 7 碼 Short SHA；表格可另提供 Short SHA 方便閱讀，但完整 SHA 必須存在。

## 3. Finding 狀態

沿用弱掃根目錄 README 的正式狀態：

| 狀態 | 定義 |
|---|---|
| 原始 Finding | Scanner 當次報告列出的結果 |
| 待分析 | 尚未完成白箱／Runtime 判斷 |
| Code mitigation 已完成 | 已有對應程式修正，但尚未正式複掃 |
| Runtime 驗證完成 | 已實際重現並取得預期結果；不代表 Scanner 已清除 |
| 疑似 False Positive | 白箱／Runtime 顯示 Scanner 漏洞名稱可能不成立，仍需證據或人工覆核 |
| 複掃通過 | 相同或更完整 Coverage 的正式複掃已確認 Finding 消失 |
| Accepted Risk | 經正式風險決策保留；必須有責任人與理由 |

禁止用「已修好」「All Clear」同時代表 Code、Runtime 與 Scanner 三種不同狀態。

## 4. 每筆修改的標準紀錄欄位

後續新增弱掃修正時，至少記錄：

| 欄位 | 說明 |
|---|---|
| 日期 | 實際修正或確認日期 |
| 版本／掃描來源 | 例如 FE1.5.3 / BE1.5.2.1、2026-08-20 AppScan |
| Severity／Finding | Scanner 原始名稱與等級 |
| 問題本質 | Scanner 為什麼會判定；Runtime 真正問題是什麼 |
| 影響邊界 | Frontend／Node SSR／Backend／DB／IIS／Browser |
| 修改方向 | 採用的架構與處理方式 |
| 主要異動單元 | 共用 Module／Feature／Middleware／Policy |
| Commit SHA（完整） | 對應 Git Commit |
| 驗證狀態 | Code／Runtime／複掃／False Positive |
| 證據／下一步 | Response、Log、SQL Parameter、DB State、正式複掃等 |

若一個 Finding 需要多個 Commit，應保留完整 Commit Chain，不把最後一筆 Commit 當成所有修改的唯一來源。

### 5.2 Browser Unsafe Method XSRF

**原始問題**  
Browser 使用 Cookie／Credential 呼叫 POST、PUT、PATCH、DELETE 等 Unsafe Method 時，若沒有強制 Antiforgery Token 驗證，Scanner 會判定 CSRF 防護不足。

**修改方向**

- Backend Browser Unsafe Method 納入統一 XSRF 驗證。
- 使用 ASP.NET Core Antiforgery Cookie + `XSRF-TOKEN` + `X-XSRF-TOKEN` 契約。
- 前端在需要時取得 Token，並於 Unsafe Method 回送 Header。
- Authorization 與 XSRF 分開處理；不能用 XSRF 取代 Permission。

**Commit**

- Full：`65ec797df00940f8695b7a615da79e4ca5736940`
- Message：`BE Security：補齊 Browser Unsafe Method XSRF Token 驗證`

`Code mitigation 已完成；正式複掃待執行。`

## 6. Critical／High 疑似 False Positive 處理方針

### 6.1 Blind SQL Injection

若 Scanner 以 TRUE／FALSE Payload 判定 Blind SQL Injection，但 WCMS 使用 EF／Parameterization，仍不得只寫：

> 「我們用 EF Core，所以是誤判。」

至少保留：

1. Endpoint／HTTP Method／欄位。
2. 正常值、TRUE-like、FALSE-like Request。
3. 三組 Response Status／Schema／關鍵 Data。
4. DB 前後狀態。
5. SQL Command Text。
6. SQL Parameter Name／Value。
7. 證明 Payload 只在 Parameter Value，不在 SQL Syntax。

若 Response 差異來自「更新後回傳舊資料」等非 SQLi 問題，也要先修正 Response 契約，再重送 Scanner Payload。

判定方向：

```text
SQL Injection Finding 名稱疑似誤判
+
SQL Parameterization 證據完整
+
TRUE / FALSE 不再改變 SQL 語意
+
DB 狀態正常
→ 可整理疑似 False Positive 證據
```

---

### 6.2 Integer Overflow

若 Scanner 將極大數字 Payload 打入實際型別為 `string` 的欄位，可疑似判定「漏洞名稱錯誤」，但仍須分開判斷：

```text
Scanner 名稱可能判錯
≠ Payload 造成 500 可以忽略
```

應確認：

- JSON Value 是否為 quoted string。
- C# Model／OpenAPI 是否為 string。
- DB Column Type／Length。
- 是否有 Integer Cast／Arithmetic。
- 超過允許長度時能否於 Validation／4xx 收斂。

如果極端字串最後進 SQL Server 才因 Truncation 500，仍屬 Error Handling／Input Boundary robustness 問題，需要修正後再提交 False Positive 證據。

## 7. 可重現 500 的處理方針

2026-08-20 弱掃 Runtime Log 顯示大量特殊輸入最後成為 500，主要包括：

- Dynamic LINQ Parser Invalid Condition。
- `DbUpdateConcurrencyException`。
- DB String／Binary Truncation。
- Foreign Key Conflict。
- Duplicate Key。

處理原則不是「所有 Exception 改 400」，而是依語意分類：

```text
Invalid Request
→ 400

Authentication
→ 401

Authorization / Permission
→ 403

Data State / Unique / Concurrency Conflict
→ 409

Rate Limit
→ 429

Unknown Server Bug
→ 500
```

Framework Exception 本身不直接決定 HTTP Status。`ArgumentException`、`InvalidOperationException`、`FormatException` 等可能來自 Request，也可能代表程式 Bug，必須在最接近錯誤來源處先確認語意。

截至 2026-08-25，第一批 ErrorHandling／Validation 已完成主要 Code mitigation；目前不是「所有項目都已複掃通過」，而是從 Code 收斂進入 Runtime Replay。

本輪固定下列可重用原則：

- 不把 `ArgumentException`、`FormatException`、`InvalidOperationException`、`SqlException` 等 Framework Exception 全域機械式 Mapping；只在能確認語意的邊界轉成 WCMS 已知結果。
- Request 可預期錯誤盡可能在 API／Model Boundary 先回 400；資料競爭／Constraint Conflict 依語意回 409；真正 Server／Schema 問題保留 500。
- `[LibField]`／`[LibStr]`／`[LibNum]` 使用共用 `LibFieldValidator`，API 與 SaveChanges 不維護兩份不同 BECode 判斷。
- SaveChanges 最終驗證只拒絕不合法資料，不自動截斷字串或 Clamp 數值。
- Model 契約已合法但 DB 因 NOT NULL／Truncation／型別容量拒絕時，視為 Persistence Contract Drift，回 500 + BECode00046；未來 DB Version ↔ Model Version 啟動檢查是主防線，Runtime Guard 仍保留。
- `IFormFile` 缺檔屬 FileManagement HTTP Request Boundary，不屬 Persistence；目前 Filter 與 File API／Biz 同置 `PlatformServices/FileManagement`，不擴張成全域 FeatureDriver Filter。
- FileManagement 公開下載的 Duplicate Key 雖可由 409 收斂，但若根因是 DownloadRecent RowId 競爭，長期仍應做併發安全／Idempotent 改善，不能只以 HTTP Mapping 視為完成。

## 8. Header 類 Finding 的固定方針

Header 類一律以完整鏈路檢查：

```text
Browser
→ IIS / ARR
→ Node SSR
→ Backend
```

至少確認：

- Backend Direct Response。
- Node `/Service` Proxy Response。
- IIS 對外最終 Response。
- HTML／Static JS／API／PDF 不同 Resource Type。

禁止只用 Source Code 中「有 `Headers.Append(...)`」就判定 Finding 已清除。

## 9. 安全例外的治理方式

CSP／COEP／CORP／Trusted Types 若因第三方功能或 PDF 需要例外，必須記錄：

- 哪個 Resource／Domain。
- 為什麼需要。
- 只開放哪個 Directive／Response Type。
- 是否只限某 Feature／Spec。
- 有沒有更小權限替代方案。
- Runtime Regression 結果。

不得為了解一個第三方功能直接加入：

```text
過寬 wildcard
全站 unsafe-inline
全站 unsafe-eval
不受控任意 frame / script / connect source
```

例外應集中於共用 Security Policy，不散落 Feature Component。

詳細專項文件可保留，但主架構的安全責任不能只存在專項文件，避免後續 AI／RD 讀取主架構時漏掉正式 Security Boundary。

## 12. 目前下一階段

截至 2026-08-25，Header Security Hardening 與後端第一批 ErrorHandling／Validation 的主要 Code mitigation 已完成。接下來停止繼續擴張抽象層，優先把原始／等價弱掃 Payload 一筆一筆 Replay，確認實際 HTTP、ApiResponse、DB State 與 NLog。

目前驗證順序：

```text
1. JSON / PageNumber、PageSize 超大數值
2. LibStr 超長、LibNum Range / Min / Max
3. Dynamic LINQ Invalid Condition
4. EF Concurrency / SQL 547 / Duplicate
5. FileManagement 缺檔／空檔 Upload
6. Model / DB Schema Drift Evidence
7. Critical Blind SQL Injection TRUE / FALSE + SQL Parameter Evidence
8. High Integer Overflow 欄位型別／極端字串證據
9. Frontend Header / Trusted Types Runtime Regression
10. 正式 AppScan 複掃
```

每完成一個 Case：

1. 重送原始／等價 Payload。
2. 確認 HTTP Status + ApiResponse + SysMessage。
3. 確認 Browser 不洩漏 Exception；真正 500 才保留完整 NLog。
4. 必要時保留 SQL Command／Parameter、DB 前後狀態或 Schema Evidence。
5. 若發現 Code mitigation 仍不足，再做最小修正並記錄 Commit SHA。
6. 回寫版本 README 與本文件。
7. 正式複掃後才能更新為 Scanner 通過。
