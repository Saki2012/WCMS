# 專項白箱檢測

## 1. 目的與適用範圍

本規範用於橫向檢查某一項系統性能力、共用底層或跨多個 Feature／Spec 的技術主題，確認其責任、引用、註冊、契約與使用方式是否一致合理。

專項檢測不是完整全專案回歸，也不只對應單一 PR。它可由 PR 影響自動觸發，或由 RD 主動指定主題與 Commit 執行。

## 2. 觸發方式

### 2.1 PR 影響觸發

需求與單元檢測發現修改碰觸特定技術邊界時，應追加對應專項。

常見對應：

- Cache Key、Registry、Output Cache、Redis 規劃 → Cache 專項。
- SSR Entry、Loader、Browser API、Initial Data → SSR／Hydration 專項。
- ARIA、鍵盤、焦點、語意與報讀 → AA 專項。
- DTO、OpenAPI、Nullable、Payload → API 契約專項。
- JWT、Cookie、Permission、Authorization → JWT／權限與資安專項。
- Operation Log、Change Log、NLog、Auditing → 操作／變更日誌專項。
- Feature 與 Spec 共用或覆寫 → Feature／Spec 專項。
- DateTime、UTC、DateOnly、時區 → 日期與時間專項。

### 2.2 RD 主動發起

RD 可直接指定目前 Branch／Commit 與主題，例如：

```text
針對目前 Feature/Dev 的 Cache 做專項白箱檢測。
```

AI 應自行取得檢測基準；只有版本或主題範圍不明時才要求補充。

## 3. 專項檢測原則

- 不只搜尋名稱或關鍵字，必須確認實際責任與呼叫關係。
- 不只檢查單一檔案，應跨越註冊入口、實作、使用者、失效或例外流程。
- 應區分正式底層、Feature 使用、Spec 延伸與 Legacy 相容內容。
- 應找出重複實作、平行流程、繞過正式入口與責任混用。
- 沒有對應正式規範時，只能標示觀察或待確認，不得自行建立強制規則。

## 4. 建議專項分類與 Rule 來源

所有正式 Rule ID、版本、狀態、判定條件與生命週期，唯一維護於 [`RULE_REGISTRY.yml`](./RULE_REGISTRY.yml)。

未來可視需要建立 `Topics/`，但其責任僅限於保存專項背景、責任邊界、搜尋入口、常見證據、執行順序與人工驗證建議，不得建立另一份 Rule 清冊或與 Registry 重複維護判定條件。

```text
Topics/
├─ Cache.md
├─ Library.md
├─ SSR_Hydration.md
├─ Accessibility.md
├─ ApiContract.md
├─ JwtPermissionSecurity.md
├─ Auditing.md
├─ FeatureSpec.md
└─ DateTimeUtc.md
```

尚未建立 Topic 不代表不需要檢查；AI 應依 `RULE_REGISTRY.yml` 中與範圍相關的 `active` Rule 執行，未收錄但有正式規範來源的項目則使用規範定位，不得臨時建立永久 Rule ID。

## 5. 共通檢測面向

每個專項至少確認：

1. **責任定位**：此能力應屬 SysCore、Feature、Spec、FeatureDriver 或基礎設施哪一層。
2. **正式入口**：是否透過指定 Library、Hook、Template、ModuleSetup、Service 或其他入口。
3. **引用一致性**：各 Feature／Spec 是否使用相同契約。
4. **生命週期**：初始化、註冊、執行、失效、清理與例外處理是否完整。
5. **契約與安全**：型別、資料、權限、日誌、快取或外部輸入是否有明確邊界。
6. **重複與繞過**：是否存在局部 Helper、直接底層操作或平行流程。
7. **影響範圍**：修改一處是否會影響其他 Feature、Spec、SSR、AA、API 或部署。

## 6. 專項執行流程

```text
鎖定主題與 Commit
    ↓
讀取相關架構、開發規範與 Rule Registry
    ↓
篩選與主題相關的 active Rule
    ↓
建立正式入口與使用路徑清單
    ↓
跨 Feature／Spec 搜尋實際引用
    ↓
比對責任、契約、生命週期與例外流程
    ↓
去除僅命名相似但責任不同的結果
    ↓
產出發現、證據與信心程度
    ↓
RD 判定、分批修正與複驗
```

## 7. 專項結果摘要

除個別發現外，應提供：

```text
【專項名稱】
【檢測 Commit】
【Rules Commit】
【套用 Rule】
【正式入口】
【主要使用範圍】
【一致性結論】
【高風險區域】
【未能確認項目】
【是否建議全專案回歸】
```

若問題數量較多，應先依共用底層、Feature、Spec 或風險分批，不一次產生大量未經 RD 判定的修正。

## 8. 修正與複驗

RD 確認成立的項目才可進入修正。AI 依 [`README.md`](./README.md) 提供修改單元 ZIP。

專項修正後，除複驗原問題外，還應確認：

- 其他使用相同底層的 Feature／Spec 是否需要同步。
- 正式入口與生命週期是否仍一致。
- 是否因修正局部問題而新增另一套平行流程。
- 修改規模是否已達全專案白箱回歸觸發條件。
