# 需求與單元白箱檢測

## 1. 目的與適用範圍

本規範用於檢查一次需求、Commit 或 PR 的修改是否符合需求、架構與開發規範，並確認異動對直接依賴、共用底層與 Feature／Spec 邊界的影響。

每個 PR 原則上都必須執行本檢測；同一對話中的中間 Commit 可視開發節奏決定是否先行檢查，但 PR 最終 Head Commit 應完成檢測與必要複驗。

## 2. 檢測輸入

AI 應優先自行取得：

- 原始需求、Issue、PR 或對話脈絡。
- Base Commit 與 Head Commit。
- Commit Summary、Description 與交付說明。
- Changed Files、Diff 與受影響的直接引用。
- 對應的前端、後端、共通與 Git／Commit 規範。

若同一對話與 Git 狀態一致，不要求 RD 重複填寫完整檢測表單。

## 3. 檢測範圍

單元檢測不是只看 Diff 行數，範圍至少包含：

```text
異動檔案
＋直接依賴
＋直接被引用位置
＋契約或共用底層邊界
```

應依修改內容確認：

- 需求是否完整實現，是否存在超出需求的改動。
- 是否正確沿用既有 Library、Hook、Component、Template、Adapter、FeatureDriver、Service 或 Repository。
- 是否建立重複 Helper、平行流程或不必要的新底層。
- 前端型別、Hook、SSR／CSR、AA、多語系與 API 邊界。
- 後端 Model、Biz、API、Transaction、Cache、Auditing、權限與錯誤回應邊界。
- Feature／Spec Fallback、Override 與共用影響。
- Commit 交付說明是否與實際 Code 一致。

## 4. 執行流程

```text
讀取需求與交付宣告
    ↓
鎖定 Base／Head Commit
    ↓
分析 Changed Files 與 Diff
    ↓
追蹤直接依賴與契約邊界
    ↓
比對正式架構與開發規範
    ↓
判斷是否觸發專項或全專案回歸 Gate
    ↓
產出發現與證據
    ↓
RD 判定、修正與複驗
```

## 5. 必查項目

### 5.1 需求與範圍

- 修改是否對應需求、Issue 或 PR 目標。
- 是否遺漏明確需求。
- 是否混入無關重構、格式化或其他功能。
- 新增單元的架構歸屬是否合理。

### 5.2 共用能力與架構

- 交付說明聲稱沿用的能力是否真的被使用。
- 是否已有相近共用能力卻另建局部版本。
- 共用能力不足時，擴充或獨立建立的理由是否符合規範。
- 修改共用底層時，是否檢查可能受影響的 Feature 與 Spec。

### 5.3 程式結構與契約

- Function／Method、註解、型別、非同步與存取範圍是否符合規範。
- API、Schema、Nullable、日期時間與資料格式是否維持契約一致。
- 是否繞過標準 Adapter、Template、FeatureDriver 或資料流程。
- 是否出現明顯的編譯、型別、Runtime 或安全風險。

### 5.4 交付與驗證真實性

- Commit Summary／Description 是否與修改內容一致。
- 是否清楚記錄影響範圍、共用能力異動與尚未執行的驗證。
- 未執行的 Build、測試、AA、Freego、弱掃或部署是否被錯寫成通過。

## 6. Gate 判定

檢測結束前必須給出：

```text
【需求與單元 Gate】通過／不通過／待確認
【專項 Gate】未觸發／觸發：<專項名稱>
【全專案回歸 Gate】未觸發／建議觸發
```

一般文字、單一樣式或低風險局部修正通常不觸發其他 Gate；涉及 Cache、SSR、AA、API 契約、JWT、Auditing、Feature／Spec 或日期時間等邊界時，應追加對應專項檢測。

## 7. 結果與複驗

每一項發現依 [`README.md`](./README.md) 的共通格式輸出。

RD 確認成立後才進行修正。複驗應使用新的 Head Commit，至少確認：

- 原問題已消失。
- 修正內容未超出確認範圍。
- 直接依賴與契約未引入新問題。
- 原先觸發的專項 Gate 是否仍需重新檢測。
