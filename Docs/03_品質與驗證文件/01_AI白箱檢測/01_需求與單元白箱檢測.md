# 需求與單元白箱檢測

## 1. 目的與適用範圍

本規範用於檢查一次需求、Commit 或 PR 的修改是否符合需求、架構與開發規範，並確認異動對直接依賴、共用底層與 Feature／Spec 邊界的影響。

每個 PR 原則上都必須執行本檢測；同一對話中的中間 Commit 可視開發節奏決定是否先行檢查，但 PR 最終 Head Commit 應完成檢測與必要複驗。

## 2. 檢測輸入

AI 應優先自行取得：

- 原始需求、Issue、PR 或對話脈絡。
- Base Commit 與 Head Commit。
- Commit Summary、Description 與交付說明。
- Changed Files、Diff 與受影響的直接引用。
- 對應的前端、後端、共通與 Git／Commit 規範。

若同一對話與 Git 狀態一致，不要求 RD 重複填寫完整檢測表單。

## 3. 檢測範圍

單元檢測不是只看 Diff 行數，範圍至少包含：

```text
異動檔案
＋直接依賴
＋直接被引用位置
＋契約或共用底層邊界
```

應依修改內容確認：

- 需求是否完整實現，是否存在超出需求的改動。
- 是否正確沿用既有 Library、Hook、Component、Template、Adapter、FeatureDriver、Service 或 Repository。
- 是否建立重複 Helper、平行流程或不必要的新底層。
- 前端型別、Hook、SSR／CSR、AA、多語系、CSP UI Style 與 API 邊界。
- 後端 Model、Biz、API、Transaction、Cache、Auditing、權限與錯誤回應邊界。
- Feature／Spec Fallback、Override 與共用影響。
- Commit 交付說明是否與實際 Code 一致。

## 4. 執行流程

```text
讀取需求與交付宣告
    ↓
鎖定 Base／Head Commit
    ↓
分析 Changed Files 與 Diff
    ↓
追蹤直接依賴與契約邊界
    ↓
比對正式架構與開發規範
    ↓
判斷是否觸發專項或全專案回歸 Gate
    ↓
產出發現與證據
    ↓
RD 判定、修正與複驗
```

## 5. 必查項目

### 5.1 需求與範圍

- 修改是否對應需求、Issue 或 PR 目標。
- 是否遺漏明確需求。
- 是否混入無關重構、格式化或其他功能。
- 新增單元的架構歸屬是否合理。

### 5.2 共用能力與架構

- 交付說明聲稱沿用的能力是否真的被使用。
- 是否已有相近共用能力卻另建局部版本。
- 共用能力不足時，擴充或獨立建立的理由是否符合規範。
- 修改共用底層時，是否檢查可能受影響的 Feature 與 Spec。

### 5.3 程式結構與契約

- Function／Method、註解、型別、非同步與存取範圍是否符合規範。
- API、Schema、Nullable、日期時間與資料格式是否維持契約一致。
- 是否繞過標準 Adapter、Template、FeatureDriver 或資料流程。
- 是否出現明顯的編譯、型別、Runtime 或安全風險。

### 5.4 React UI Style Strict-Compatible 檢測

前端修改若涉及 React Component、TSX／TS UI、共用 UI Library、Spec UI 或會控制 DOM Style 的 Hook，AI 白箱必須執行本項。

判定基準依 [`02_前端開發規範.md`](../../01_研發與技術文件/02_開發規範/02_前端開發規範.md)「5.7 UI Style 必須符合 Strict CSP 開發強度」。

必查：

- 是否新增或保留於本次重構範圍的 React `style={{ ... }}`。
- 是否由 WCMS 自行產生 `style="..."` 字串或 HTML Attribute。
- 是否使用 `setAttribute("style", ...)` 或 `style.cssText`。
- 是否以 `element.style.xxx = ...` 作為一般 UI 樣式機制。
- 是否在 Feature／Spec 業務 Code 建立未受管理的 `<style>` 或動態 Style Injection。
- 原本可用 `className`、`data-*`、CSS Module 或正式 CSS 解決的樣式，是否仍使用 Inline Style。
- 真正 Runtime Dynamic Style 是否沿用既有 Strict-Compatible 共用機制；若沒有共用能力，是否應回到底層擴充，而非在 Feature／Spec 建立平行方案。
- 第三方／Legacy 無法立即移除的 Style 行為，是否被隔離在最小 Wrapper／Adapter，並具有原因與後續處理條件。

> [!IMPORTANT]
> 平台 Runtime Style CSP 可因 CMS 自定義 Content 相容需求採 `balanced`；**AI 不得因此降低 React Component 的白箱判定標準。** WCMS 自行維護的 UI Code 仍以 `strict` CSP 相容強度判定。

> [!NOTE]
> CMS／TinyMCE 使用者自定義 Content 中的 `style` Attribute 不套用本項 Component Strict 規則；該內容改由 CMS Sanitizer、URL／HTML 安全流程與 Runtime CSP 檢查。WCMS 自行產生的 Template／Component HTML 不得假借 Content 名義列為例外。
>
> `element.style.xxx` 不得僅因關鍵字命中就宣稱瀏覽器在 Strict CSP 下一定阻擋；白箱判定重點是「WCMS 自行開發 UI 是否違反 Strict-Compatible 開發規範」。涉及瀏覽器實際 CSP 行為時，應標示需要 Runtime 驗證。

建議結果分類：

- **不符合**：WCMS 自行維護 UI Code 明確使用規範禁止的 Inline Style／Style Attribute，且不存在正式例外。
- **可能不符合**：第三方、CSSOM 或動態 Style 行為需確認 Wrapper、Runtime 或 Browser 行為。
- **不適用**：純 CMS 使用者 Content，且未涉及 WCMS 自行產生的 UI Template／Component。

### 5.5 交付與驗證真實性

- Commit Summary／Description 是否與修改內容一致。
- 是否清楚記錄影響範圍、共用能力異動與尚未執行的驗證。
- 未執行的 Build、測試、AA、Freego、弱掃或部署是否被錯寫成通過。

## 6. Gate 判定

檢測結束前必須給出：

```text
【需求與單元 Gate】通過／不通過／待確認
【專項 Gate】未觸發／觸發：<專項名稱>
【全專案回歸 Gate】未觸發／建議觸發
```

一般文字或不涉及 UI Code 的低風險局部修正通常不觸發其他 Gate；涉及 React UI Style、Cache、SSR、AA、API 契約、JWT、Auditing、Feature／Spec 或日期時間等邊界時，應執行對應規則或追加專項檢測。

## 7. 結果與複驗

每一項發現依 [`README.md`](./README.md) 的共通格式輸出。

RD 確認成立後才進行修正。複驗應使用新的 Head Commit，至少確認：

- 原問題已消失。
- 修正內容未超出確認範圍。
- 直接依賴與契約未引入新問題。
- React UI Style 修正沒有因 Runtime `balanced` 而重新引入 Strict-Incompatible 寫法。
- 原先觸發的專項 Gate 是否仍需重新檢測。
