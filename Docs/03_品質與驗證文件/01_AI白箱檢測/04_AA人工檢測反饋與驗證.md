# AA 人工檢測反饋與驗證

> 文件版本：Version 1.1  
> 文件狀態：draft（RD Review 後啟用）  
> 適用 Repository：`Saki2012/WCMS`  
> 適用範圍：經 AA 人工檢測確認、且 Freego 無法單獨判定的實際案例  
> 最終判定：RD／AA 人工檢測人員  
> AI 角色：依實際案例檢查相同程式風險，並列出必要的人工複驗項目

---

## 1. 目的

本文件記錄 WCMS 實際收到的 AA 人工檢測反饋，將人工判斷原因、成立條件、修正方向及 AI 白箱檢查注意項保留下來，供後續相同或相近功能檢查。

本文件只收錄：

- 有正式人工檢測紀錄或可回溯反饋來源的案例。
- 必須透過畫面、鍵盤、縮放、捲動或使用情境進行人工判斷的項目。
- Freego 無法單獨確認是否符合的項目。
- 具有後續重複檢查價值的人工判斷經驗。

本文件不收錄：

- Freego 已能直接辨識並明確產出結果的項目。
- 僅有 AI 推測、但沒有人工檢測來源的案例。
- 單純依關鍵字即可判定、且已由 `RULE_REGISTRY.yml` 或其他正式規則管理的項目。
- 尚未確認成立的一般最佳實務。

> [!IMPORTANT]
> 本文件是「人工案例與判斷依據」的補充來源，不取代 Freego 報告、WCAG、政府網站無障礙規範、`RULE_REGISTRY.yml` 或實際人工複驗。

## 2. Freego 與人工檢測的歸納邊界

### 2.1 歸納至本文件

符合下列情況時，歸納至本文件：

- Freego 無法從 HTML／CSS／ARIA 靜態結果直接判定。
- 是否成立取決於實際 Viewport、縮放倍率、鍵盤焦點或畫面可視範圍。
- 檢測人員需觀察操作過程與使用障礙後才能判定。
- 已有正式檢測網址、報告、截圖、錄影或人工補充說明。

### 2.2 不歸納至本文件

下列內容仍維持於原本的 Freego、AA Rule 或工具報告流程：

- Freego 能直接產出明確錯誤的檢測項目。
- 可由 DOM、Attribute 或固定規則自動確認的錯誤。
- 已有正式 Rule ID，且不依賴人工畫面判斷的項目。
- Freego 版本、執行方式及工具操作紀錄。

### 2.3 AI 的使用方式

AI 白箱檢測命中本文件案例時，應：

1. 搜尋相同或相近的程式結構。
2. 提出可能造成問題的程式證據。
3. 區分「靜態可確認」與「必須人工確認」。
4. 列出人工複驗條件與操作步驟。
5. 未取得實際畫面證據前，不得宣稱 AA 已通過或確定不符合。

## 3. 人工案例紀錄格式

後續新增案例時，使用下列格式：

```text
【案例 ID】
【來源網址】
【檢測項目】
【人工檢測原文】
【人工判斷原因】
【成立條件】
【建議修正方向】
【AI 白箱檢查注意項】
【必要人工複驗】
【不應誤判的情況】
```

同一根因同時影響多個成功準則時，可放在同一案例內，分別列出檢測項目，不需要重複建立多份相同案例。


### 3.1 同仁補充人工案例的建議 Prompt

同仁不需要自行整理完整案例格式。只要提供可回溯來源、人工判斷原因及已確認的解法方向，AI 應依本文件格式完成整理。

建議使用下列 Prompt：

```text
我要補充 AA 人工檢測實際案例，請更新
04_AA人工檢測反饋與驗證.md。

來源：
<正式檢測網址、報告、截圖、錄影或附件>

人工判斷原因：
<檢測人員實際認為造成使用障礙的原因>

確認解法：
<本次已確認或預計採用的修正方向>

請依序處理：
1. 實際讀取來源內容。
2. 整理指引、成功準則、檢測碼、檢測項目及人工檢測原文。
3. 先確認是否已有相同根因案例，避免重複新增。
4. 判斷是否屬於 Freego 可直接檢測：
   - Freego 可直接判定者，不追加至本文件。
   - 必須依畫面、裝置、縮放、鍵盤、焦點或人工操作判斷者，才追加至本文件。
5. 依現有格式建立或合併案例。
6. 區分來源事實、人工補充、AI 推論及待確認項目。
7. 補上 AI 白箱檢查注意項、必要人工複驗及不應誤判的情況。
8. 完成後回傳修改後的 Markdown 檔案與異動摘要。
9. 不要直接 Commit、Push，也不要自行建立正式 Rule ID。
```

也可使用較短的版本：

```text
我要補充 AA 人工檢測實際案例。

來源：<網址或附件>
人工判斷原因：<原因>
解法：<修正方向>

請先判斷是否只能由人工檢測；若是，追加至
04_AA人工檢測反饋與驗證.md。
請避免重複案例，完成後回傳 Markdown，不要直接 Commit。
```

收到上述要求後，AI 應自行：

1. 讀取目前最新版的本文件。
2. 解析正式檢測來源，不只依使用者摘要判斷。
3. 搜尋既有案例是否已有相同根因。
4. 決定新增案例或合併至既有案例。
5. 依序使用下一個 `AA-MANUAL-###` 案例 ID。
6. 保留人工檢測原意，不將特定案例擴張成所有站台的絕對規則。
7. 資料不足時標示待補或要求補充，不得自行猜測。
8. 回傳修改檔供 RD Review，不直接修改 Repository。

### 3.2 Warning 至 Error 的判定邊界

人工 AA 案例通常無法只靠靜態程式碼直接判定「一定符合」或「一定不符合」，因此 AI 白箱初次命中時，應保留從 Warning 到 Error 的證據層級。

本節中的 `Warning`／`Error` 是方便理解的顯示名稱，不另外建立一套正式結果狀態。正式白箱報告仍沿用 [`README.md`](./README.md) 的結果：

| 顯示名稱 | 白箱正式結果 | 適用情況 |
|---|---|---|
| Warning | `可能不符合` | 程式結構與既有人工案例相似，但尚未取得實際畫面或人工操作證據 |
| Error | `不符合` | 已有正式人工檢測結果，或可依指定環境穩定重現實際使用障礙 |
| Unknown | `無法確認` | 缺少來源、版本、測試環境、操作步驟或必要程式 |
| Pass | `符合` | 修正後已完成必要 Runtime 與人工複驗，確認障礙不再發生 |

> [!IMPORTANT]
> `Warning`／`Error` 表示證據與判定成熟度，不等同白箱嚴重度的 `High`、`Medium` 或 `Low`。

#### Warning：可能不符合

符合下列情況時，AI 原則上只能列為 Warning：

- 找到與既有人工案例相同或相近的程式結構。
- 例如窄版仍存在固定 Header、Sticky 區塊、Focus 捲動或可視範圍風險。
- 靜態程式能證明風險條件存在，但無法證明使用者一定受到障礙。
- 尚未取得指定瀏覽器、Viewport、縮放倍率、鍵盤操作、截圖、錄影或人工複驗結果。

此時 AI 應輸出：

```text
【結果】可能不符合
【判定層級】Warning
【原因】命中既有人工案例的高風險條件，但缺少 Runtime／人工證據
【需要的驗證】列出實際縮放、RWD、鍵盤與焦點操作
```

不得只看到 `position: fixed`、`position: sticky` 或相同 Class 名稱，就直接判定 Error。

#### Error：不符合

符合下列任一情況時，才可升級為 Error：

- 正式人工檢測紀錄已明確指出該頁面與版本發生此障礙。
- 依記錄的操作條件可穩定重現內容無法完整閱讀、焦點不可見或操作受阻。
- 修正前後有截圖、錄影、人工測試紀錄或其他可回溯證據。
- RD／AA 檢測人員已確認問題成立。

此時 AI 應輸出：

```text
【結果】不符合
【判定層級】Error
【人工案例】AA-MANUAL-###
【成立證據】正式檢測來源或可重現的 Runtime／人工操作結果
```

#### 同一案例在不同檢查範圍的判定差異

同一人工案例可以依檢查對象具有不同結果：

```text
正式檢測報告所指的原頁面與原版本
→ 已有人工成立證據
→ Error／不符合

其他頁面只找到相同固定 Header 程式
→ 尚未驗證是否真的造成可視範圍過小
→ Warning／可能不符合

完成程式修正，但尚未人工複驗
→ 原 Error 已處理，仍屬待人工複驗
→ 不得直接標示 Pass

完成必要 Runtime 與人工複驗
→ 確認障礙已排除
→ Pass／符合
```

#### 升級與降級流程

```text
AI 靜態命中相似風險
    ↓
Warning／可能不符合
    ↓
Runtime 或人工操作確認障礙成立
    ↓
Error／不符合
    ↓
完成程式修正
    ↓
已修正、待人工複驗
    ↓
人工複驗確認障礙排除
    ↓
Pass／符合
```

若人工操作無法重現，不能立即認定原檢測為誤判。應先核對：

- 檢測時與目前的 Commit／部署版本是否相同。
- 瀏覽器、作業系統、Viewport 與縮放倍率是否相同。
- 操作順序、鍵盤方向與選單狀態是否相同。
- 問題是否只出現在特定頁面、語系、資料或動畫狀態。

只有確認適用條件不成立，才由 RD 將該 Finding 判定為誤判或不適用。

## 4. 案例 AA-MANUAL-001：窄版畫面固定 Header 壓縮可視範圍

### 4.1 來源網址

主要複驗來源：

- `https://accessibility.moda.gov.tw/Applications/DetectLog/194701`

同根因人工檢測來源：

- `https://accessibility.moda.gov.tw/Applications/DetectLog/190475`
- `https://accessibility.moda.gov.tw/Applications/DetectLog/193325`
- `https://accessibility.moda.gov.tw/Applications/DetectLog/194284`

上述來源均曾指出導覽列於一般或高倍放大情境遮蔽內容、壓縮可視範圍，或使鍵盤焦點被固定區塊遮住，因此合併為同一根因案例，不重複建立案例 ID。

### 4.2 關聯檢測項目

#### 指引 1.4：可辨識

- 成功準則：`1.4.10 流動排版`（檢測等級 AA）
- 檢測碼：`CS2141007E`
- 檢測項目：使用 CSS 最大寬度和高度容納圖像

#### 指引 2.4：可導覽

- 成功準則：`2.4.7 焦點可視`（檢測等級 AA）
- 檢測碼：`CS2240700E`
- 檢測項目：使用者介面取得焦點時，使其鍵盤焦點指示具高可見度

### 4.3 人工檢測反饋

人工檢測指出：

- 網頁放大至 400% 時，上方固定導覽列可能遮住或壓縮下方內容的可視範圍。
- 在 200% 至 400% 放大並使用鍵盤操作時，部分焦點可能位於固定導覽列後方或因可視範圍過小而難以辨識。
- 相同情形應於全網站一併檢視。

### 4.4 人工判斷原因

本案例的人工判斷重點不是禁止使用 `fixed` 或 `sticky`。

實際問題是：

1. 弱視使用者可能將瀏覽器放大至 200% 至 400%。
2. 放大後的 CSS Viewport 會縮小，畫面進入手機或平板的 RWD 配置。
3. Header、機關 Logo、漢堡選單等區塊若仍固定於畫面上方，會長時間占用有限的垂直可視範圍。
4. 下方內容或鍵盤焦點可見範圍因此過小，造成資訊難以完整閱讀或焦點難以辨識。

因此，本案例的核心判斷為：

> Header 在手機、平板或高倍放大後的窄版畫面仍維持固定定位，並因此造成可視範圍過小。

### 4.5 建議修正方向

於手機、平板及高倍放大後所進入的窄版 RWD 範圍：

- 不使用固定 Header。
- 將 Header 放回一般文件流。
- 讓使用者向下閱讀時，Header 可隨頁面離開可視區域。
- 桌面寬版可依設計需求保留固定 Header。
- 實際 Breakpoint 依各站台 RWD 與 Header 高度決定，不將單一像素值視為全專案固定規則。

概念如下：

```text
桌面寬版
→ 可依設計保留固定 Header

手機／平板／高倍放大後的窄版
→ 移除固定定位
→ Header 回到一般文件流
```

### 4.6 AI 白箱檢查注意項

當修改或檢查 Header、Navigation、Layout、RWD 或焦點流程時，AI 應搜尋：

```text
position: fixed
position: sticky
position-fixed
fixed-top
sticky-top
Header
Site-Header
main-header
matchMedia
useMediaQuery
min-width
max-width
overflow
scroll-padding-top
scroll-margin-top
```

AI 至少確認：

- [ ] 固定 Header 是否只依頁面判斷，未依窄版 Viewport 判斷。
- [ ] 手機與平板 Breakpoint 下是否仍加入固定定位 Class。
- [ ] 桌面瀏覽器放大後進入窄版 RWD 時，固定定位是否仍存在。
- [ ] Header 在窄版的高度、Logo、Padding 或工具列是否占用過多垂直空間。
- [ ] 下方內容是否有固定高度、`100vh`、Sticky Section 或 Overflow，進一步放大可視範圍不足。
- [ ] Tab／Shift + Tab、Skip Link、Accesskey 或頁內錨點的焦點是否可能停在 Header 後方。
- [ ] 選單展開時的 Overlay／Drawer 是否被誤認為一般頁面內容遮蔽。
- [ ] 相同 Header、Layout 或共用 Hook 是否影響其他頁面。

### 4.7 AI 結果判定限制

只有程式證據時，AI 可判斷：

- 固定定位是否存在。
- 固定定位是否於窄版持續套用。
- 是否缺少 RWD 條件。
- 是否存在高風險的 Fixed／Sticky／Viewport 組合。

但 AI 不得只憑 `fixed` 或 `sticky` 判定違規。

沒有實際操作證據時，結果應標示為：

- `可能不符合`，或
- `需要人工複驗`

人工檢測已明確確認相同畫面障礙時，才能依實際證據判定為 `不符合`。

### 4.8 必要人工複驗

至少檢查：

- [ ] 手機版畫面。
- [ ] 平板版畫面。
- [ ] 瀏覽器 200%、300%、400% 放大。
- [ ] 約 320 CSS px 寬度的窄版畫面。
- [ ] 頁面由上往下正常捲動。
- [ ] 使用 Tab 正向移動焦點。
- [ ] 使用 Shift + Tab 反向移動焦點。
- [ ] 開啟及關閉漢堡選單。
- [ ] 選單關閉後，下方內容仍可完整閱讀。
- [ ] 焦點停留時，焦點框未被 Header 蓋住。
- [ ] 全網站使用相同 Header／Layout 的頁面已抽查。

### 4.9 不應誤判的情況

下列情形不應只依外觀直接判定為本案例：

- `fixed` 或 `sticky` 本身。
- 內容捲動過程中短暫經過 Header 後方，但仍可透過正常捲動完整閱讀。
- 漢堡選單展開後以 Overlay／Drawer 覆蓋背景，且背景已停止操作、選單可完整捲動。
- Header 雖固定，但人工驗證確認窄版仍保有足夠可視範圍，內容與焦點皆可完整閱讀。
- 問題實際由輪播、動畫、Transform、固定高度或 Overflow 裁切造成，而非 Header 固定定位。

不同根因應分開記錄，不得全部歸類為固定 Header 問題。

## 5. 文件維護原則

新增人工案例時：

1. 必須保留正式檢測網址或可回溯來源。
2. 優先保留人工檢測原文，不由 AI 改寫成不同規範。
3. 另外整理人工判斷原因與實際成立條件。
4. 明確標示哪些內容可由 AI 靜態檢查。
5. 明確標示哪些內容必須由人工複驗。
6. Freego 可直接檢測的內容不重複收錄。
7. 新案例是否需要建立或調整 Rule ID，由 RD 依 `RULE_REGISTRY.yml` 維護規則判定。
8. 未實際執行人工複驗時，不得記錄為已通過。
9. 同仁可使用第 3.1 節 Prompt 交由 AI 整理，但 AI 必須回傳檔案供 RD Review，不直接 Commit。
10. 靜態命中人工案例時原則上先列為 Warning／`可能不符合`；只有具備正式人工或 Runtime 成立證據時，才列為 Error／`不符合`。
11. 完成程式修正但尚未人工複驗時，應標示「已修正、待人工複驗」，不得直接標示 `符合`。

## 6. 案例 AA-MANUAL-002：展開式導覽選單未正確管理收合、焦點範圍與返回位置

### 6.1 來源網址

- `https://accessibility.moda.gov.tw/Applications/DetectLog/190475`
- `https://accessibility.moda.gov.tw/Applications/DetectLog/191089`
- `https://accessibility.moda.gov.tw/Applications/DetectLog/193325`

### 6.2 關聯檢測項目

#### 指引 1.4：可辨識

- 成功準則：`1.4.1 色彩使用`
- 檢測碼：`CS1140101E`
- 來源情境：鍵盤焦點進入並展開導覽選單後，展開內容持續遮蔽其他主要內容。

#### 指引 2.4：可導覽

- 成功準則：`2.4.3 焦點順序`
- 檢測碼：`GN1240301E`
- 來源情境：漢堡選單開啟後，焦點可離開選單進入背景內容，關閉後亦需確認焦點返回合理位置。

#### 指引 2.4：可導覽

- 成功準則：`2.4.7 焦點可視`
- 檢測碼：`CS2240700E`
- 來源情境：高倍放大時，未收合選單遮蔽主要內容，需要可辨識的焦點及可操作的關閉方式。

### 6.3 人工檢測反饋

人工檢測曾指出：

- 展開上層導覽項目後，完成該區鍵盤操作時，選單不應持續覆蓋主要內容而沒有合理的離開方式。
- 200% 以上進入漢堡選單配置時，選單需具有可理解的鍵盤操作生命週期。
- 選單開啟期間若採用遮罩／抽屜式互動，焦點不應任意跳到背景內容。
- 應提供鍵盤可操作的關閉方式；來源檢測特別提到 `Esc`。
- 關閉後需將焦點帶回合理的觸發位置，避免鍵盤使用者失去操作脈絡。

### 6.4 人工判斷原因

本案例不是要求所有 DropDown、Mega Menu 或 Hamburger Menu 都「焦點離開就立即收合」。

核心判斷是：

1. 選單開啟後是否形成一個會遮蔽主要內容的互動區域。
2. 鍵盤使用者是否能預期地在選單中操作、離開或關閉。
3. 若採 Modal／Drawer 型態，背景內容是否仍被錯誤地納入 Tab 順序。
4. 關閉後焦點是否回到可理解的位置。
5. 高倍放大後選單是否因 RWD 改變，而出現與桌面版不同的焦點風險。

成立條件通常為：

> 選單開啟後會遮蔽或阻斷主要內容，但焦點範圍、關閉方式或焦點返回沒有與互動模式一致地管理。

### 6.5 建議修正方向

依選單型態處理，不套用單一寫法：

- 一般桌面 DropDown：
  - 鍵盤可開啟及關閉。
  - 焦點離開該導覽群組後，應回到合理收合狀態。
  - 不應讓已失去操作脈絡的選單長時間覆蓋主要內容。

- 手機／高倍放大的 Hamburger Drawer：
  - 觸發按鈕需可用鍵盤操作。
  - 若互動設計屬 Modal／Drawer，開啟期間應限制焦點於有效操作區。
  - 支援 `Esc` 關閉。
  - 關閉後焦點回到觸發按鈕或其他明確且合理的位置。
  - 背景若不可操作，需同步避免其成為鍵盤焦點目標。

- 非 Modal 型導覽選單可允許焦點自然離開，只要離開後狀態合理且不造成遮蔽。

- 選單不需要因每一次焦點變更都立即收合。
- `Esc` 只是來源人工檢測明確要求的可用方式之一，不代表所有非覆蓋型選單都只能以 `Esc` 關閉。

人工檢測要求狀態型控制元件除了名稱與角色外，還需讓輔助科技取得目前狀態；來源案例建議以 `aria-selected` 表達已選取狀態。

### 10.4 人工判斷原因

核心問題是：

> 視覺上已有「目前選擇」狀態，但輔助科技只能知道這是按鈕，無法得知目前哪一個選項有效。

### 10.5 建議修正方向

- 明確定義控制元件的語意模型。
- 若元件採用可選項目角色，使用與角色相容的 `aria-selected`。
- 若採 Toggle Button 模型，應評估與該角色相容的狀態屬性。
- 視覺狀態與 ARIA 狀態必須由同一份 State 驅動，避免不同步。
- 多語系的可存取名稱由共用 i18n／平台能力提供。

AI 應搜尋：

```text

```

AI 至少確認：

- [ ] 是否存在視覺 Active Class 但沒有可存取狀態。
- [ ] ARIA 狀態是否與實際 Role 相容。
- [ ] State 變更後 ARIA 是否同步。
- [ ] 初始預設值是否有正確狀態。
- [ ] 多語系名稱是否與目前站台語系一致。

### 10.7 AI 結果判定限制

只看到 `aria-selected` 缺少，不代表一定違規；必須先確認元件角色與互動模型。

AI 靜態命中「視覺有 Active、可存取狀態缺失」時可列 Warning，實際報讀無法辨識目前選取值時才升級。

### 10.8 必要人工複驗

- [ ] 鍵盤可依序操作所有字級選項。
- [ ] 螢幕報讀可得知控制名稱。
- [ ] 螢幕報讀可得知目前選取／啟用狀態。
- [ ] 切換後狀態立即更新。
- [ ] 視覺 Active 與報讀狀態一致。
- [ ] 重新載入後預設狀態合理。

### 10.9 不應誤判的情況

- 不應要求所有 Button 都加 `aria-selected`。
- `aria-selected`、`aria-pressed` 等屬性不可脫離 Role 語意單獨套用。
- 單純動作型按鈕沒有「持續選取狀態」時不適用本案例。
- 只因存在 `active` CSS Class 不足以直接判定 ARIA 錯誤，需先確認該 Active 是否代表使用者可感知的持續狀態。

- 關聯人工建議：圖片連結在 Firefox 可看到焦點框，但 Chrome 看不到，需進行跨瀏覽器焦點可視性確認。

- [ ] Outline／Box Shadow 是否被 Overflow 裁掉。

2. Component 內的 `aria-label`、`title`、隱藏輔助文字等也應使用相同 i18n 來源。
3. 多語系切換後，可見文字與不可見的可存取名稱不能留在上一個語系。

### 15.5 建議修正方向

- `<html lang>` 由 WCMS 語系狀態／SSR 輸出統一管理。
- Component 的可存取名稱使用 i18n Key，不硬編碼英文或中文。
- 輪播 Prev／Next、Menu Open／Close、下載、搜尋等平台共用文字優先由共用元件處理。
- `zh-Hant-TW` 僅作為來源人工報告對臺灣繁體中文站的建議，不擴張成所有語系固定值。

### 15.6 AI 白箱檢查注意項

AI 應搜尋：

```text

aria-label="Previous"
aria-label="Next"
Previous
Next
Open
Close

i18n
t(
Lang
locale
```

AI 至少確認：

- [ ] HTML Lang 是否由目前語系決定。
- [ ] SSR 初始 HTML 的 Lang 是否與 Hydration 後一致。
- [ ] 共用元件是否硬編碼英文 `aria-label`。
- [ ] 語系切換後 ARIA／Title 是否同步。
- [ ] 中文站與英文站是否共用錯誤的單一常數。
- [ ] 使用者 Key／CMS 資料中的可存取文字是否有語系來源。

### 15.7 AI 結果判定限制

AI 可靜態找到硬編碼字串與 `<html lang>`，但實際頁面內容是否屬該語系、SSR 首屏輸出是否正確，需依 Runtime 頁面確認。

### 15.8 必要人工複驗

- [ ] 中文站初次 SSR 回應即有正確 Lang。
- [ ] 英文／其他語系切換後 Lang 正確更新。
- [ ] Prev／Next 等控制名稱跟著語系切換。
- [ ] 螢幕報讀軟體不會因錯誤 Lang 使用不適合的語音。
- [ ] 頁面重新整理後語系仍一致。
- [ ] 多語系路由直接進入時，不先輸出錯誤語系再改寫。

### 15.9 不應誤判的情況

- 不應把 `zh-Hant-TW` 寫成 WCMS 所有站台固定值。
- 外文專有名詞出現在中文頁面不代表整頁 Lang 錯誤。
- 個別外語片段可有自己的語言標記，不應因此改變整頁主語系。
- 只看到 `Previous` 字串不代表使用者一定會聽到它，需確認該字串是否真的成為可存取名稱；但共用元件硬編碼仍屬白箱風險。

## 16. 案例 AA-MANUAL-012：控制元件重複提供名稱／狀態資訊，造成輔助科技重複報讀

### 16.1 來源網址

`https://accessibility.moda.gov.tw/Applications/DetectLog/194284`

### 16.2 關聯檢測項目

#### 指引 4.1：相容性

- 成功準則：`4.1.2 名稱、角色和值`
- 檢測碼：`GN1410200E`
- 來源情境：漢堡選單摺疊控制已有 ARIA 狀態資訊，又保留額外 `title`，人工檢測認為可能造成重複報讀或資訊混淆。

### 16.3 人工檢測反饋

人工檢測建議避免在已具有足夠可存取名稱與展開／收合狀態資訊的控制元件上，再疊加會造成相同語意重複的 `title`。

### 16.4 人工判斷原因

需要特別區分：

- `aria-expanded` 表達「展開／收合狀態」。
- 可見文字、`aria-label` 或 `aria-labelledby` 等負責「控制元件名稱」。
- `title` 可能成為補充資訊或名稱來源。

因此不能把來源建議簡化為：

> 有 `aria-expanded` 就一定刪除 `title`。

真正成立條件是：

> 控制元件已經具有完整可存取名稱與狀態，但額外 `title` 再次輸出同義資訊，造成實際輔助科技重複報讀或混淆。

### 16.5 建議修正方向

- 先確認控制元件的可存取名稱來源。
- 保留必要的名稱與 `aria-expanded` 狀態。
- 若 `title` 只是重複相同內容，移除多餘資訊。
- 若 `title` 是唯一名稱來源，不得只因看到 `aria-expanded` 就直接刪除。
- WCMS 共用 Button／Hamburger 元件應統一名稱與狀態策略。

### 16.6 AI 白箱檢查注意項

AI 應搜尋：

```text
aria-expanded
aria-label
aria-labelledby
title
button
navbar-toggler
hamburger
menu
```

AI 至少確認：

- [ ] `title` 與 `aria-label` 是否完全重複。
- [ ] `title` 是否只是重複「開啟／關閉主選單」。
- [ ] 刪除 `title` 後是否仍有可存取名稱。
- [ ] `aria-expanded` 是否與實際狀態同步。
- [ ] 是否因多個來源組合出過長或重複名稱。

### 16.7 AI 結果判定限制

DOM 中同時出現 `title`、`aria-label`、`aria-expanded` 只能視為檢查訊號，不能直接判定 Error。

必須實際確認 Accessible Name 計算與輔助科技報讀結果。

### 16.8 必要人工複驗

- [ ] 聚焦 Hamburger Button。
- [ ] 關閉狀態報讀名稱自然且只出現一次。
- [ ] 展開後狀態可被理解。
- [ ] 再次聚焦／收合後不重複讀出同義資訊。
- [ ] Chrome／Firefox 搭配至少一種主要螢幕報讀工具複驗。
- [ ] 移除 `title` 後控制名稱仍存在。

### 16.9 不應誤判的情況

- `aria-expanded` 不能取代控制元件名稱。
- 不得因存在 `aria-expanded` 就無條件刪除 `title`。
- `title` 與 ARIA 同時存在不一定會重複報讀，需確認實際 Accessible Name／Description。
- 若 `title` 提供不同且必要的補充資訊，需另外判斷，不應套用本案例直接刪除。

## 17. 案例 AA-MANUAL-013：同一資源的毗鄰圖片與文字各自成為連結，造成重複報讀

### 17.1 來源網址

`https://accessibility.moda.gov.tw/Applications/DetectLog/193706`

### 17.2 關聯檢測項目

#### 指引 2.4：可導覽

- 成功準則：`2.4.4 鏈結目的（脈絡）`
- 檢測碼：`HM1240402E`
- 檢測項目：合併相同資源的毗鄰圖片與文字鏈結。

### 17.3 人工檢測反饋

人工檢測發現，卡片中的圖片與鄰近 `View all`／文字內容分別建立連結，但兩者前往同一資源；螢幕報讀會依序把它們當成兩個功能元件，造成同一目的重複報讀。

### 17.4 人工判斷原因

本案例的核心是：

1. 圖片與文字在視覺上屬同一張 Card／同一功能。
2. 兩個毗鄰 Link 的 Destination 相同。
3. 輔助科技卻需要走訪兩個等效操作點。
4. 使用者沒有從第二個 Link 得到新的功能價值。

成立條件為：

> 同一視覺功能被拆成毗鄰且等效的多個 Link，導致鍵盤與語音使用者重複走訪／重複報讀。

### 17.5 建議修正方向

優先依元件結構整合：

- 單一卡片只有一個目的時，讓圖片與文字共用同一個 Link。
- 若圖片只是 Link 內的視覺裝飾，避免它再產生第二個重複名稱。
- 若業務需求確實需要兩個不同操作點，則必須確認兩者目的或脈絡真的不同，而不是只複製相同 URL。
- 共用 Card／List 元件應從模板層修正，避免每頁重做。

### 17.6 AI 白箱檢查注意項

AI 應搜尋：

```text
<a
<Link
LangLink
href
to=
Card
Picture
Image
View all
Read more
map(
```

AI 至少確認：

- [ ] 同一 Card 內是否有兩個相鄰 Link 指向相同 URL。
- [ ] 一個只包圖片、另一個只包標題／View all。
- [ ] 兩個 Link 的可存取名稱是否實質相同。
- [ ] 是否能由共用 Card Component 合併。
- [ ] 合併後是否造成巢狀互動元件問題。
- [ ] 圖片 Alt 是否在合併後讓 Link 名稱變得過長或重複。

### 17.7 AI 結果判定限制

AI 可以靜態比對同一 Render 區塊的 `href/to`，但若 URL 是 Runtime 組合、或兩個 Link 雖 URL 相同卻承擔不同操作脈絡，仍需要人工判斷。

### 17.8 必要人工複驗

- [ ] Tab 進入該 Card 時只需一次主要操作即可前往同一資源。
- [ ] 螢幕報讀不會先讀圖片 Link、再讀等效文字 Link。
- [ ] Link 的最終可存取名稱能清楚表達目的。
- [ ] 滑鼠仍可合理點擊圖片與文字區域。
- [ ] 卡片內若另有次要功能，仍可獨立操作。
- [ ] 中英文版皆確認。

### 17.9 不應誤判的情況

- 相同 URL 不一定代表一定要合併；若兩個 Link 在不同區塊或不同脈絡中，可能各自合理。
- 不相鄰的導覽、Breadcrumb、本文連結即使指向相同資源，也不屬本案例。
- 一張 Card 內若圖片與文字分別代表不同功能，不應強行合併。
- 合併 Link 時不可產生 `<a>` 巢狀 `<a>` 或把 Button 等互動元件包進 Link 的新問題。
