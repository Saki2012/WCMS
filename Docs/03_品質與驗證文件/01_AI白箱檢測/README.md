# WCMS AI 白箱檢測

> 文件版本：Version 1.0  
> 適用 Repository：`Saki2012/WCMS`  
> 執行與最終判定：RD  
> AI 角色：依正式文件與指定 Commit 提供靜態分析、證據與修正建議

## 1. 目的

本目錄定義 WCMS 使用 AI 協助進行白箱檢測的共同流程。

AI 白箱檢測用來確認指定版本的程式是否符合 WCMS 架構、開發規範、需求與共用底層契約。它不能取代 RD／QA 實際操作、Build、Typecheck、Lint、AA、Freego、弱點掃描、效能測試或部署驗證。

## 2. 角色與責任

- **RD**：發起檢測、確認範圍、判定問題、決定是否修正與執行實際驗證。
- **AI**：讀取正式文件與程式，提出規則依據、程式證據、影響、信心程度與建議。
- **QA／AA／資安／維運**：執行其專業工具、環境與實際操作驗證。

> [!WARNING]
> AI 不得自行宣布專案、PR、AA、Freego、弱點掃描、部署或功能驗證已通過。

## 3. 檢測基準

原則上檢查已 Commit 且 Push 的版本，並使用 Commit SHA 鎖定內容。

- `code_ref`：被檢查程式的 Commit SHA。
- `rules_ref`：本次採用文件與白箱規則的 Commit SHA。
- `base_ref`：單元檢測用的修改前 Commit SHA。
- `head_ref`：單元檢測用的修改後 Commit SHA。

同一對話中，AI 應優先自行由對話、Commit、PR、Summary、Description 與 Diff 解析上述資訊；只有存在多個可能版本或範圍無法判斷時，才要求 RD 補充。

Commit／PR／Issue 用來理解修改意圖與交付宣告；指定 Commit 的實際程式碼才是檢測事實來源。

## 4. 規則讀取順序

AI 執行檢測前，依序讀取：

1. [`WCMS_AI資料讀取入口.md`](../../WCMS_AI資料讀取入口.md)。
2. [`Docs/README.md`](../../README.md)。
3. [`AI_INDEX.yml`](../../AI_INDEX.yml)。
4. 對應的系統架構文件。
5. [`01_共通開發規範.md`](../../01_研發與技術文件/02_開發規範/01_共通開發規範.md)。
6. 前端或後端開發規範。
7. [`04_Git與Commit規範.md`](../../01_研發與技術文件/02_開發規範/04_Git與Commit規範.md)。
8. 本目錄中對應的白箱檢測規範。
9. 指定 Commit 的實際程式與設定。

正式判定優先順序：指定 Commit 的實際程式、正式架構與開發規範、白箱檢測規則、Commit／PR／Issue、對話內容。

## 5. 三個檢測 Gate

每個 PR 都要經過三個 Gate 判斷，但不代表每次都完整執行三種檢測。

1. **需求與單元 Gate**：每個 PR 原則上必跑。
2. **專項 Gate**：每個 PR 都判斷是否命中技術邊界；命中時執行對應專項。
3. **全專案回歸 Gate**：每個 PR 都判斷是否達到大型底層重構、里程碑或 Release 前的觸發條件。

對應文件：

- [`01_需求與單元白箱檢測.md`](./01_需求與單元白箱檢測.md)
- [`02_專項白箱檢測.md`](./02_專項白箱檢測.md)
- [`03_全專案白箱回歸檢測.md`](./03_全專案白箱回歸檢測.md)

## 6. 共通結果格式

每一項發現至少包含：

```text
【Rule ID】
【結果】
【信心程度】
【規範來源】
【程式證據】
【影響】
【建議方向】
【需要的驗證】
```

### 結果狀態

- **符合**：有足夠證據確認符合規則。
- **不符合**：有明確規範與程式證據。
- **可能不符合**：存在風險，但仍需 Runtime、資料或業務條件確認。
- **無法確認**：資料、權限、環境或規則不足。
- **未檢查**：本次未涵蓋。
- **不適用**：規則與本次範圍無關。

### 信心程度

- **高**：規範與程式證據明確，可直接重現或定位。
- **中**：風險明確，但需確認執行條件、資料或上下游。
- **低**：主要為推論或架構疑慮，不得直接要求修改。

## 7. AI 幻覺與延伸限制

- 沒有正式規範或程式證據時，不得判定為確定問題。
- 推論必須明確標示為推論。
- 不得以一般最佳實務推翻 WCMS 正式架構。
- 不得把規劃中的能力當成目前已存在。
- 不得把 Legacy Code 反向視為正式規範。
- 不得只依檔名、命名或關鍵字推定實際責任。
- 低信心或無法確認的項目不得直接進入修正。
- AI 發現的項目須由 RD 判定為成立、誤判、待確認、接受風險或不適用。

## 8. 修正與複驗

RD 確認問題成立並要求修正後，AI 才能進入修正階段。

修正交付原則：

- 提供只包含本次新增或修改單元的 ZIP。
- 保留 Repository 相對路徑，供 RD 直接覆蓋。
- 不包含完整專案、Build 產物、`node_modules`、`bin`、`obj` 或無關檔案。
- 需要刪除檔案時，另外列出手動刪除清單。
- 不得順便處理未經 RD 確認的其他發現或重構。

RD 覆蓋後應執行必要 Build、測試與實際驗證，再 Commit、Push。AI 複驗必須使用修正後的新 Commit SHA，並確認原問題是否消失及是否引入新風險。

## 9. 共通流程

```text
RD 發起檢測
    ↓
AI 鎖定 Commit 與規則來源
    ↓
AI 讀取正式文件並選擇檢測模式
    ↓
AI 提出發現、證據與信心程度
    ↓
RD 判定
    ↓
成立項目才進入修正
    ↓
AI 提供修改單元 ZIP
    ↓
RD 覆蓋、Build／測試、Commit／Push
    ↓
AI 以新 Commit SHA 複驗
```
