# WCMS 前端開發規範

> 文件狀態：Draft v0.2  
> 適用範圍：`WCMS_Frontend`  
> 對標分支：`Feature/Dev`  
> 最後整理：2026-07-31

> [!NOTE]
> 本文件先收斂「不依賴前端架構重整即可成立」的技術開發規範，作為下一階段前端 Code Review、新功能開發與既有程式整改依據。
>
> Route、Loader、Form Template、Feature／Spec、API Adapter 等完整分層與框架使用規則，待前端 Code Review 完成後再逐步補入，不在本版過早定案。
>
> Function 長度、註解、Library 優先、無效 Code 清理、緊密排版與 Function 拆分原則，請先遵循 `01_共通開發規範.md`。

## 1. 程式單元與撰寫規則

### 1.1 Region 排列順序

`.ts` 一般依實際內容使用：

```text
Property
Initialization
Public
Protected Virtual
Protected
Private
```

`.tsx` 一般依實際內容使用：

```text
Property
Initialization
Public
Protected
Section
EntityComp
Private
```

> [!NOTE]
> 沒有內容的 Region 不建立。
>
> `Initialization` 僅放模組載入階段會立即使用的 Constant 或 Helper；一般 Runtime 才會執行的 Helper，依責任放入 `Protected` 或 `Private`。

### 1.2 Component 與 Helper 的 Region 判斷

- 可用 `<Xxx />` 呼叫的 React Component，才可放入 `Public`、`Section` 或 `EntityComp`。
- 必須用 `xxx()` 呼叫的一般 Function、狀態解析、資料組裝、事件時機或條件判斷，放入 `Protected` 或 `Private`。
- `Section`、`EntityComp` 不放一般 Helper、Hook Timing 或回傳 JSX 的 Render Node Helper。
- SSR 真正 Render 流程，例如 `renderApp`、`renderByEntry`、`renderAppHtml`，保留既有命名例外。

### 1.3 Named Export

一般前端功能單元使用 Named Export：

```ts
export const SurveyForm = () =>
{
    return <div />;
};
```

> [!WARNING]
> 一般 Feature、Spec、Hook、Component 或 Library 不使用 `export default`。
>
> Vite、ESLint 等框架設定檔，或第三方契約明確要求 Default Export 時例外。

### 1.4 Function 與 Component 宣告方式

新增前端方法原則上使用：

- `const`
- `interface`
- `type`
- Custom Hook
- Arrow Function Component

```ts
/** 建立問卷標題。 */
const buildSurveyTitle = (name: string): string =>
{
    return name;
};
```

> [!WARNING]
> 除框架、第三方套件或既有型別契約要求外，不新增傳統 `function` 宣告。

### 1.5 JSX 區塊使用 React Component

涉及 DOM／JSX 的可讀區塊，優先拆成 PascalCase React Component：

```tsx
/** 問卷欄位區塊。 */
const AnswerFields = (props: { items: AnswerDisplayItem[]; }) =>
{
    return (
        <>
            {props.items.map(item => <LibTextBox key={item.key} ColumnDisplayName={item.label} InputValue={item.value} disabled={true} />)}
        </>
    );
};
```

直接使用：

```tsx
<AnswerFields items={items} />
```

> [!WARNING]
> 新增或重構畫面區塊時，不主動建立 `renderXxx`、`buildXxxNode`、`xxxNode` 等回傳 JSX 的 Helper 或節點變數。

### 1.6 Component 責任

Component 原則上只負責：

- JSX／DOM 組合。
- Props 傳遞。
- UI 狀態呈現。
- 事件綁定。
- AA 語意與互動。

Component 不直接處理：

- Axios／API。
- Toast 的底層解析。
- 複雜 Payload 組裝。
- 跨功能共用資料整理。
- 重複的日期、URL 或格式轉換。

### 1.7 List Key 放置位置

`key` 放在 `map` 直接回傳的那一層：

```tsx
items.map(item => <SurveyRow key={item.InternalId} item={item} />);
```

> [!WARNING]
> `key` 不放在 Component 內部固定子節點，也不以 Wrapper 內部節點代替直接回傳層的 `key`。

## 2. TypeScript 型別與資料契約

### 2.1 後端 Schema 是唯一契約來源

後端已提供的下列型別，一律使用 OpenAPI Schema 產生結果：

- Model
- DTO
- Request
- Response
- Enum
- Required／Optional
- Nullable
- 欄位型別

```ts
import type { components } from "@/types/api";

type Survey = components["schemas"]["Survey"];
type SurveySubmissionRequest = components["schemas"]["SurveySubmissionRequest_DTO"];
```

> [!WARNING]
> 不得在前端重新宣告與後端內容相同的 Interface／Type。
>
> 後端 Schema 不正確時，應修正後端 Model、Attribute 或 OpenAPI 契約後重新產生型別，不得以前端手寫補丁掩蓋契約錯誤。

### 2.2 禁止模糊空值語意

以下型別具有不同意義：

```ts
value: string;
value: string | null;
value?: string;
```

| 型別 | 語意 |
|---|---|
| `T` | 值一定存在 |
| `T \| null` | 欄位存在，但可明確無值 |
| `prop?: T` | 欄位本身可以不存在 |
| `T[]` | 清單；無資料使用 `[]` |

> [!WARNING]
> 不得無理由將型別擴張為 `T | null | undefined`，或使用 `prop?: T | null` 卻沒有清楚定義各空值狀態。
>
> Optional 與 Nullable 必須依照後端 Schema，或由明確的前端 UI 狀態契約定義。

### 2.3 UI 狀態不得污染後端 DTO

後端 DTO 與前端 UI 狀態應分開：

```ts
type AccountDto = components["schemas"]["Account"];

interface AccountFormState
{
    data: AccountDto;
    selectedRoleId: string;
    isDirty: boolean;
}
```

建議命名明確區分：

```text
XxxDto
XxxRequest
XxxResponse
XxxFormState
XxxViewModel
XxxPayload
```

> [!NOTE]
> UI 需要額外狀態時，建立前端專用型別，不修改或放寬後端產生型別。

### 2.4 型別應排除不合理狀態

不建議使用多個 Optional／Nullable 欄位拼出模糊狀態：

```ts
interface QueryState<T>
{
    data?: T | null;
    isLoading?: boolean;
    errorText?: string | null;
}
```

狀態互斥時，優先使用 Discriminated Union：

```ts
type QueryState<T> =
    | { status: "idle"; }
    | { status: "loading"; }
    | { status: "success"; data: T; }
    | { status: "error"; errorText: string; };
```

> [!TIP]
> 型別設計的目的不是接受所有可能組合，而是排除不應發生的組合。

### 2.5 ApiResponse 泛型語意唯一

前端契約應與後端一致：

```ts
export interface ApiResponse<T>
{
    IsSuccess: boolean;
    Data: T[];
    SysMessage: SysMessageModel[];
}
```

正確：

```ts
ApiResponse<Account>
ApiResponse<ModelDisplaySchema>
ApiResponse<number>
```

不正確：

```ts
ApiResponse<Account[]>
ApiResponse<ModelDisplaySchema[]>
```

> [!WARNING]
> `ApiResponse<T>` 的 `T` 已代表 `Data` 陣列元素，不得再將陣列型別放入泛型形成二層陣列語意。

### 2.6 單筆與多筆資料契約

```ts
const firstData = response.Data[0] ?? null;
const listData = response.Data;
```

- 單筆：由共用 Adapter／Hook 取 `Data[0]`。
- 多筆：直接使用 `Data`。
- 無資料：使用 `[]`。
- Feature Component 不自行判斷 `Array.isArray`、`Data?.[0]` 或其他不同解析方式。

### 2.7 限制 any

一般 Feature、Spec、Hook、Component 與 Library 不使用 `any`。

未知資料先使用：

```ts
unknown
```

再透過：

- Type Guard
- Parser
- Validator
- Adapter

轉成可使用型別。

> [!NOTE]
> `any` 僅允許出現在第三方套件邊界、Legacy Adapter 或必要相容層，並限制在最小範圍，不得向 Feature 內部擴散。

### 2.8 限制 as 與非空斷言

不得為了消除 TypeScript 錯誤直接使用：

```ts
value as any
value as Account
value!
```

> [!WARNING]
> `as` 與 `!` 必須能證明 Runtime 一定成立，不得作為忽略型別問題的快捷方式。

### 2.9 外部資料必須驗證

下列來源一律視為不可信 Runtime 資料：

- API Response
- `JSON.parse`
- Local／Session Storage
- Query String
- Route Param
- `postMessage`
- iframe
- CMS HTML
- 第三方 Callback
- 使用者上傳內容

```ts
const parseAccount = (value: unknown): Account =>
{
    if (!isAccount(value)) throw new Error("Invalid account data.");
    return value;
};
```

### 2.10 Utility Type 使用限制

`Pick`、`Omit`、`Record` 等可在責任清楚時使用。

`Partial<T>` 不得用於模糊後端 Model／DTO：

```ts
// 不建議
type AccountPatch = Partial<Account>;
```

應使用具名契約：

```ts
interface UpdateAccountNamePayload
{
    AccountId: Account["AccountId"];
    AccountName: Account["AccountName"];
}
```

### 2.11 Enum 與 Union 完整處理

後端已有 Enum 時使用 Schema 型別，不手寫另一套字串。

前端 Literal Union 應完整處理所有分支：

```ts
const assertNever = (value: never): never =>
{
    throw new Error(`Unhandled value: ${String(value)}`);
};
```

> [!TIP]
> 重要狀態的 `switch` 應具備 Exhaustive Check，避免新增狀態後舊流程靜默漏接。

### 2.12 日期、時間與時區契約

前端不得將以下資料全部視為同一種普通 `string` 或 `Date`：

```text
DateOnly
Local DateTime
UTC DateTime
DateTimeOffset
datetime-local Input
格式化後顯示文字
```

原則：

| 資料 | 處理方式 |
|---|---|
| 只有年月日 | DateOnly 字串，不進行 UTC 位移 |
| 實際時間點 | UTC／Offset ISO 契約 |
| `datetime-local` | 使用者所在地 Local DateTime |
| 畫面顯示 | 使用共用 `LibDate` 與語系格式化 |

> [!WARNING]
> Feature 不自行散落 `new Date(...)`、自行加減時區或寫死日期格式。
>
> 既有 `LibDate` 能力不足時，依共通規範提出 Library 擴充，不在個別 Feature 建立另一套日期流程。

## 3. React Component 與狀態生命週期

### 3.1 Props、State 與 API 資料不可直接修改

禁止：

```ts
props.data.Name = value;
state.items.push(item);
apiData.Detail[index].Title = title;
```

應建立新的 Object／Array Reference：

```ts
const nextData = { ...data, Name: value };

const nextItems = items.map(item =>
{
    if (item.InternalId !== targetId) return item;
    return { ...item, Title: value };
});
```

> [!WARNING]
> 除共用框架明確提供 Mutable Binding 外，不得直接 Mutate Props、React State 或 API Response。

### 3.2 Hook 執行規則

- Hook 不得放在條件式。
- Hook 不得放在迴圈。
- Hook 不得放在一般 Helper。
- Custom Hook 以 `use` 開頭。
- 不得因排版或重構改變 Hook 呼叫順序。

### 3.3 Dependency 不得任意刪除

不得為了避免 Effect 重跑：

- 刪除實際使用的 Dependency。
- 使用空 Dependency 隱藏外部值。
- 使用大量 Disable Comment 關閉 Hook 檢查。

> [!NOTE]
> 應處理真正的 Reference 穩定性、資料生命週期或流程責任，不以關閉檢查取代修正。

### 3.4 衍生資料不重複存 State

可由 Props／State 直接計算的資料，不另建 State 與 Effect：

```ts
const totalPages = Math.ceil(totalCount / pageSize);
```

不建議：

```ts
const [totalPages, setTotalPages] = useState(0);

useEffect(() =>
{
    setTotalPages(Math.ceil(totalCount / pageSize));
}, [totalCount, pageSize]);
```

### 3.5 不濫用 useMemo／useCallback

只有符合以下情況時使用：

- 傳給 Memoized Component。
- 作為其他 Hook 的必要 Dependency。
- 計算成本明顯。
- Reference 穩定確實影響行為。

> [!WARNING]
> 不得為了形式或假想效能，將所有 Function 與簡單資料都包成 `useMemo`／`useCallback`。

### 3.6 複合狀態使用明確 State Model

當畫面同時存在：

```text
data
isLoading
isSaving
error
mode
isDirty
selectedRow
```

且狀態具有互斥或明確轉換關係時，應評估：

- Discriminated Union
- `useReducer`
- Custom Hook
- 明確 State Model

> [!WARNING]
> 不得使用大量互不約束的 Boolean，拼出實際上具有狀態機的流程。

### 3.7 Controlled／Uncontrolled 一致

同一個 Input 在完整生命週期中必須維持一致的值型別。

文字欄位的空值正規化應在 Binding／Field 共用邊界完成：

```ts
const value = sourceValue ?? "";
```

> [!WARNING]
> 不使用 `value || ""` 處理所有型別，避免將合法的 `0` 或 `false` 誤判成空值。

### 3.8 List Identity 必須穩定

可排序、新增、刪除、拖曳或編輯的清單，不得使用 Array Index 作為 `key`。

```tsx
items.map(item => <SurveyRow key={item.InternalId} item={item} />);
```

> [!NOTE]
> 尚未取得後端 ID 的新增資料，應建立穩定的前端暫存 ID。

## 4. API、非同步與執行環境

### 4.1 HTTP 與 Biz 結果

前端統一判斷：

```text
非 2xx
→ HTTP／授權／系統錯誤

2xx + IsSuccess=false
→ Biz 業務提示

2xx + IsSuccess=true
→ 正常處理 Data
```

> [!NOTE]
> API 回應判斷應集中於共用 API／Adapter 層，不得在每個 Component 或 Feature 中重複建立不同解析方式。

### 4.2 Promise 必須被明確處理

合法方式：

```ts
await saveAsync();
return saveAsync();
void saveAsync();
```

> [!NOTE]
> 使用 `void` 表示刻意不等待；該非同步流程必須自行處理錯誤。
>
> 不得直接呼叫 Promise 而沒有 `await`、`return` 或明確 `void`。

### 4.3 Action 防止重複提交

Save、Submit、Delete、Upload 等操作執行中，必須透過共用 Action Hook 或明確狀態：

- 阻止第二次執行。
- Disable 操作按鈕。
- 顯示 Loading。
- 在 `finally` 正確復原狀態。

### 4.4 Query 必須處理競態

查詢條件、語系、分頁或 Route 快速變更時，舊 Request 不得覆蓋較新的結果。

共用 Query 流程應使用：

- `AbortController`
- Axios Signal
- Request ID
- Latest Request Check

> [!WARNING]
> 不得以「最後回來的 Response」直接更新 State，而不確認它是否仍屬於最新查詢。

### 4.5 Effect Cleanup

Effect 建立下列資源時，必須在 Cleanup 釋放：

- Event Listener
- Timer
- Observer
- Swiper／Bootstrap／PDF Viewer Instance
- iframe Message
- WebSocket
- 第三方物件

```ts
useEffect(() =>
{
    const handleResize = (): void =>
    {
        updateViewport();
    };

    window.addEventListener("resize", handleResize);
    return () => window.removeEventListener("resize", handleResize);
}, []);
```

### 4.6 模組載入階段禁止直接使用 Browser API

不得在模組頂層直接使用：

```text
window
document
navigator
location
localStorage
sessionStorage
```

禁止：

```ts
const viewportWidth = window.innerWidth;
```

應放在 Client Effect、事件時機或共用環境 Adapter 中。

### 4.7 SSR 與 CSR 初始 DOM 必須一致

不得讓 Server Render 與 Client 第一次 Render 產生不同結構：

```tsx
// 不建議
return typeof window === "undefined"
    ? <div>Loading</div>
    : <ActualPage />;
```

> [!WARNING]
> 不得以「Dev CSR 可以執行」判斷 SSR 安全。
>
> 涉及 Route、Loader、Component、Browser API 或第三方套件的修改，必須通過完整 CSR／SSR Build。

### 4.8 SSR Initial Data 不重複 Fetch

SSR Loader 已取得的資料，Hydration 時應直接作為 Initial Data 使用，不應在 Client Mount 後無條件重新查詢。

> [!NOTE]
> Initial Data、Loading、Error 與 Refetch 的詳細責任，待 API Adapter／Loader 架構 Review 後另行補充。

## 5. 畫面互動、錯誤回饋與 AA

### 5.1 錯誤不得被吞掉

禁止：

```ts
try
{
    await saveAsync();
}
catch
{
}
```

禁止只留下：

```ts
catch (error)
{
    console.log(error);
}
```

錯誤必須明確選擇：

```text
轉成 ApiAdapterError
→ 交給共用訊息流程

加入 Field Error
→ 顯示於對應表單欄位

重新 Throw
→ 交由上層 Error Boundary／共用處理

確認可忽略
→ 必須有明確條件與原因註解
```

### 5.2 WCMS 正式 Code 不使用 console

WCMS 自行開發的正式程式不得使用：

```text
console.log
console.debug
console.info
console.warn
console.error
```

> [!WARNING]
> 臨時除錯用 `console.*` 必須在 Commit／PR 前移除，不得將 Console 當成正式錯誤處理、操作提示或紀錄機制。

### 5.3 使用者可理解的錯誤回饋

- 後台一般操作與系統錯誤：使用共用 Toast／Message Center。
- 表單欄位錯誤：優先顯示於對應 Field，並具備可報讀關聯。
- 需要使用者選擇的情境：使用共用 Dialog。
- 前台全域錯誤：使用共用前台訊息元件或可報讀的狀態區，不以 Console 取代畫面回饋。
- SSR 階段不直接觸發 Toast；錯誤應進入 Loader／Response／Initial State 流程。

> [!NOTE]
> 前台全域 Message 的完整元件與規則尚未收斂，本版先確立「錯誤必須可被使用者理解，且不得只存在 Console」的底線。

### 5.4 CMS HTML

- 不直接輸出未經處理的 `dangerouslySetInnerHTML`。
- CMS HTML 使用共用 Sanitizer。
- SSR 與 CSR 的 Sanitization 規則必須一致。
- 使用者輸入內容不得繞過 URL、HTML 與檔案安全檢查。

### 5.5 Link 使用共用入口

一般內外站連結使用：

```tsx
<LangLink />
<LangNavLink />
```

由共用元件處理：

- 語系路徑。
- 內站／外站。
- `_self`／`_blank`。
- 安全 URL Scheme。
- `rel="noopener noreferrer"`。
- 另開視窗 AA 提示。

> [!WARNING]
> 一般 Feature 不自行重新實作內外站、語系與另開視窗判斷。

### 5.6 互動元件技術底線

- 優先使用原生 `button`、`a`、`input` 等語意元素。
- 不使用只有 `onClick` 的 `div`／`span` 模擬按鈕。
- Icon Button 必須有可存取名稱。
- 滑鼠可操作的功能，也必須能用鍵盤完成。
- 動態錯誤與操作結果必須具備可報讀方式。
- Focus 順序與 Focus 可見性不得被破壞。
- ARIA 狀態必須與實際 UI 狀態同步。

## 6. Code Review 與 Release 品質門檻

### 6.1 不得降低全域檢查標準

不得為了讓單一功能通過而：

- 關閉 `strict`。
- 關閉未使用變數／參數檢查。
- 新增大範圍 `exclude`。
- 降低 SSR Build 檢查。
- 大量加入 Ignore Comment。
- 修改共用設定隱藏單一檔案問題。

> [!NOTE]
> 既有 Legacy 設定與第三方相容例外，列入 Code Review 待整改項目，不代表新 Code 可繼續沿用低標準。

### 6.2 Ignore 與第三方例外

不得使用無原因的：

```ts
// @ts-ignore
```

必要例外優先使用：

```ts
// @ts-expect-error 第三方型別缺少 xxx，待套件升級後移除。
```

並限制於最小範圍。

> [!WARNING]
> 不得為了處理第三方型別問題，將 `any`、Ignore 或寬鬆型別擴散到 Feature 業務層。

### 6.3 PR 前最低檢查

一般前端 PR 原則上執行：

```bash
npm run typecheck
npm run lint
npm run check
npm run build
```

其中完整 `build` 必須同時確認 CSR 與 SSR。

> [!NOTE]
> 若目前既有 Legacy Code 造成全專案檢查尚未完全通過，PR 至少不得新增新的 Error／Warning，並應記錄既有問題與本次修改範圍。
>
> 最終強制 Gate 與 CI 規則，待前端 Code Review 完成後正式收斂。

### 6.4 Release Console 目標

正式 Release 的 F12 Console 應達成：

- 無 WCMS 自行留下的 Debug Log。
- 無未處理 Promise Rejection。
- 無 React Warning。
- 無 Hydration Warning。
- 無重複 Key Warning。
- 無 Controlled／Uncontrolled Warning。
- 無可由 WCMS 修正的第三方初始化錯誤。

第三方套件或外掛若仍產生訊息，處理順序：

1. 確認是否為真正錯誤。
2. 優先升級、修正設定或調整初始化方式。
3. 透過 Adapter／Wrapper 隔離。
4. 無法排除時，記錄套件、版本、訊息、影響與暫緩理由。

> [!WARNING]
> 不得全域覆寫或關閉 `console` 來隱藏真正錯誤。

### 6.5 Code Review Checklist

#### 程式單元

- [ ] Region 與檔案結構符合 `.ts`／`.tsx` 規則。
- [ ] 一般單元使用 Named Export。
- [ ] 新增方法使用 `const`／Hook／Interface／Type。
- [ ] JSX 區塊使用 React Component，而不是 Render Node Helper。
- [ ] Component 沒有直接處理 Axios、Toast 底層解析或複雜 Payload。
- [ ] `key` 放在 `map` 直接回傳層。

#### 型別與契約

- [ ] 後端已有型別時，使用 OpenAPI Schema 產生型別。
- [ ] 沒有無理由的 `T | null | undefined`。
- [ ] UI State 未污染或放寬後端 DTO。
- [ ] `ApiResponse<T>` 的 `T` 是單一元素型別。
- [ ] 沒有無理由的 `any`、`as` 或非空斷言。
- [ ] 外部 Runtime 資料已驗證。
- [ ] `Partial<T>` 未用於模糊業務契約。
- [ ] Enum／Union 已完整處理。
- [ ] 日期與時區使用明確語意及共用 Library。

#### React 生命週期

- [ ] Props、State、API Data 沒有直接 Mutate。
- [ ] Hook 沒有放在條件或迴圈。
- [ ] Dependency 沒有任意刪除或 Disable。
- [ ] 沒有不必要的衍生 State。
- [ ] 沒有濫用 `useMemo`／`useCallback`。
- [ ] 複合狀態未使用大量互不約束的 Boolean。
- [ ] Input 沒有 Controlled／Uncontrolled 切換。
- [ ] 可編輯清單沒有使用 Index Key。

#### API、非同步與 SSR

- [ ] Promise 已明確 `await`、`return` 或 `void`。
- [ ] Action 已防止重複提交。
- [ ] Query 已處理競態或取消。
- [ ] Effect 建立的資源已 Cleanup。
- [ ] 模組頂層未直接使用 Browser API。
- [ ] SSR／CSR 初始 DOM 一致。
- [ ] SSR Initial Data 沒有被無條件重複 Fetch。

#### 錯誤、AA 與品質

- [ ] 錯誤沒有被吞掉。
- [ ] 正式 Code 沒有 `console.*`。
- [ ] 後台錯誤使用 Toast／Message Center；欄位錯誤顯示於 Field。
- [ ] 前台錯誤有可理解且可報讀的 UI 回饋。
- [ ] CMS HTML 經過共用 Sanitizer。
- [ ] Link 使用 `LangLink`／`LangNavLink`。
- [ ] 互動元件可使用鍵盤。
- [ ] 沒有降低 TypeScript、Lint 或 Build 檢查。
- [ ] 已執行必要的 Typecheck、Lint、Check 與 CSR／SSR Build。
