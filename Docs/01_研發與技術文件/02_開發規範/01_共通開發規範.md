# WCMS 共通開發規範

> [!NOTE]
> 本文件適用於 WCMS 前端與後端的程式新增、修改與重構工作。
>
> 規範目的為統一開發者與 AI 的實作判斷，避免重複建置既有能力、過度拆分 Function，以及僅為排版而改變原有程式行為。

## 1. 開發前確認與共用優先

### 1.1 搜尋既有實作

#### 規範

> [!NOTE]
> 新增或修改功能前，必須先搜尋專案內是否已有相同或相近的實作。
>
> 搜尋範圍應包含：
>
> - 共用 Library、Helper 與 Utility。
> - 前端 Hook、Component 與 Template。
> - 後端 Service、Repository 與既有底層能力。
> - Feature 與目前 Spec 中相近的實作方式。
>
> 不得在尚未確認既有能力前，直接建立新的 Function、Helper 或平行流程。

### 1.2 共用 Library 優先

#### 規範

> [!NOTE]
> 技術性且可共用的基礎處理，應優先使用既有 Library，不應在各功能內重複建立小型 Function。
>
> 常見技術性處理包含：
>
> - `trim` 與空值正規化。
> - 字串、陣列與型別轉換。
> - 日期與固定格式處理。
> - 共用驗證與條件組裝。
> - 共用 URL、檔案或資料轉換。

#### 不建議範例

> [!WARNING]
> 以下 Function 只包裝空值轉換與 `trim`，沒有額外流程或業務語意。

```ts
/** 正規化 SpecCode。 */
const normalizeSpecCode = (value: string | undefined): string =>
{
    return String(value ?? "").trim();
};

const specCode = normalizeSpecCode(inputSpecCode);
```

#### 建議範例

> [!TIP]
> 目前前端共用文字 Library 已提供 `safeTrim`，應直接調用既有能力。

```ts
import { safeTrim } from "@/SysCore/Utils/Library/LibData/LibText";

const specCode = safeTrim(inputSpecCode);
```

### 1.3 Library 不足時的處理方式

#### 規範

> [!NOTE]
> 發現既有 Library 無法完整處理需求時，不得直接建立另一套獨立流程。
>
> 應立即提出分析與見解，先判斷是否應優化或擴充既有 Library。
>
> 只有符合以下任一情況時，才建立獨立流程：
>
> - 新需求與既有 Library 的責任或處理方式有明確差異。
> - 新需求具有特定業務語意，不屬於通用技術能力。
> - 將新需求加入 Library 會造成參數、分支或行為過度彈性。
> - 擴充後會使 Library 責任模糊、難以理解或提高誤用風險。

#### 判斷順序

> [!TIP]
> 1. 確認既有 Library 是否已提供相同或相近能力。
> 2. 判斷差異是否仍屬於共用技術需求。
> 3. 屬於共用技術需求時，提出 Library 優化方案。
> 4. 只有責任明顯不同或會使 Library 過度複雜時，才建立獨立流程。

### 1.4 避免重複與平行實作

#### 規範

> [!NOTE]
> 同一種技術能力不得分散於多個 Feature、Spec 或單一功能內各自實作。
>
> 已有共用能力時，應優先調用或提出共用層優化，不得僅因目前修改範圍較小而複製一份局部版本。
>
> 業務流程確實不同時，可以保留於對應 Feature 或 Spec，但必須清楚區分其業務責任，不得偽裝成共用技術 Helper。

### 1.5 寫死值與既有契約確認

#### 規範

> [!NOTE]
> 應盡可能避免重複寫死字串、欄位名稱、參數名稱、狀態值與固定數值。
>
> 使用優先順序如下：
>
> 1. 既有共用常數或設定值。
> 2. Enum 或明確型別。
> 3. `nameof` 或其他可由程式取得的名稱。
> 4. 集中宣告且具有清楚名稱的常數。
>
> 新增常數前，仍必須先確認專案內是否已有相同定義。

## 2. Function 與程式結構

### 2.1 Function／Method 長度與主流程

#### 規範

> [!NOTE]
> Function／Method 原則上控制在約 15～30 行。
>
> 內容較多時，應先判斷是否存在可獨立表達的工作階段、業務流程或內部實作，再決定是否拆分。
>
> 主流程應盡可能維持以下結構：
>
> 1. 宣告必要變數。
> 2. 執行主要流程。
> 3. 回傳結果。
>
> 無回傳值時，不需要為形式額外加入 `return`。

### 2.2 Function／Method 拆分時機

#### 規範

> [!NOTE]
> 符合以下情況時，可以拆出子 Function／Method：
>
> - 該段程式具備明確流程語意或業務語意。
> - 能明顯降低主流程複雜度。
> - 需要封裝條件分支、例外處理、副作用或資料組裝。
> - 會被多個位置重複使用。
> - 能讓 Public、Protected、Private 的責任與時機更加清楚。
>
> 偏向技術性的處理，不應優先拆成局部 Function；必須先搜尋既有 Library，並依「1.3 Library 不足時的處理方式」判斷是否應優化共用能力。

#### 建議範例

> [!TIP]
> 以下拆分具備清楚的工作階段。

```ts
/** 儲存目前表單資料。 */
const saveForm = async () =>
{
    const payload = buildSavePayload(formData);
    await validateBeforeSave(payload);
    await submitSaveRequest(payload);
};
```

> [!NOTE]
> `buildSavePayload`、`validateBeforeSave` 與 `submitSaveRequest` 各自代表清楚的工作階段，不是單純包裝一行技術操作。

### 2.3 避免過度封裝

#### 規範

> [!NOTE]
> 不得只為以下內容建立額外的 Private／Protected Function：
>
> - 單純一行 Library 呼叫。
> - 單純轉接參數。
> - 宣告變數接收回傳值後立即 Return。
> - 單純執行 `trim`、空值轉換或基本型別轉換。
> - Function 名稱沒有增加流程或業務語意。

#### 不建議範例

```ts
/** 取得清理後的標題。 */
const getTrimmedTitle = (title?: string): string =>
{
    return safeTrim(title);
};
```

#### 建議範例

```ts
const title = safeTrim(formData.title);
```

### 2.4 Public／Protected／Private 使用原則

#### 規範

> [!NOTE]
> 存取範圍應盡可能縮小，不確定是否需要對外使用時，不得預先開放為 Public。
>
> - **Public**：明確提供外部單元或主要入口調用的能力。
> - **Protected／Protected Virtual**：屬於某一個工作區塊、流程階段或執行時機，供繼承、覆寫或相關子類別延伸使用。
> - **Private**：單一事件、局部處理或目前單元內部的實作細節。
>
> Protected 不應只因「未來可能會用到」而建立；必須能說明它所代表的工作區塊、流程時機或擴充目的。

#### 範例

```csharp
/// <summary>
/// 儲存完成後執行 Feature 可覆寫的後續時機。
/// </summary>
protected virtual async Task AfterSaveChanges(CancellationToken ct)
{
    await Task.CompletedTask;
}

/// <summary>
/// 建立目前儲存事件使用的內部識別碼。
/// </summary>
private string CreateInternalId()
{
    return Guid.NewGuid().ToString();
}
```

### 2.5 註解與 Summary

#### 規範

> [!NOTE]
> 程式註解只寫在個別 Function／Method 或 Property 的宣告上方。
>
> - TypeScript／React 使用簡短 JSDoc。
> - C# 使用簡短 XML Summary。
> - 特殊處理、業務原因、時機與上下游關係，也應寫在對應 Function／Method 或 Property 上方。
> - Function 內的參數與區域變數不另外撰寫說明註解，應以清楚命名表達用途。
> - 不在 Function 內加入「宣告變數」「呼叫方法」「回傳結果」等表面行為註解。

#### 不建議範例

```ts
const saveData = async (data: SaveModel) =>
{
    // 宣告 payload
    const payload = buildPayload(data);
    // 呼叫 API
    await api.save(payload);
    // return
    return payload;
};
```

#### 建議範例

```ts
/** 建立儲存資料並送出 API Request。 */
const saveData = async (data: SaveModel) =>
{
    const payload = buildPayload(data);
    await api.save(payload);
    return payload;
};
```

### 2.6 無效程式與舊程式清理

#### 規範

> [!NOTE]
> 修改程式結構後，不保留 Obsolete Code，也不得以整段註解方式保存舊實作。
>
> 應同步移除：
>
> - 未使用的 Function／Method。
> - 未使用的變數與 Property。
> - 未使用的 Import／Using。
> - 暫存測試碼與不再執行的分支。
>
> 舊版內容由 Git 歷史保存，不應留在目前程式碼內增加維護負擔。

### 2.7 Region 與檔案區塊

#### 規範

> [!NOTE]
> - `import`／`using` 不建立 Region。
> - 沒有內容的 Region 不建立。
> - Region 依責任、工作區塊與執行時機分類。
> - 不得為符合形式而建立空 Region。
> - 前端與後端的實際 Region 順序，依各自開發規範處理。

### 2.8 緊密排版與空行

#### 規範

> [!NOTE]
> 程式應維持相對緊密，不加入沒有區隔意義的空行。
>
> - Region 與 Region 之間可以保留空行。
> - 短參數、方法呼叫、型別與簡單物件盡量維持同一行。
> - 不因參數稍多就預設逐項換行。
> - 不因自動格式化工具習慣產生過度垂直的程式碼。

### 2.9 拆行與控制敘述

#### 規範

> [!NOTE]
> 只有在單行明顯過長、內容複雜或巢狀程度過高時才拆行，拆行優先控制在兩至三行。
>
> 單一且簡短的控制敘述可以省略大括號並維持單行；符合以下情況時應保留完整區塊：
>
> - 包含多個動作。
> - 宣告區域變數。
> - 存在巢狀條件。
> - 包含例外處理。
> - 該流程容易在後續增加步驟。

### 2.10 排版與重構安全

#### 規範

> [!NOTE]
> 排版整理與程式重構不得改變：
>
> - 條件判斷。
> - 參數與傳遞內容。
> - Function／Method 呼叫順序。
> - 回傳值。
> - 非同步行為。
> - 事件綁定與執行時機。
> - 業務流程與既有結果。
>
> 前端 React Hook、SSR／CSR 與後端 Transaction 等特殊限制，依各端開發規範補充。

## 3. 開發完成與交付

> [!NOTE]
> 完成一個可獨立交付或驗證的修改單元時，開發者或 AI 必須提供變更說明。
>
> 變更說明不得虛構搜尋結果、Build、測試、AA、Freego、弱點掃描、部署或實機驗證結果。
>
> 實際交付欄位、交付粒度、Commit Summary、Description、影響範圍與驗證格式，依 [`04_Git與Commit規範.md`](./04_Git與Commit規範.md) 執行。
