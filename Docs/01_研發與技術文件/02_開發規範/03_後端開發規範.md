## 1. C# 檔案與 Region 結構

### 1.1 using 與 namespace

> [!NOTE]
> `using` 不建立 Region，`namespace` 放在所有 `using` 之後。
>
> 沒有內容的 Region 不建立，不為了形式補上空區塊。

```csharp
using WCMS.SysCore.FeatureDriver.Biz;
using WCMS.SysCore.Security.IdentityAccess.Authorization;
namespace WCMS.Features.WEB.Survey;
```

### 1.2 Region 排列順序

一般 C# 類別依實際內容使用下列順序：

```text
Property
Construct
Public
Internal
Protected Virtual
Protected
Explicit Interface
Private
```

> [!TIP]
> `Construct` 僅在類別有 Constructor 時建立。
>
> `Internal` 僅用於 Assembly 內部公開的底層能力。
>
> `Explicit Interface` 僅在實際使用 Explicit Interface Implementation 時建立。

### 1.3 Region 使用判斷

| Region | 使用範圍 |
|---|---|
| `Property` | Field、Property、類別狀態及唯讀依賴 |
| `Construct` | Constructor |
| `Public` | 對外入口 |
| `Internal` | Assembly 內部共用入口 |
| `Protected Virtual` | 明確提供繼承類別覆寫的流程時機 |
| `Protected` | 某個工作區塊、流程階段或繼承類別可使用的能力 |
| `Explicit Interface` | 明確介面實作 |
| `Private` | 單一事件、資料組裝、條件判斷及目前類別內部實作 |

> [!WARNING]
> 不得因「未來可能會用到」就任意將方法改成 `Public` 或 `Protected Virtual`。
>
> 需要新增擴充點時，必須先判斷是否應優化既有底層框架。

### 1.4 特殊語意 Region

Model 關聯、底層特定技術區塊等，可在確實有助於閱讀時建立特殊語意 Region，例如：

```csharp
#region 主子表關聯
// Navigation Properties
#endregion
```

> [!WARNING]
> 特殊語意 Region 不得取代主要存取範圍分類，也不得把互不相關的方法全部塞入同一區塊。

## 2. 功能類型與底層框架選擇

### 2.1 建立功能前的分類流程

新增後端功能前，依序完成：

```text
確認需求
    ↓
判斷功能類型
    ↓
選擇對應 Model／Biz／API 底層
    ↓
選擇 Attribute 與 Metadata 契約
    ↓
使用底層提供的標準入口
    ↓
透過既有 Hook 加入功能差異
```

> [!WARNING]
> 不得看到「需要資料庫」就直接建立一套 Controller、Biz、Repository。
>
> 必須先判斷該功能屬於哪一種後端功能類型。

### 2.2 功能類型總表

| 功能類型 | 目前狀態 | Model 方向 | Biz 方向 | API 方向 |
|---|---|---|---|---|
| 基本表單資料 | 已有 | Form Aggregate Root／Detail | `BizService<TFormModel>` | `ApiDataController<TFormModel>` |
| 報表資料 | 尚無 | Report DTO／Result | Report Query Service | Report API |
| 操作功能（Func） | 已有零散實作，待收斂 | Func Request／Result | Func Biz／Transaction | Func API |
| SaaS 前台對外服務 | 尚無 | Public Contract DTO | SaaS Service | Versioned Public API |

> [!NOTE]
> 尚未建立的底層名稱只是設計方向，不是目前可直接引用的 Class。
>
> 在正式底層建立前，不得由單一 Feature 自行建立一套暫時框架。

### 2.3 基本表單資料

基本表單資料適用於：

- 一般主表。
- Root 加 Detail／SubDetail。
- 後台清單與表單。
- 標準新增、修改、刪除、作廢及查詢。
- 需要保留主明細同步、差異更新、生命週期欄位及框架 Hook 的功能。

標準底層：

```text
Model
→ Root 使用符合需求的既有 Model 基底
→ Detail／SubDetail 使用 FormDetailModel 或對應底層基底

Biz
→ BizService<TFormModel>

API
→ ApiDataController<TFormModel>
→ 僅查詢時評估 ApiDataQueryController<TFormModel>
```

#### 2.3.1 WEB 專用表單資料

WEB 專用表單資料是基本表單資料的延伸，主要承接「前台網站網頁功能使用」的資料模組，包括：

- 前台頁面與內容模組。
- 網站、單元與選單歸屬。
- 語系與前台顯示資料。
- 發布、下架及顯示期間。
- SEO 與前台路由。
- 前台讀取與後台維護差異。
- 未來主站、子站及多站台共同契約。
- WEB 專用 Metadata 或 Attribute。

> [!NOTE]
> WEB 專用表單仍建立在基本表單框架之上，只追加前台網站領域的共同需求，不重新建立 CRUD、Transaction 或 Repository 主線。
>
> 未來主站與子站能力應透過共用站台契約延伸，不在個別 Feature 中各自建立一套網站資料流程。

### 2.4 報表資料

報表資料以查詢、統計、彙總、分組及匯出為主，可能跨多個 Entity，回傳 Report DTO，而不是 Form Aggregate。

> [!WARNING]
> 報表功能不得為了方便，假裝成標準表單並直接繼承 `BizService<TFormModel>`。
>
> 報表底層尚未建立時，應先提出共用框架設計。

### 2.5 操作功能（Func）

操作功能是 WCMS 的 Func 層，代表一個獨立業務動作。目前修改密碼、重置密碼、同步或匯入等功能已具備雛形，但尚未完成統一分類與底層收斂。

常見情境：

- 修改或重置密碼。
- 發布或下架。
- 批次轉換。
- 匯入或匯出。
- 寄送通知。
- 外部同步。
- 重建資料。
- 其他不等同標準 CRUD 的命令流程。

> [!TIP]
> 若需求只是標準表單 CRUD 前後的補值、驗證或儲存後處理，應優先使用既有 Hook。
>
> 只有本身是一個獨立業務動作時，才歸類為 Func。

#### 2.5.1 操作日誌

操作日誌記錄「誰在何時執行哪個 API／Func、來源資訊、執行結果與耗時」。

規劃原則：

```text
Request 進入 Middleware
    ↓
建立操作開始資訊
    ↓
執行後續 API／Biz
    ↓
取得成功、業務失敗、系統失敗或取消結果
    ↓
完成操作日誌
```

> [!NOTE]
> 操作日誌應由 Middleware 或共用 HTTP 管線統一收口，在 API 執行前建立開始資訊，並在執行後補上成功、失敗或取消結果。
>
> 個別 Controller 不應重複建立不同格式的操作日誌流程。

#### 2.5.2 變更日誌

變更日誌記錄「資料異動前後的欄位差異、變更原因與變更來由」，屬於 Biz 與資料 Transaction 的責任。

規劃流程：

```text
Biz 取得修改前資料
    ↓
建立修改後資料
    ↓
計算欄位差異
    ↓
寫入資料
    ↓
寫入變更日誌與變更來由
    ↓
同一個 Transaction Commit
```

> [!NOTE]
> 變更日誌必須與資料異動位於同一個 Transaction；資料或日誌任一失敗時，整體應 Rollback。
>
> 標準 CRUD 應由共用 Transaction 自動取得前後差異；特殊 Func 在動態修改資料時，必須傳入修改值、變更原因或變更來由，不得直接繞過共用變更流程。

> [!WARNING]
> 操作日誌與變更日誌責任不同，不得互相取代。
>
> 沒有 Entity 差異的 Func 仍可能需要操作日誌；有資料異動的 Func 則必須確認已進入共用變更日誌流程。

### 2.6 SaaS 前台對外服務

SaaS 對外服務預計處理：

- Tenant 資料隔離。
- 對外驗證與授權。
- API Version。
- Rate Limit。
- 對外 DTO 與內部 Model 隔離。
- 契約穩定性。
- 對外錯誤格式。
- 使用量與 Auditing。
- 公開資料 Cache 策略。

> [!WARNING]
> SaaS 對外服務不得直接暴露內部 Form Model，也不得直接將後台 `ApiDataController<TFormModel>` 當成公開 API。

## 3. 新功能的標準建立方式

### 3.1 Model 基底選擇

> [!NOTE]
> Model 基底必須依資料角色選擇，不得只因名稱相似直接複製。

| 資料角色 | 使用原則 |
|---|---|
| 標準表單聚合根 | 使用最接近需求的既有 Root Model 基底，例如 `HeaderModel` |
| Detail／SubDetail | 使用 `FormDetailModel` 或對應明細基底 |
| 一般特殊資料模型 | 先確認是否已有適合的 SysCore／Feature 基底 |
| 對外或報表資料 | 使用獨立 DTO／Contract，不直接暴露 Entity |

### 3.2 Model Attribute 來源分組

Model Property 同時需要框架 Attribute 與 WCMS 自定義 Attribute 時，依來源分組排列：

1. 第一組：.NET、ASP.NET Core、EF Core 或其他框架提供的 Attribute。
2. 第二組：WCMS 自定義的 `Lib...Attribute`。
3. 每個 Attribute 原則上各占一行。
4. 相同來源保持連續排列，兩組之間不加空行。

#### 主鍵範例

```csharp
/// <summary>
/// 問卷代碼。
/// </summary>
[Key]
[LibStr(ApiFieldMode.ReadOnly, DbStrLen.ID, DisplayName.SurveyId)]
public string SurveyId { get; set; } = string.Empty;
```

#### 關聯範例

```csharp
/// <summary>
/// 所屬問卷。
/// </summary>
[ForeignKey(nameof(SurveyId))]
[LibField(ApiFieldMode.Ignore)]
public Survey Survey { get; set; } = null!;
```

#### 多個框架 Attribute 範例

```csharp
[Key]
[DatabaseGenerated(DatabaseGeneratedOption.None)]
[LibStr(ApiFieldMode.ReadOnly, DbStrLen.ID, DisplayName.SurveyId)]
public string SurveyId { get; set; } = string.Empty;
```

#### 僅使用 WCMS Attribute

```csharp
/// <summary>
/// 問卷名稱。
/// </summary>
[LibStr(ApiFieldMode.ReadWrite, DbStrLen.Name, DisplayName.SurveyName)]
public string SurveyName { get; set; } = string.Empty;
```

> [!TIP]
> 框架 Attribute 負責 ORM、Key、資料關聯或框架驗證。
>
> `Lib...Attribute` 負責 WCMS API 欄位模式、Metadata、顯示名稱、字串長度及系統欄位政策。

### 3.3 Biz 基底與 Attribute

標準表單 Biz 應繼承 `BizService<TFormModel>`，並使用 `LibBiz` 描述功能 Metadata。

```csharp
using WCMS.Features._Resx;
using WCMS.SysCore.FeatureDriver.Biz;
using WCMS.SysCore.Security.IdentityAccess.Authorization;
namespace WCMS.Features.WEB.Survey;

[LibBiz(ProgKeys.WEB.Code, ProgKeys.WEB.Survey)]
public class SurveyBiz(BizDeps bizDeps) : BizService<Survey>(bizDeps)
{
}
```

> [!NOTE]
> 標準 Biz 只保留該功能真正需要的驗證、補值及 Hook Override，不重新建立 CRUD 主流程。

### 3.4 API 基底與 Attribute

需要標準 CRUD 時：

```csharp
using WCMS.Features._Resx;
using WCMS.SysCore.FeatureDriver.Api.Controllers;
using WCMS.SysCore.FeatureDriver.Api.Metadata;
using WCMS.SysCore.Security.IdentityAccess.Authorization;
namespace WCMS.Features.WEB.Survey;

[LibApiController(ProgKeys.WEB.Code, ProgKeys.WEB.Survey, FuncAction.MasterData)]
public class SurveyController : ApiDataController<Survey> { }
```

僅需要標準查詢能力時，優先評估：

```csharp
public class SurveyQueryController : ApiDataQueryController<Survey>
{
}
```

> [!WARNING]
> 不得因為只需要普通 CRUD，就自行重寫整套 Controller、Repository 或 Transaction。

### 3.5 標準表單功能最小組成

```text
Feature/
└─ WEB/
   └─ Survey/
      ├─ Survey_Model.cs
      ├─ Survey_Biz.cs
      └─ Survey_Api.cs
```

> [!TIP]
> DTO、額外操作、特殊查詢或其他檔案，只有實際需要時才建立。

## 4. CRUD 標準入口

### 4.1 CRUD 方法對照

一般 Feature、Spec 及 API 應使用下列 `BizService<TFormModel>` 對外入口：

| 功能 | 標準方法 |
|---|---|
| 初始化匯入 | `BizInitCreateDatasAsync` |
| 新增 | `BizCreateDataAsync` |
| 修改 | `BizUpdateDataAsync` |
| 刪除 | `BizDeleteDataAsync` |
| 作廢／恢復 | `BizInvalidDataAsync` |
| 查詢單筆 | `BizQueryDataAsync` |
| 查詢清單 | `BizQueryListAsync` |
| 查詢筆數 | `BizQueryTotalCounts` |

### 4.2 標準入口附帶的底層行為

使用標準 CRUD 入口，可保留目前 WCMS 底層提供的共同處理，包括：

- 統一 Transaction。
- Root、Detail、SubDetail 寫入與同步。
- Key 與生命週期欄位處理。
- 實際 Scalar 差異套用。
- Feature／Spec Hook。
- 系統訊息。
- 共用操作日誌 Middleware 串接。
- API 寫入後的 Output Cache 清除。
- 資料異動與變更日誌位於同一個 Transaction。
- 既有 Auditing 與變更紀錄流程。

> [!NOTE]
> 實際底層行為會持續優化；開發者應使用標準入口，而不是依賴或複製某一個內部實作 Class。

### 4.3 一般功能不得直接使用的底層能力

```text
DoCreateAsync
DoUpdateAsync
DoDeleteAsync
ExecTransactionAsync
GraphRepo
FormWriteOperations
RepositoryWriteOperations
ApplicationDbContext
DbSet
```

> [!WARNING]
> 一般 CRUD 直接呼叫底層方法、Repository、`DbContext` 或 `DbSet`，可能繞過交易、生命週期欄位、主明細同步、差異更新、Hook、訊息與 Auditing。

### 4.4 特殊交易流程

只有標準 CRUD 確實無法涵蓋的特殊流程，才能評估使用 `ExecTransactionAsync` 或更底層能力。

判斷流程：

1. 先確認是否已有標準 CRUD 或 Hook。
2. 提出是否應優化共用 Biz／Library。
3. 評估是否會讓既有框架過度靈活或責任混亂。
4. 確認確實屬於不同流程後，才建立特殊交易實作。
5. 必須補上完整註解、錯誤處理及對標範例。

## 5. 客製邏輯與擴充時機

### 5.1 Biz Hook 對照

| Hook | 使用時機 |
|---|---|
| `BeforeUpdate` | 寫入前驗證、補值與正規化 |
| `AfterUpdate` | Repository 寫入後、Commit 前 |
| `AfterSaveChanges` | SaveChanges 與 Commit 後 |
| `CheckIsUsedAsync` | 刪除前確認資料是否已被使用 |
| `AfterInvalid` | 作廢或恢復後處理 |
| `DataScopeCondition` | 功能固定套用的 Root 資料範圍 |

### 5.2 API Hook 對照

| Hook | 使用時機 |
|---|---|
| `SpecBeforeWrite` | API 輸入資料在寫入前的補值或轉換 |
| `SpecAfterRead` | API 回傳前的補值或轉換 |

### 5.3 寫入前驗證範例

```csharp
#region Protected Virtual

/// <summary>
/// 儲存前整理問卷選項並檢查必要欄位。
/// </summary>
protected override async Task BeforeUpdate(Survey data, FuncAction action, CancellationToken ct = default)
{
    await base.BeforeUpdate(data, action, ct);
    if (!action.In(FuncAction.Create, FuncAction.Update)) return;

    AutoSetData(data);
    CheckData(data);
}

#endregion
```

> [!WARNING]
> 不得在不清楚執行時機的情況下，把所有客製處理塞進 Controller 或直接覆寫完整 CRUD。
>
> 應先判斷該處理屬於寫入前、Commit 前、Commit 後、刪除檢查，或 API 輸入輸出轉換。

### 5.4 Protected Virtual 使用原則

- 只有明確需要子類別覆寫的流程時機才使用。
- 新增覆寫點前先確認既有 Hook 是否足夠。
- 不因「未來可能客製」就新增空 Hook。
- 現有 Hook 不足時，先提出是否優化共用底層。
- 若新增 Hook 會讓底層過度靈活或語意混亂，應建立責任明確的獨立流程。

## 6. API 統一回應契約

### 6.1 JSON API 使用 ApiResponse

除 Binary、Stream、Redirect 及基礎設施端點外，標準 Feature／Func JSON API 原則上使用：

```csharp
ApiResponse<T>
```

正式回應欄位：

```text
IsSuccess
Data
SysMessage
```

> [!NOTE]
> Auth、Filter、Middleware 等全域入口的完整套用方式另案設計；在正式收斂前，不新增新的裸字串或匿名錯誤格式。

### 6.2 Data 一律為陣列

後端契約：

```csharp
public class ApiResponse<T> : ApiResponse
{
    public IList<T> Data { get; set; } = [];
}
```

統一規則：

- 單筆成功：`Data = [item]`
- 多筆成功：`Data = items`
- 無資料：`Data = []`
- 業務檢查失敗：`Data = []`
- 不使用 `null` 作為標準回應

> [!NOTE]
> `ApiResponse<T>` 的 `T` 代表陣列元素型別。
>
> 清單回應仍使用 `ApiResponse<Survey>`，不是 `ApiResponse<Survey[]>`，避免形成二層陣列語意。

### 6.3 IsSuccess 與 SysMessage

`IsSuccess` 表示 WCMS 業務流程結果，依 `SysMessage` 中是否存在 `MessageStatus.Error` 判定。

因此：

> [!WARNING]
> 業務檢查失敗時，`SysMessage` 必須至少包含一筆 `MessageStatus.Error`。
>
> 不得只中止 Biz 流程卻不加入錯誤訊息，否則前端可能將結果判斷為成功。

### 6.4 HTTP Status 與 Biz 結果的界線

HTTP Status 表示 Request、授權、路由及系統執行結果；`IsSuccess` 表示 Biz 正常執行後的業務判斷結果。

#### Biz 預期內的檢查失敗

例如：

- 必填資料或商業規則不符合。
- 密碼規則不符合。
- 舊密碼錯誤。
- 資料已被使用，不能刪除。
- 資料目前狀態不允許操作。
- 儲存前檢查未通過。

統一回應：

```text
HTTP 200
IsSuccess = false
Data = []
SysMessage = 業務提示
```

> [!NOTE]
> Request 已成功進入系統，Biz 也正常完成檢查，只是業務結果不允許繼續時，可以使用 `HTTP 200 + IsSuccess=false`。

#### 非 Biz 預期結果

| 情況 | HTTP Status |
|---|---:|
| Request、JSON、Model Binding 或參數格式錯誤 | `400` |
| 未登入或憑證失效 | `401` |
| 已登入但沒有功能權限 | `403` |
| Route 或指定資源不存在 | `404` |
| 唯一鍵、版本或併發衝突 | `409` |
| Rate Limit | `429` |
| 未預期 Exception | `500` |

> [!WARNING]
> 未預期 Exception、授權失敗、Request 無法解析等非業務檢查問題，不得以 `HTTP 200 + IsSuccess=false` 隱藏。

### 6.5 非 200 由全域管線處理

除 `Ok(...)` 與 Biz 正常檢查結果外，非 200 回應原則上由全域錯誤處理管線統一收口。

目前規劃以 Middleware 作為主要入口；Authentication、Authorization、ModelState、Route 與其他 ASP.NET Core 管線的詳細整合方式另案設計。

> [!WARNING]
> 個別 Controller 不應各自散落 `BadRequest("...")`、`Unauthorized("...")`、匿名物件或不同格式的錯誤回應。

### 6.6 成功回應範例

```csharp
ApiResponse<Survey> response = OkResponse(result);
return Ok(response);
```

### 6.7 Biz 檢查失敗範例

```csharp
Message.AddMessage(MessageStatus.Error, SysMessageCode.BECode00035, nameof(internalId));

ApiResponse<Survey> response = new()
{
    Data = [],
    SysMessage = Message.Messages
};

return Ok(response);
```

前端統一判斷：

```text
非 2xx
→ HTTP／授權／系統錯誤處理

2xx + IsSuccess=false
→ 顯示 Biz 業務提示

2xx + IsSuccess=true
→ 正常處理 Data
```

### 6.8 ApiBaseController 共用入口

目前 `ApiBaseController` 已提供 `OkResponse<T>`。

成功回應與 Biz 檢查結果的組裝應集中於 `ApiBaseController` 或對應共用 Helper，不由各 Controller 重複建立不同格式。

> [!NOTE]
> 非 200 的共用回應入口待全域錯誤處理管線完成後再正式定義，不在本版先寫死 Helper 名稱。

### 6.9 非 JSON 回應例外

下列端點不強制包成 `ApiResponse`：

- 檔案下載。
- 圖片、PDF、影音及其他 Binary／Stream。
- Redirect。
- XSRF Token 等只負責設定 Cookie 或 Header 的基礎設施端點。
- 其他經確認不屬於 JSON API 契約的端點。

## 7. 非同步與服務註冊

### 7.1 非同步方法命名

新增的一般非同步方法原則上使用 `Async` 結尾。

例外：

- Override。
- 既有 Interface。
- 生命週期 Hook。
- 第三方或框架契約。
- 相容性需求。

例如下列 Hook 維持既有名稱：

```text
BeforeUpdate
AfterUpdate
AfterSaveChanges
```

### 7.2 CancellationToken

- 上層已有 `CancellationToken` 時，必須繼續向下傳遞。
- 不得無故改成 `CancellationToken.None`。
- 不得在中途遺漏。
- 不使用 `.Result` 或 `.Wait()` 同步阻塞。
- 不在未確認相依性的情況下任意改為 `Task.WhenAll` 平行執行。

### 7.3 標準 Biz 自動註冊

標準 `BizService<TFormModel>` 實作由 FeatureDriver 掃描註冊，不需要個別加入：

```csharp
services.AddScoped<SurveyBiz>();
```

> [!WARNING]
> 不得對可由 FeatureDriver 掃描的標準 Biz 重複手動註冊。

### 7.4 特殊服務與 ModuleSetup

下列服務應放入責任相符的 `ModuleSetup`：

- 非標準 Biz 或 Service。
- Cache、Provider、Store。
- Startup Task。
- 特殊 Interface 實作。
- 無法由既有掃描機制註冊的服務。

> [!WARNING]
> 不得將同類型服務註冊散落在 `Program.cs`、個別 Biz 或不相關模組。

## 8. Metadata、常數與框架契約

### 8.1 使用既有 Attribute 與 Metadata

建立 Model、Biz、API 或資料關聯時，先確認既有：

```text
LibApiController
LibBiz
LibField
LibStr
ApiFieldMode
DbStrLen
DisplayName
Key
ForeignKey
InverseProperty
```

> [!WARNING]
> 不得在個別 Feature 中重複定義相同的欄位契約、顯示名稱、關聯字串或路由規則。

### 8.2 nameof、Enum 與既有常數

優先使用：

- `nameof(...)`
- 既有 Enum
- `SysParam`
- `ProgKeys`
- `DbStrLen`
- `DisplayName`
- `SysMessageCode`
- 其他既有 Constants

```csharp
[ForeignKey(nameof(SurveyId))]
```

> [!NOTE]
> 當常數值只是用來對應既有型別、Property、Field 或成員名稱時，應優先使用 `nameof(...)`，避免重新手寫相同字串。
>
> 若該常數需要提供其他單元使用，應明確宣告為共用常數，例如：

```csharp
/// <summary>
/// 問卷代碼欄位名稱。
/// </summary>
public const string SurveyId = nameof(SurveyId);
```

> [!TIP]
> 只有常數值本身確實包含空白、符號、固定格式、外部契約文字，或無法由 `nameof(...)` 表達時，才直接使用字串內容。

```csharp
/// <summary>
/// 報表顯示名稱。
/// </summary>
public const string ReportDisplayName = "問卷統計報表";
```

> [!WARNING]
> 不得以 `"SurveyId"`、`"/Service"`、`"application/json"` 等裸字串取代已有的常數或 `nameof`。
>
> 也不得在可以寫成 `nameof(...)` 時，另外宣告一份內容相同的手寫字串常數，以免成員改名後產生無法追蹤的不一致。

### 8.3 新增框架能力前的判斷

當既有 Attribute、Metadata、Biz 或 API 能力不足時：

1. 立即提出目前不足點。
2. 評估是否應優化既有底層。
3. 確認優化是否會讓既有框架過度靈活或責任混亂。
4. 只有確實屬於不同功能類型或不同契約時，才建立新的獨立框架。

## 9. 標準表單功能對標範例

### 9.1 Model

```csharp
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;
using WCMS.SysCore.FeatureDriver.Model.Base;
using WCMS.SysCore.FeatureDriver.Model.Metadata;
namespace WCMS.Features.WEB.Survey;

/// <summary>
/// 問卷。
/// </summary>
public class Survey : HeaderModel
{
    /// <summary>
    /// 問卷代碼。
    /// </summary>
    [Key]
    [LibStr(ApiFieldMode.ReadOnly, DbStrLen.ID, DisplayName.SurveyId)]
    public string SurveyId { get; set; } = string.Empty;

    /// <summary>
    /// 問卷名稱。
    /// </summary>
    [LibStr(ApiFieldMode.ReadWrite, DbStrLen.Name, DisplayName.SurveyName)]
    public string SurveyName { get; set; } = string.Empty;

    #region 主子表關聯
    [InverseProperty(nameof(SurveyItem.Survey))]
    [LibField(ApiFieldMode.ReadWrite)]
    public List<SurveyItem> Items { get; set; } = [];
    #endregion
}

/// <summary>
/// 問卷欄位。
/// </summary>
public class SurveyItem : FormDetailModel
{
    /// <summary>
    /// 問卷代碼。
    /// </summary>
    [Key]
    [LibStr(ApiFieldMode.ReadOnly, DbStrLen.ID, DisplayName.SurveyId)]
    public string SurveyId { get; set; } = string.Empty;

    #region 主子表關聯
    [ForeignKey(nameof(SurveyId))]
    [LibField(ApiFieldMode.Ignore)]
    public Survey Survey { get; set; } = null!;
    #endregion
}
```

### 9.2 Biz

```csharp
using WCMS.Features._Resx;
using WCMS.SysCore.FeatureDriver.Biz;
using WCMS.SysCore.Security.IdentityAccess.Authorization;
namespace WCMS.Features.WEB.Survey;

[LibBiz(ProgKeys.WEB.Code, ProgKeys.WEB.Survey)]
public class SurveyBiz(BizDeps bizDeps) : BizService<Survey>(bizDeps)
{
    #region Protected Virtual

    /// <summary>
    /// 儲存前檢查問卷名稱。
    /// </summary>
    protected override async Task BeforeUpdate(Survey data, FuncAction action, CancellationToken ct = default)
    {
        await base.BeforeUpdate(data, action, ct);
        if (!action.In(FuncAction.Create, FuncAction.Update)) return;
        if (data.SurveyName.IsNullOrEmpty())
            Message.AddMessage(MessageStatus.Error, SysMessageCode.BECode00012, nameof(data.SurveyName));
    }

    #endregion
}
```
