## 4. HTTP Middleware Pipeline

目前 Pipeline 順序：

```text
ErrorHandlingMiddleware
→ Forwarded Headers
→ Cookie Policy
→ Security Headers
→ XSRF Protection
→ Request Localization
→ Swagger Access
→ HSTS
→ HTTPS Redirect
→ CORS
→ Response Compression
→ Authentication
→ Authorization
→ Output Cache
→ MapControllers
```

順序目的：

- 最外層先接住未處理例外。
- 先解析可信 Proxy 資訊。
- 在 API 前完成 Cookie、Security、XSRF 與語系。
- Authentication 先於 Authorization。
- Output Cache 在 Controller 前套用。
- 最後 MapControllers。

安全上需注意：

- `Forwarded Headers` 的可信來源與 Host Policy 屬安全邊界，不只是部署方便設定。
- CORS 只控制 Browser Origin 行為，不取代 Authentication／Authorization。
- XSRF 保護 Browser Credential Request；Bearer Token／Cookie Authentication 的責任需分開理解。
- Security Header 在 Backend 產生後，仍可能經 Node Proxy／IIS 調整；弱掃應以 Browser 最終 Response 為準。

> [!WARNING]
> `HardeningSetup` 雖提供 Rate Limiting 註冊方法，但目前 Program 未見 `AddRateLimiting`／`UseRateLimiter`，不能宣稱已正式啟用。

## 5. FeatureDriver 核心架構

FeatureDriver 是目前後端資料型功能的主框架。

```text
Feature API
→ ApiDataController<TFormModel>
→ BizService<TFormModel>
→ Form Query / Write Operations
→ FormGraphRepoScope
→ BasicRepository<TDbModel>
→ Repository Query / Write Operations
→ ApplicationDbContext
```

核心目的：

- 以 Form Aggregate 取代舊式分散 DTO Mapping。
- 統一 Root／Detail／SubDetail 查詢與 CUD。
- 集中 Transaction、Key、Lifecycle 與 Metadata。
- 保留 Feature Biz 的 Hook 與特殊業務空間。
- 讓標準 Feature API 大幅減少重複 CRUD。

安全上，FeatureDriver 同時是欄位政策、Dynamic Query、Model Binding、Repository Parameterization 與 Error Flow 的共同入口，因此弱掃修正應優先收斂共用層，不在每個 Feature 重複補丁。

### 14.4 Auth Session Timeout 與 Refresh Rotation

後台使用者 Idle Policy 由前端 Browser Shared LastActivity 管理，正式環境為 30 分鐘、Development 為 2 分鐘。Backend Access Token 期限同步設定為正式 30 分鐘、Development 2 分鐘，避免前後端主要登入時間基準漂移。

Refresh Token 目前仍使用 7 天設定，責任是讓「仍在有效 Browser Idle Window 且正常持續操作」的 Session 可以進行 Rotation；它不是使用者可見的 Idle Deadline。Frontend 在 LastActivity 缺失或已超過 Idle 時不得先透過 `/Auth/Me → Refresh` 將 Session 救回。

Refresh 流程：

```text
Browser Activity / API 401
→ Frontend AuthRefreshCoordinator
→ /Auth/Refresh
→ TokenService.TryRotateRefreshAsync
→ TokenStateCache.TryRotateRefreshAsync
```

目前 Backend Atomicity 保證限定：

```text
Single Backend Process
+ Local Token State
+ Singleton TokenStateCache
+ process-local SemaphoreSlim Rotation Lock
```

Rotation Critical Section 會在 Lock 內重新確認 old RTID Owner，再建立 new RTID 並撤銷 old RTID；同一 old RTID 於目前部署範圍只能成功一次。修正後 Runtime 已驗證同一 old RTID 並行結果由 `200 + 200` 收斂為 `200 + 401`。

Frontend Web Locks／Single-flight 只降低正常 Browser 流程的重複 Refresh，不是 Backend Security Boundary。未來進入 LB／Multi-instance 時，`SemaphoreSlim` 無法跨 Process，必須把 `TryRotateRefreshAsync` 底層替換成 Redis／Shared Store 的 Atomic Operation；Refresh Token State 若宣告為 Required Dependency，不得在 Redis 不可用時各 Instance 靜默 fallback Local。

#23 的 RequireAuth HTTP／網路錯誤分類不屬於 Token Rotation，本項已拆至後續 #89。

## 15. XSRF、CORS 與 Security Hardening

Backend 安全架構以 `SysCore/Security/Hardening` 與 `SysCore/Security/IdentityAccess` 為主，並與最外層 `ErrorHandlingMiddleware`、IIS／Node Proxy 形成完整 HTTP 安全邊界。

### 15.1 安全單元與責任

| 單元 | 主要責任 |
|---|---|
| `HardeningSetup.cs` | Host／Kestrel／Forwarded Headers、CORS、Cookie、HSTS 與 Security Hardening 組合入口 |
| `SecurityHeadersSetup.cs` | Backend API Security Header Policy |
| `XsrfProtectionSetup.cs` | Antiforgery、Browser Unsafe Method XSRF 驗證與 Token Cookie 契約 |
| `IdentityAccessSetup.cs` | JWT Authentication、Current User、Permission 與 Token Security DI |
| `TokenService.cs` | Access／Refresh Token 建立、驗證、Rotation 流程 |
| `TokenStateCache.cs` | JTI／RTID State、Revocation 與目前單 Process Atomic Rotation |
| `ErrorHandlingMiddleware.cs` | 系統 Exception 的安全 HTTP Response 收口，不洩漏內部 Exception 細節 |
| Feature／Controller Permission Attribute | 每個功能 Endpoint 的 Server-side Authorization Boundary |

安全責任不應散落成各 Controller 自行設定 Header、Cookie 或 XSRF；Feature 只應宣告自身權限與必要業務規則。

### 15.2 Host、Proxy Trust 與 Browser-facing Response

部署鏈路：

```text
Browser
→ IIS / ARR
→ Node / Express SSR
→ /Service Proxy
→ ASP.NET Core Backend
```

Backend 應只信任明確允許的 Forwarded Header／Proxy 來源；Node SSR 同時負責 Browser-facing `Host`／`X-Forwarded-Host` Allowlist。

Header 類弱掃需注意：

- Backend Header 正確，不代表 Browser 最終 Header 一定正確。
- Node Proxy Hook 若未實際觸發，Backend 補的 COOP／CSP 等可能無法依預期出現在 Browser Response。
- IIS 也可能加入、移除或覆蓋 Header。

因此複驗應同時保留 Backend Direct Response 與 Browser-facing Final Response。

### 15.3 XSRF

後端目前契約：

- HttpOnly Antiforgery Cookie。
- 可供 Axios 讀取的 `XSRF-TOKEN`。
- 前端回送 `X-XSRF-TOKEN`。
- Browser Unsafe Method 進行 Antiforgery 驗證。
- 前端遇 Antiforgery 403 可重新取得 Token，再重試一次。
- Login／Refresh 改變登入狀態後重新取得 XSRF Token。

2026-08-24 已收斂 AppScan 對 Browser Unsafe Method 的 XSRF Finding，並修正 Development HTTP 情境取得 XSRF Token 曾出現的 500；這些屬 Code／Runtime mitigation，正式 AppScan 複掃仍需另外確認。

### 15.4 XSRF Session Cookie 與 Authentication Token 分工

`XSRF-TOKEN` 的目的為 Antiforgery，不是 Login Credential。它應跟目前 Browser Session／Identity 生命週期協調，不應因人工指定過長 `Expires`／`Max-Age` 而被弱掃視為永久敏感 Session 資料。

2026-08-24 後的方向：

```text
Login / Refresh
→ 不再以不必要的永久期限手動建立 XSRF-TOKEN
→ 前端重新取得新的 XSRF Token
```

但下列 Token 仍各有自己的必要安全生命週期：

- Access Token。
- Refresh Token／RTID。
- JTI／RTID Server-side State。

修正 XSRF Cookie 時不得誤刪或混淆 Authentication Token 的正式期限。

### 15.5 CORS

- 依前端 Host 白名單。
- Allow Credentials。
- 限制 Header。
- 限制 Method。

CORS 是 Browser Origin Policy，不是 Authorization。即使 Origin 被允許，Request 仍必須通過 Authentication、Permission 與 XSRF 等對應安全邊界。

### 15.6 Cookie

- SameSite Strict。
- Secure Always 為正式安全基準。
- Path Root。
- Token Cookie 安全設定。
- Development HTTP 等非 Production 測試情境須透過明確環境策略處理，不得為了解決本機相容性而放寬 Production Cookie Policy。

### 15.7 Security Header

Backend Security Header 目前重點包含：

- CSP／`frame-ancestors`。
- COOP。
- CORP／其他 Cross-Origin Header 與前端 Proxy 協作。
- HSTS／HTTPS。
- 移除或避免輸出不必要 Server Identifying Header。

2026-08-24 已針對 API `frame-ancestors` 收斂為 `none`，並補齊 Backend COOP；Scanner 是否清除仍以正式複掃為準。

### 15.8 Input Boundary 與弱掃 Robustness

弱掃常使用極端字串、超大數值、Dynamic Query Parser Payload 或不合法資料狀態。安全架構不應只問「漏洞名稱是否正確」，還要確認 Payload 是否能造成不合理的 Server 500。

處理原則：

```text
JSON / Request Format Error
→ 400

Authentication Failure
→ 401

Authorization / Permission Failure
→ 403

Known Data Conflict / Concurrency / Constraint
→ 409

Rate Limit
→ 429

Unknown Server Bug
→ 500
```

但 HTTP Status 不能只看 Framework Exception Type；必須在最接近錯誤來源處確認語意，再交由 Error Handling 收口。

### 15.9 SQL／Repository 安全

SQL Injection 類人工覆核至少確認：

- Dynamic Query 使用受控 Field／Operator 契約。
- EF／SQL Command 保持 Parameterization。
- Scanner Payload 只出現在 Parameter Value。
- Request 的 TRUE／FALSE Probe 不造成 SQL 條件語意差異。
- DB 前後狀態符合預期。

不得只以「使用 EF Core」作為 False Positive 的唯一證明。

### 15.10 安全驗證狀態

安全修正統一區分：

```text
原始 Finding
→ Code mitigation 已完成
→ Runtime 驗證完成
→ 正式 Scanner 複掃通過
```

Commit 存在只代表程式有修改；未執行正式複掃前不得描述為 All Clear。

弱掃修正歷史、Finding 實例與後續方針統一記錄於：

`Docs/03_品質與驗證文件/03_弱掃報告/修改歷史與方針.md`

## 16. Auditing 與 Error Handling

> [!IMPORTANT]
> 本章同時記錄目前 ErrorHandling 架構與已確認的收斂方向。
> `IWCMSException` 只處理「異常流程」，不取代既有 Biz 正常檢查；Biz 預期內失敗維持 `HTTP 200 + IsSuccess=false + SysMessage`。

### 16.1 四條主要結果流程

WCMS 標準 JSON API 依語意分成四類：

```text
A. 成功
→ Controller / API
→ OkResponse<T>
→ ApiResponse<T>
→ 2xx + IsSuccess=true

B. Biz 預期內失敗
→ Biz 正常執行檢查
→ Message / SysMessage
→ ApiResponse<T>
→ HTTP 200 + IsSuccess=false

C. 已知系統性異常
→ WCMSXXXException + IWCMSException
→ ErrorHandlingMiddleware
→ 對應 4xx / 5xx
→ Error ApiResponse + SysMessage

D. 未知系統性異常
→ 原始 Exception
→ ErrorHandlingMiddleware
→ 500
→ 安全 SysMessage + NLog
```

Biz Failure 與 System Exception 不得混為同一種控制流程。

### 16.2 Biz Failure 與 Exception 邊界

下列屬於 Biz 正常檢查結果：

- 必填資料或商業規則不符合。
- 密碼規則不符合。
- 舊密碼錯誤。
- 資料狀態不允許目前操作。
- 儲存前檢查未通過。
- 其他已進入 Biz、且 Biz 能正常判斷的業務結果。

標準流程：

```text
Request 已正常解析
→ Controller / Biz 正常執行
→ Biz 判斷不允許繼續
→ Message.Add...
→ HTTP 200
→ IsSuccess=false
→ SysMessage 說明原因
```

> [!WARNING]
> 不得為了 ErrorHandling 形式統一，將一般 Biz Validation 大量改成 `throw`。
> `Message.HasError`、Biz Validation 與 `HTTP 200 + IsSuccess=false` 仍是正式業務結果機制。

下列較屬於異常流程：

- JSON / Request 無法解析。
- Model Binding 的系統型輸入異常。
- Authentication / Authorization 管線異常或失敗。
- DB Constraint、Concurrency、Connection 等已知系統異常。
- File / Cache / External Service 等 Infrastructure 異常。
- Runtime 中可明確分類、但不屬於 Biz 正常結果的異常。

### 16.3 IWCMSException 契約

`IWCMSException` 用來標記：

> 「這是一個 WCMS 已能辨識其系統異常語意、並能安全對應 MessageCode 的 Exception。」

第一階段契約保持最小化：

```csharp
/// <summary>
/// 定義 WCMS 可辨識例外的系統訊息契約。
/// </summary>
public interface IWCMSException
{
    string MessageCode { get; }
    object[] MessageArgs { get; }
}
```

`IWCMSException` 不承擔：

```text
Biz Validation Result
Message.HasError 的替代品
一般表單驗證結果
StatusCode / HttpStatus
Response / IActionResult
前端最終 UserMessage
```

HTTP Status 由 `ErrorHandlingMiddleware` 決定；前端顯示文字則統一走：

```text
MessageCode + MessageArgs
→ IErrorHelper
→ Resx / I18n
→ SysMessage
```

原始 Framework / DB / Runtime Exception 應盡可能保存於 `InnerException`：

```text
WCMSXXXException
└─ InnerException
   └─ Framework / DB / Runtime Exception
```

### 16.4 WCMSXXXException 與 sealed 原則

具體 WCMS 系統異常使用明確語意命名，例如：

```text
WCMSJsonException
WCMSPermissionException
WCMSDataConflictException
WCMSInfrastructureException
```

除已實際需要的 Exception 外，不預先建立大量類別；名稱必須對應真實系統異常語意，而不是一般 Biz Rule。

具體 `WCMSXXXException` 預設一律 `sealed`：

```csharp
public sealed class WCMSJsonException : JsonException, IWCMSException
{
}
```

只有未來確定某 Exception 需要作為可繼承的基底類別時，才另案討論取消 `sealed`。

### 16.5 Framework Exception 與 WCMS Exception

判斷順序：

```text
發生 Framework / DB / Runtime Exception
        ↓
這是不是 Biz 正常檢查結果？
        ├─ 是 → 不使用 Exception，維持 Biz Message Flow
        └─ 否
            ↓
WCMS 是否已能明確辨識系統異常語意？
        ├─ 否 → 保留原始 Exception，交由 ErrorHandling 視為未知異常
        └─ 是 → 以 WCMSXXXException + IWCMSException 表達
                  並保留原始 InnerException
```

下列模糊 Framework Exception 不得直接做全域 HTTP Mapping：

```text
FormatException
ArgumentException
InvalidOperationException
KeyNotFoundException
```

例如不得直接建立：

```text
FormatException → 400
ArgumentException → 400
KeyNotFoundException → 404
```

因為它們可能來自 Request，也可能代表程式 Bug。只有在最接近錯誤來源的邊界能確認系統異常語意時，才轉成具體 `WCMSXXXException`。

ASP.NET Core / MVC 也可能對特定 Exception 有既定行為，例如 JSON Input Formatter、ModelState、Authentication Challenge、Authorization Forbid。因此 WCMS Exception 是否繼承 Framework Exception，必須以實際 Pipeline 行為驗證。

### 16.6 WCMSJsonException 第一階段驗證

目前弱點掃描的超大數值 Case：

```json
{
  "PageNumber": 99999999999999999999,
  "PageSize": 10
}
```

此 Case 在 JSON → `Int32` 階段即失敗，尚未正常進入 Biz，因此屬於系統性的 Request Parsing Error。

第一階段驗證方向：

```csharp
/// <summary>
/// 表示 WCMS API JSON 輸入無法依預期格式解析。
/// </summary>
public sealed class WCMSJsonException : JsonException, IWCMSException
{
    public string MessageCode { get; }
    public object[] MessageArgs { get; }
}
```

預期流程：

```text
FormatException / OverflowException / JsonException
→ WCMSJsonException
→ ErrorHandlingMiddleware
→ 400 Bad Request
→ MessageCode / MessageArgs
→ IErrorHelper
→ ApiResponse.SysMessage
```

驗證必須確認：

```text
WCMSJsonException
→ ErrorHandlingMiddleware catch
→ HTTP 400
→ ApiResponse
→ SysMessage
→ 不回傳原始 Exception.Message
```

若實測變成：

```text
WCMSJsonException : JsonException
→ MVC Input Formatter / ModelState
→ InvalidModelStateResponseFactory
```

則改為：

```csharp
public sealed class WCMSJsonException : Exception, IWCMSException
{
}
```

> [!IMPORTANT]
> 是否採第二方案以實測結果決定；未驗證前不得宣稱第一方案已能由 Middleware 接住。

### 16.7 ErrorHandlingMiddleware 責任

目前最外層 `ErrorHandlingMiddleware` 接住未處理例外；目標上它是標準 HTTP JSON API「異常流程」的主要收口點，不處理 Biz 正常失敗。

目標流程：

```text
Exception
    ↓
辨識 WCMSXXXException / IWCMSException / Unknown Exception
    ↓
決定 HTTP Status
    ↓
取得 MessageCode / MessageArgs
    ↓
IErrorHelper
    ↓
ApiResponse.SysMessage
    ↓
回傳 JSON Response
```

Middleware 責任：

- 系統 Exception 分類。
- HTTP Status Mapping。
- `IWCMSException` 的 `MessageCode / MessageArgs` 轉成 `SysMessage`。
- 未知 Exception 加入安全的系統錯誤訊息。
- 依 Logging Policy 記錄 NLog。
- 保留 TraceId 與 Request 診斷資訊。

Middleware 不負責：

- Biz Validation。
- `Message.HasError` 的正常業務結果。
- 業務資料加工。
- DB Transaction Rollback。
- Startup / Setup 初始化失敗。
- 直接把 `Exception.Message` 當作前端訊息。

### 16.8 HTTP Status、SysMessage 與 NLog

Biz 正常失敗：

```text
HTTP 200
IsSuccess=false
SysMessage=業務提示
```

系統性異常第一階段目標分類：

| 系統異常語意 | 建議 HTTP Status |
|---|---:|
| Request / JSON / Model Binding / 格式錯誤 | `400` |
| Authentication 失敗 | `401` |
| Authorization / Permission 失敗 | `403` |
| 指定 Resource / Route 不存在 | `404` |
| DB Constraint、版本或併發衝突 | `409` |
| Rate Limit | `429` |
| 未知系統 Exception | `500` |

`502 Bad Gateway` / `504 Gateway Timeout` 只應用於 WCMS 確實扮演 Upstream Proxy / Gateway 的情境。

前端訊息：

```text
IWCMSException.MessageCode
IWCMSException.MessageArgs
→ ErrorHelper
→ 多語系 Resx
→ ApiResponse.SysMessage
```

禁止直接輸出：

```text
Exception.Message
InnerException.Message
StackTrace
SQL Statement
Database / Server 詳細資訊
檔案路徑
Runtime 內部資訊
```

NLog / 維運則保存：

```text
Exception Type
Exception.Message
InnerException
StackTrace
TraceId
User / IP / Lang
HTTP Method / Path
必要 Runtime 診斷資訊
```

Logging Policy 與前端 `MessageCode` 必須分離；Biz `IsSuccess=false` 也不自動等於 Error Log。

### 16.9 DB / EF Core Exception 收斂

DB Case 必須先分辨是 Biz Rule 還是系統性異常：

```text
Biz 已能在正常流程提前判斷
→ Biz Message Flow
→ HTTP 200 + IsSuccess=false

DB / EF 執行時產生的已知系統異常
→ 具體 WCMSXXXException + IWCMSException
→ ErrorHandling
→ 對應 4xx / 5xx

Infrastructure / Schema / 未知 SQL Error
→ 保留原始 Exception
→ ErrorHandling
→ 500 或後續定義的 Infrastructure Status
→ 安全 SysMessage + NLog
```

常見待盤點 Case：

- Foreign Key Constraint。
- Unique / Duplicate Key。
- EF Concurrency Conflict。
- DB Timeout。
- DB Connection Failure。
- Deadlock / Retry Exhausted。
- SQL / Schema 未知異常。

> [!WARNING]
> 不得將所有 `SqlException`、`DbUpdateException` 或 `DbUpdateConcurrencyException` 一律轉為同一 HTTP Status。

### 16.10 Transaction / OperateLog 的 catch 原則

不是所有 `try / catch` 都應移除。

可保留：

```text
Transaction catch
→ Rollback
→ throw
→ ErrorHandlingMiddleware

OperateLog catch
→ 標記 Fail / Cancel
→ throw
→ ErrorHandlingMiddleware
```

這些 catch 是 Cleanup / Rollback / Auditing，不是自行建立 Error Response。

應逐步收斂的模式：

```csharp
catch (Exception ex)
{
    return BadRequest(ex.Message);
}
```

以及系統性異常時散落的：

```text
BadRequest(...)
Unauthorized(...)
Forbid(...)
NotFound(...)
Conflict(...)
StatusCode(...)
JsonResult + StatusCode
```

正常 Biz `Message + HTTP 200 + IsSuccess=false` 不在移除範圍。

### 16.11 Startup / Setup 排除 ErrorHandlingMiddleware

下列流程不進 `ErrorHandlingMiddleware`：

```text
XXXSetup.AddServices
Host Build
ApplicationStartupInitializer
IApplicationStartupTask
Program Startup
```

標準流程：

```text
Startup / Setup Exception
→ Program / Host 捕捉
→ Fatal Log
→ Fail Fast / 啟動失敗
```

Startup 階段沒有可回覆的 HTTP Request，因此不得建立假的 `ApiResponse`。

### 16.12 ASP.NET Core 特殊管線

部分 Framework 流程可能在 Middleware catch 之前或之外自行完成 Response：

- JSON Input Formatter。
- ModelState / `InvalidModelStateResponseFactory`。
- Authentication Challenge。
- Authorization Forbid。
- Route / 404 / 405。
- Request Size / Server Limit。
- Rate Limiter。

後續原則：

> 先確認 Framework 實際執行點，再決定以 WCMS Exception、Framework Handler / Adapter 或共用 Error Response Writer 接入 ErrorHandling 體系；不得把正常 Framework / Biz 流程全部 Exception 化。

### 16.13 Operate Log

目前包含：

- `IOperateLog`
- `OperateLogService`
- `OperateLog`
- `OperateLogModel`
- `ExcStatus`
- Skip Attribute
- Middleware 結構

目前 `ApiDataController` 仍直接建立操作紀錄，因此稽核流程同時存在共用服務與 Controller 整合。

### 16.14 NLog

NLog 套件仍保留，適合：

- 實體 Runtime Log。
- 未處理例外。
- 系統診斷。
- 部署環境記錄。

NLog 不取代業務 `SysMessage` 與資料庫操作稽核。

### 16.15 後續 Error Flow 盤點分類

正式盤點 `try / catch / throw / BadRequest / Unauthorized / SqlException / JsonException` 等 Case 時，每一個點分成：

```text
A. Biz 正常檢查
   → 維持 Message Flow / HTTP 200 + IsSuccess=false

B. Cleanup / Rollback / Auditing catch
   → 保留並 rethrow

C. 已知系統性異常
   → sealed WCMSXXXException + IWCMSException

D. Framework 特殊管線
   → Handler / Adapter / Error Response 對接策略

E. 未知系統 Exception
   → 不強制包裝
   → ErrorHandling 500 + NLog

F. Startup / Setup
   → 排除 HTTP ErrorHandling
```

目前第一階段優先順序：

```text
1. IWCMSException
2. sealed WCMSJsonException
3. LibJsonNullDefaultConverter JSON Convert Error 收斂
4. ErrorHandlingMiddleware Mapping WCMSJsonException → 400 + SysMessage
5. 驗證 JsonException Framework 繼承是否會被 MVC 攔截
6. 重測 PageNumber / PageSize 超大數值 Case
7. 再盤點其他系統性 Exception
8. Biz Validation Flow 維持既有機制，不納入 Exception 化
```

> [!IMPORTANT]
> Build、QA、弱點掃描或實機驗證只有實際執行並取得結果後才能記錄為通過。
