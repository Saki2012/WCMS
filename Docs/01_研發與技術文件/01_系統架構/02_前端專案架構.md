## 4. 前端啟動與 SSR 架構

### 4.1 SSR Server

`src/SSR/SSR-Server.ts` 是 Node／Express 對外入口，負責：

- 讀取環境設定。
- 建立 HTTPS／Proxy 執行環境。
- 開發時接 Vite Middleware。
- 正式環境提供 `dist/CSR` 靜態檔。
- 載入 `dist/SSR/entry-server.js`。
- Proxy `/Service` 至後端 API。
- 建立 CSP Nonce。
- 套用 `SysCore/Security/Hardening` 提供的安全 Policy。
- 設定 HTML、靜態資源與 API Proxy 的 Browser-facing 安全標頭。
- 驗證 `Host`／`X-Forwarded-Host`。
- 移除 `Server` 與 `X-Powered-By`。
- 注入 SSR Initial State。
- 避免 HTML／API 被不當快取。

安全 Policy 的規則應集中於 `SysCore/Security/Hardening`，`SSR-Server.ts` 主要負責組合與實際套用，不應重新散落另一套 CSP／COEP／CORP／Host 規則。

> [!WARNING]
> 2026-08-11 已確認前端環境參數存在「程式已讀取，但 `.env.development`／`.env.production` 與型別宣告未同步」的治理缺口；目前部分參數依賴程式內預設值。此項已列入第 17 節 P1 待處理項目，弱掃／CSP 等安全參數在收斂前不得只依賴隱含預設值判定正式環境設定。

### 4.2 Server Entry

`Entry-Server.tsx` 負責：

```text
Request URL
→ 依前台／後台載入 Assets
→ AppRouteModule
→ createServerRouter
→ 執行 React Router Loaders
→ renderToString
→ Helmet Head Tags
→ Initial State
```

Provider 順序目前包含：

```tsx
<MessageProvider>
    <HelmetProvider>
        <HeaderMetaComp />
        <StaticRouterProvider />
    </HelmetProvider>
</MessageProvider>
```

### 4.3 Client Entry

`Entry-Client.tsx` 負責：

```text
初始化 Trusted Types／XSRF
→ 依 Route 載入 Assets
→ 讀取 SSR Initial State
→ 建立 Client Router
→ 判斷可否 Hydrate
→ hydrateRoot 或 createRoot
```

Hydration 判斷目前依賴：

- Root 是否存在實際 SSR DOM。
- Initial State 是否存在。
- `hydrationData` 是否為有效 Record。

> [!WARNING]
> 目前 Entry Client 仍有 `console.error` 用於 Initial State Parse、Hydration Recoverable Error 與 CSR Fallback。依新的 Release 規範，這些必須改由正式診斷／錯誤回饋機制處理，不能直接視為最終完成狀態。

## 6. API 與資料存取架構

### 6.1 APIBase

`APIBase.ts` 建立 CSR／SSR 共用 Axios：

```text
CSR
├─ baseURL: VITE_API_BASE_URL 或 /Service
├─ withCredentials
├─ Accept-Language Interceptor
├─ XSRF Cookie / Header
└─ 403 後補票並重試一次

SSR
├─ baseURL: SSR_API_ORIGIN + /Service
├─ Forward Cookie
├─ Forward Accept-Language
└─ Request-scoped WeakMap Cache
```

安全責任上：

- CSR 對 Browser Unsafe Method 需配合 Backend Antiforgery 契約回送 XSRF Header。
- Login／Refresh 改變登入身分後，必須重新取得符合目前身分生命週期的 XSRF Token。
- SSR 只能 Forward 當次 Request 所需 Cookie，不得把使用者 Token 寫入跨 Request 的全域 Cache。
- 403 重取 XSRF 只處理 Antiforgery 補票情境，不得用來繞過真正的 Authorization 403。

### 6.2 APIClient

`APIClient.ts` 目前負責：

- `ApiBaseService`。
- HTTP Error 轉換。
- `ApiDataService<T>` CRUD。
- QueryData／QueryList／Count。
- ModelDisplay。
- System API。
- File Preview／Download URL。

目前標準呼叫概念：

```text

→ ApiBaseService.CallApi
```

### 6.3 Feature API Adapter

Feature 通常建立：

```ts

class AnnouncementService extends ApiDataService<AnnouncementFormModel>
{
    constructor(apiInstance?: AxiosInstance)
```

- 未來 REST／GraphQL 轉換時降低 Component 變動。

### 11.6 Security Hardening

前端安全責任以 `SysCore/Security` 作為 Browser Security 的正式入口。現階段實體檔案主要集中在 `Hardening`，但架構責任已明確分成「Policy 定義」、「SSR／Proxy Boundary 套用」、「Browser Runtime Enforcement」與「前後端 Security Contract」四個面向，不應全部堆在 `SSR-Server.ts`，也不應由個別 Feature／Spec 自行發明全域安全規則。

安全設計共通原則：

```text
Security Requirement
→ Default Policy
→ 必要時建立 Named Exception
→ Boundary Enforcement
→ Browser Final Runtime / Response 驗證
```

`Default Policy` 是一般流程的保守安全基準；只有已確認的相容性或跨站需求才能建立 `Named Exception`。例外不得直接散落於 Feature／Spec，也不得因單一功能失效就放寬全站 Policy。

#### 11.6.1 安全模組

| 單元 | 主要責任 |
|---|---|
| `SecurityHeaders.ts` | 組合前端與 Proxy Response 共用的 Security Header 基準 |
| `CSPSetting.ts` | CSP Directive、Nonce、Production 靜態 Script 與 `frame-ancestors` Policy |
| `COEPSetting.ts` | `Cross-Origin-Embedder-Policy` Policy |
| `CORPSetting.ts` | `Cross-Origin-Resource-Policy` Policy 與必要 Resource Exception |
| `HostValidation.ts` | SSR `Host`／`X-Forwarded-Host` 白名單驗證 |
| `TrustedTypesPolicy.ts` | Browser Trusted Types Policy 建立與安全 HTML Sink 契約 |
| `SSR-Server.ts` | 將以上 Policy 實際套用至 HTML、Static Asset 與 `/Service` Proxy Response |
| `Entry-Client.tsx` | Browser 啟動時初始化 Trusted Types 與 XSRF Runtime |

Feature／Spec 不應各自建立另一套全域 CSP、COEP、CORP、Host、Trusted Types 或 Browser Cookie Security 規則；若確有客製需求，必須透過共用 Policy Extension 或明確的安全例外點處理。

#### 11.6.2 Browser-facing 安全邊界

正式站流量需以完整鏈路理解：

```text
Browser
→ IIS / ARR
→ Node / Express SSR
→ /Service Proxy
→ ASP.NET Core Backend
```

因此 Header／Cookie 類弱掃不得只查看任一層 Source Code。Browser 最終收到的 Response 與 `Set-Cookie` 才是檢測基準。

責任原則：

- IIS／ARR：TLS、反向代理與最外層 Hosting 設定。
- Node SSR：HTML／Static／Proxy Browser-facing Header 與 Host 驗證。
- Backend：API 原始 Security Header、CORS、XSRF、Authentication／Authorization，以及 Cookie Security Policy Authority。
- Proxy：若 Backend Header 需要由 Browser 看到，必須確認 `http-proxy-middleware` 實際 Hook 能正確保留或重寫；Cookie 的 `SameSite` 等安全屬性原則上由 Backend 決定，Node 不維護第二套 Cookie Policy。

同一 Header 在多層都有設定時，必須以「最終 Response 是否一致」為準，避免重複、覆蓋或值互相衝突。Cookie 則必須避免 Feature Source、Backend Global Policy 與 Browser Runtime 出現不同安全語意。

#### 11.6.3 CSP 與 Trusted Types

目前安全方向：

- SSR HTML 使用 Request-scoped Nonce。
- Production 靜態 JS／MJS 需有對應 CSP 基準，避免只保護 HTML。
- API／不應被嵌入的內容以 `frame-ancestors 'none'` 為收斂方向。
- Production 啟用 `require-trusted-types-for 'script'`。
- 需要寫入 HTML Sink 的共用能力應經 Trusted Types Policy／Sanitization，而非在 Feature 任意繞過。

Trusted Types Enforcement 屬全站 Browser Runtime 契約，因此 TinyMCE、PDF Worker、Turnstile、Google Translate、Legacy Script 與 Spec Assets 都需要做 Runtime Regression；「CSP Header 已存在」不等同功能已驗證完成。

#### 11.6.4 COEP／COOP／CORP 與資源例外

Cross-Origin Isolation 類 Header 必須同時考慮安全性與前端資源相容性：

```text
COEP
→ 控制跨來源嵌入資源

COOP
→ 控制 Browsing Context Group

CORP
→ 控制 Resource 是否允許跨來源讀取
```

CORP 採 **Default `same-origin` + Named Exception**。Node 自己提供的 HTML 與 Static Asset（JS／CSS／Image／Font／PDF／其他 Static Resource）一律套用 `Cross-Origin-Resource-Policy: same-origin`，不得只因 `.pdf` 副檔名或 Resource Type 建立 blanket exception。

`/Service` 由 Backend Security Policy 決定 Resource 是否具備 CORP 例外資格。一般 API、Download、Preview 與 PDF Response 預設仍使用 `same-origin`；目前只有下列 Browser Native PDF Preview Context 是具名例外：

```text
/Service/FileManagement/Public_Preview
+ Content-Type: application/pdf
+ wcmsPreview=native
→ Backend 最終 Response 明確移除 CORP
→ Node /Service Proxy 沿用 Backend 決策，不自行擴大例外
```

`wcmsPreview=native` 只描述 Rendering Context，不具 Authentication／Authorization 語意。若未來新增其他 CORP 例外，必須同樣記錄 Resource／Domain、相容性原因、最小適用範圍與 Runtime Regression，不得以「PDF」或其他副檔名作為通用豁免條件。

Header 調整後需以 Browser-facing Final Response 驗證；Native PDF 流程另需回歸 Viewer 開啟、翻頁、縮放、搜尋、下載與列印。Google Translate、Turnstile、YouTube、CMS iframe 等第三方能力也需在 Header 調整後回歸。

#### 11.6.5 Host Validation

Node SSR 是 Browser-facing Host 邊界之一，必須驗證：

- `Host`。
- 可信 Proxy 傳入的 `X-Forwarded-Host`。
- Production 實際允許 Domain。

未在 Allowlist 的 Host 應於 SSR 邊界被拒絕，不能直接拿來建構 Proxy Target、Absolute URL 或其他安全敏感行為。

`SSR_ALLOWED_HOSTS` 等環境參數必須在正式部署明確設定，不能只依賴開發預設值。

#### 11.6.6 XSRF、Cookie 與 Browser Storage

前端與 Backend 的 XSRF 安全契約：

```text
Login / Refresh 改變登入狀態
→ 重新取得 XSRF Token
→ Browser Unsafe Method 回送 X-XSRF-TOKEN
```

XSRF Token 的 Session 生命週期與 Access／Refresh Token 生命週期是不同責任，不應因修正 XSRF Cookie 而誤改 Authentication Token 的必要期限。

Browser Cookie 的 `SameSite` 採 **Strict-by-default + Named Exception** 架構。Frontend 負責理解 Browser 使用契約與最終 Runtime 行為；真正的 `Strict`／`Lax`／`None` Policy Authority 與 Enforcement 由 Backend `SysCore/Security/Hardening` 負責，前端 Feature／Spec 與 Node Proxy 不建立第二套 SameSite 決策。

目標流程：

```text
Feature / Platform Capability
→ 宣告 Cookie 的用途或跨站需求
→ Backend Cookie Security Policy
   ├─ 無跨站需求：Default Strict
   ├─ 已核准的 Top-level Navigation Continuity：Named Lax Exception
   └─ 真正 Cross-Site Cookie Requirement：Explicit None + Secure Exception
→ Cookie Policy Middleware 最終 Enforcement
→ Backend Set-Cookie
→ Node /Service Proxy 原則上保留 Cookie Security Attribute
→ Browser Final Set-Cookie / Runtime 驗證
```

SameSite 的選擇依「是否真的需要跨站傳送」判斷，而不是只依 Cookie 是否匿名：

| Requirement | SameSite Policy | 原則 |
|---|---|---|
| 無明確 Cross-Site Requirement | `Strict` | 全站預設，不需 Feature 另行宣告 |
| 需要從外站 Top-level Safe Navigation 仍延續 Cookie | `Lax` | 必須是中央 Security Policy 的具名例外 |
| iframe、Cross-site Fetch 或第三方流程確實需要攜帶 Cookie | `None` + `Secure` | 必須是明確 Cross-Site Requirement，並完成 Security Review 與 Runtime Regression |

Feature／Spec 不應直接寫 `SameSite=Lax` 或 `SameSite=None` 作為局部修補；若出現跨站需求，應先描述 Security Requirement，由 Backend Security Policy 決定真正的 SameSite Profile。`Strict` 是預設，`Lax`／`None` 是例外，不是三個可由 Feature 任意選擇的同級設定。

`wcms.visitor` 目前用於匿名瀏覽／近期去重與公開資源計數。雖然 `Lax` 可以增加跨站導航後的 Visitor Continuity，但目前 WCMS 尚未將此 Continuity 定義為必要業務契約，因此目標安全基準仍採 Default `Strict`；未來若正式確認跨站匿名延續為需求，才在中央 Security Policy 建立具名 `Lax` 例外，而不是修改 SiteViewCount 或 FileManagement 的局部 CookieOptions。

> [!IMPORTANT]
> 上述 Cookie Security Policy 是 2026-08-28 已確認的目標架構；目前 `Feature/Dev` 仍存在 Feature Source 宣告 `Lax`、Global Cookie Policy 最低 `Strict` 的歷史 Policy Drift，Code 尚待後續收斂。因此本文件更新不代表 Cookie 弱掃 Finding 已完成 Code mitigation 或複掃通過。

SameSite 集中治理不代表所有 Cookie Attribute 必須完全一致。`HttpOnly`、`Expires`／`Max-Age`、`IsEssential` 等仍依 Cookie Role 與實際 Browser Requirement 決定；例如需要由 JavaScript 讀取的 XSRF Request Token 不得因「全域安全化」而機械改成 HttpOnly。Production `Secure` 則維持保守安全基準。

Browser Shared Storage 目前只允許保存：

- `LastActivityAt`。
- Refresh Coordination Timestamp／Event。

不得保存：

- Access Token 原文。
- Refresh Token／RTID 原文。
- XSRF Token 原文。
- 其他可直接代表登入憑證的秘密值。

#### 11.6.7 安全修改驗證層級

安全 Finding 的狀態必須分開記錄：

```text
Code mitigation 已完成
≠ Runtime 驗證完成
≠ Scanner 複掃通過
```

Header 類需驗證最外層 Response；Cookie 類需清除既有 Cookie 後重新觸發第一個 `Set-Cookie`，確認 Browser-facing `SameSite`／`Secure`／`HttpOnly` 等實際 Attribute；Trusted Types／COEP／CORP 類需驗證 Browser Runtime；Host／XSRF 類需以合法與惡意 Request 實際重送；最後仍需正式弱掃複驗。

弱掃修改歷史與實例統一記錄於：

`Docs/03_品質與驗證文件/03_弱掃報告/修改歷史與方針.md`

### 11.7 Auth Session、LastActivity 與 Multi-tab Coordination

後台 Browser Session 的使用者規則為：正式環境連續 30 分鐘無有效操作登出；Development 使用 2 分鐘方便驗證。`RequireAuth` 的 Idle Timeout 與 Backend Access Token 期限必須依相同環境規則維護。

`AuthSessionCoordinator` 管理 Browser／Origin Shared Idle：

```text
Login 成功
→ initializeAuthSessionActivity
→ Shared LastActivityAt

click / keydown / scroll / touchstart
→ 更新 LastActivityAt
→ 所有同 Origin Tab 重排同一 Idle Deadline

mousemove
→ 不算 Activity
```

`keydown` 代表真實使用者鍵盤操作，因此 F5、Ctrl+R 等由使用者主動觸發的重新整理可以重設 Idle。重新載入後的 React／Coordinator 初始化本身不再寫入 `Date.now()`，避免單純 mount 再次延長 Session。

下列事件不得在沒有實際使用者 Activity 的情況下自行刷新 LastActivity：

- 新開 Tab。
- Browser Reopen。
- `/Auth/Me`。
- Refresh Token Rotation。
- focus／visibilitychange 本身。
- Coordinator mount／Reload 完成後的重新初始化本身。

Coordinator 啟動時先讀既有 Shared LastActivity：

```text
仍在 Idle Window
→ 沿用原 LastActivity / Deadline

LastActivity 缺失或已超過 Idle
→ 視為不可續用的 Browser Session
→ RequireAuth 不先執行 /Auth/Me 或 Refresh 救回 Session
→ 進入 Login / Logout Cleanup
```

`localStorage` 不可用時，同一 Tab 可暫時以 Memory LastActivity 維持登入後的 Runtime；Reload／Reopen 後若無法證明仍在有效 Idle Window，重新要求登入。Shared Storage 只保存 timestamp／event，不保存 Access Token、RTID 或 XSRF 原文。

Refresh 入口統一為：

```text
Activity KeepAlive ─┐
Axios 401 Refresh ───┤
                    ↓
AuthAPI.refresh
→ AuthRefreshCoordinator
```

同 Tab 以 in-flight Promise single-flight；支援 Web Locks 的 Browser 使用 `wcms:auth:refresh` 跨 Tab 序列化。第一個 Tab 成功後只共享 `LastRefreshCompletedAt` timestamp，等待中的 Tab 可跳過第二支真正 Refresh。Browser 不支援 Web Locks 時只降級 Frontend Coordination，Backend Atomic Rotation 仍是最後防線。

#23 已完成的 Runtime Regression 包含：同 old RTID 並行結果由 `200 + 200` 收斂為 `200 + 401`、同 Tab 兩次 `AuthAPI.refresh()` 只送一支 Request、雙 Tab Web Locks 測試只有一方 `Performed=true`；Browser 關閉超過 Development Idle 2 分鐘後再開不會重設 LastActivity，會進入 Logout／Login。剩餘 Idle 約 30 秒時由使用者按 F5 會重設為完整 2 分鐘，依目前產品規則視為有效 `keydown` Activity，屬預期行為。

`RequireAuth` 的 401／403／5xx／Network／Timeout Error Classification 已拆至 #89，避免與 Session Idle／Refresh Rotation 混為同一變更。
