## 2. P0－API Error／Exception／Message／Response Contract

對應 Issue：[#21 統一 API 回傳格式與驗證訊息規則](https://github.com/iteasygo/WCMS/issues/21)。

### 2.1 已完成的主要基礎

目前已建立：

- `IWCMSException` 最小平台契約：`MessageCode`、`MessageArgs`。
- `WCMSQueryConditionException`、`WCMSJsonException`、`WCMSDataConcurrencyException`、`WCMSFieldValidationException` 等具體異常。
- `ErrorHandlingMiddleware` 對常見 Request、Concurrency、FK、Duplicate、Persistence Contract Drift 與未知 500 的分流。
- 安全錯誤訊息走 `MessageCode + MessageArgs → IErrorHelper → Resx → SysMessage`。
- 500 NLog 已保留 `TraceId`、User、IP、Lang、HTTP Method／Path 與完整 Exception。
- `LibFieldValidator` 與 SaveChanges Persistence Guard 已形成 HTTP Boundary＋Persistence Boundary 雙層驗證。

因此舊 Word 的「建立 ErrorHandling」可視為**第一階段已完成**，但整體 Error Response 尚不能畫成 All Done。

### 2.2 仍未完成的邊界

目前仍可在 Generic Controller／Framework Boundary 看到不同 Failure Response 路徑，例如：

- Query Param 檢查直接回 `BadRequest("查詢參數錯誤")`。
- `internalId` 格式錯誤直接回 plain `BadRequest`。
- `InitialCreateData` 仍有 `catch (Exception ex) → BadRequest($"初始化失敗：{ex.Message}")` 類 Legacy Pattern。
- Enum 查詢仍可能直接回 `{ message = ex.Message }`。
- ModelState／JSON Input Formatter、Authentication Challenge、Authorization Forbid、RateLimiter、XSRF、Host、Swagger Access 仍有各自 Framework Response 邊界。

待收斂：

1. 確認 ModelState 是否要解析 `IWCMSException` 或使用共用 Error Resolver。
2. 將 `FeatureDriverApiSetup` 中 Runtime ModelState Processor 抽離 Setup，維持 Setup 只做註冊。
3. 定義 Framework Failure Adapter／Response Writer 的最小共用契約。
4. 清理會直接把 `Exception.Message` 暴露給 Client 的 Legacy Response。
5. 與 Frontend 對齊非 2xx、Biz `IsSuccess=false`、Validation Error 的解析契約。
6. 不把正常 Biz Validation 全部 Exception 化。

### 2.3 暫時維持的正式分工

```text
Biz Expected Failure
→ Message / SysMessage
→ HTTP 200 + IsSuccess=false

ModelState / Request Binding Failure
→ ASP.NET Core Boundary
→ 目標統一安全 Error Contract

Runtime / System Exception
→ ErrorHandlingMiddleware

Startup / Setup Exception
→ Fatal Log / Fail Fast
→ 不建立假的 HTTP ApiResponse
```

## 3. P0－FeatureDriver ReadOnly／System-owned 欄位 Update 保護

對應 Issue：[#25 建立 Model 直走 API 的欄位分類與讀寫權限機制](https://github.com/iteasygo/WCMS/issues/25)。

### 3.1 已確認風險

2026-08-21 追查 Spec1821 首頁異常時曾確認資料庫 `InternalId` 被 Client Request 污染，導致前台依 `InternalId` 載入資料的鏈路中斷。這不是單一 Spec Bug，而是 Generic Update 的 Overposting／Mass Assignment／System-owned Field Enforcement 問題。

目前 `HeaderModel` 已有 `ApiFieldMode.ReadOnly` metadata，但 Generic Update 尚未完整把「API 可讀不可寫」變成 Runtime Enforcement。

### 3.2 待收斂原則

建議資料流：

```text
Client Request
→ Model Binding
→ 依外層 request.InternalId 查可信 oldData
→ 套用 ReadOnly / System-owned Field Policy
→ Server 重建 ModifyInfo
→ BeforeUpdate
→ Biz / Repository
→ EF SaveChanges
```

不得只 hard-code `InternalId`，應依既有 `ILibFieldAttr.ApiMode`／`ApiFieldMode.ReadOnly` metadata 收斂。

至少確認：

- `InternalId` 不可由一般 Update 覆寫。
- `CreateTime`／`CreateUserId` 不可由 Client 改寫。
- `ModifyTime`／`ModifyUserId` 由 Server 重新產生。
- `FormStatus`／`DataStatus`／`InvalidTime`／`InvalidUserId` 只走既有生命週期。
- `IsIniData` 不可由一般 Update 改寫。
- `DataVersion` 需維持正確 Concurrency Token 語意，不與一般 ReadOnly 欄位機械同處理。
- Root、Detail、SubDetail 都需確認相同 Policy。
- Feature `BeforeUpdate()` 應看到已套用安全欄位政策後的資料。

此項具有實際資料污染證據，維持 P0，不應因目前主線轉向 QA Bug 就長期擱置。

## 4. P0／P1－FileManagement DB／實體檔案 Mapping 一致性

### 4.1 新資料 Regression 已修正

2026-08-21 曾發現新增生命週期對 `InternalId` 二次產生：

```text
CreateNewFileInfo()
→ InternalId = A
→ Pending 實體檔案使用 A

BizCreateDataAsync()
→ ApplyCreate()
→ 又產生 InternalId = B
→ DB / API 使用 B
```

已透過 `FormLifecycleFieldApplier.ApplyCreate()` 收斂為：

```text
InternalId 已有值 → 保留
InternalId 為空 → Framework 才產生 Guid
```

對應歷史 Commit：`67cc36eeb1e899025a06f000675c27af4816090f`。

### 4.2 舊資料仍需盤點

上述修正只阻止新資料再次錯配，不代表既有歷史資料已修復。後續應先輸出一致性報告，不直接改資料：

- DB `FileManage.InternalId` 是否存在對應實體檔案。
- Pending／Permanent 檔名主體是否可反查同一 `InternalId`。
- `Path`、`FileExtension`、`FileSize`、`FileSHA256` 是否與實體一致。
- `FileStatus` 與 Pending／Permanent 所在區域是否一致。
- `IsPublic` 與 Preview／Download 行為是否一致。
- 是否存在孤兒 DB Record、孤兒實體檔或 A／B 錯配可還原配對。

正式 Repair 前至少先決定：

1. Source of Truth 是 DB、實體檔案，或透過 SHA256／大小／時間／歷史 Log 交叉判定。
2. 是否修 DB InternalId、重新命名實體檔案或建立 Migration／Mapping Script。
3. 已被業務資料引用的 ID 保留策略。
4. 執行前完整備份 DB 與 FileManage 實體目錄。
5. 修復後回歸 Announcement、FileArchive、圖片、TinyMCE Content 等既有引用。

## 6. P1－Cache 更新／失效與資料一致性

### 6.1 已有能力

正式架構已存在：

- Local／Distributed Store 抽象。
- Runtime Cache。
- Output Cache List／Detail／Permanent Policy。
- Output Cache Tag。
- Generic Create／Update／Delete 後的 `EvictForDataAsync()` Tag Eviction。
- `Accept-Language` 等 Vary 設定。

因此舊 Word 的「建立 Cache 基礎」已不是空白項目。

## 14. 架構待辦完成與移出規則

架構議題只有在下列條件滿足後才可自本文件移出：

1. 已確認實際 `Feature/Dev` Code 與責任邊界。
2. 已完成必要修正，並有對應 Commit／PR／Issue。
3. 已執行與風險相符的 Build、白箱、Runtime、QA、弱掃或資料盤點；未執行者明確標示。
4. 最終契約已回寫正式後端架構／開發規範。
5. 本文件不再需要保留第二份規格細節，只留歷史索引或移除完成項。

目前建議處理順序：

```text
P0 資料完整性／欄位寫入邊界
→ P0 API Error／Response Contract
→ QA 直接觸發的 Cache／Auth／FileManagement 共用根因
→ OperateLog／Tracing
→ UTC／I18n 等跨端契約
→ ChangeLog／Distributed／Setup 純重構
```

核心策略：**先讓目前 Release 與 QA Bug 可穩定複驗，再持續收斂不阻塞交付的架構技術債。**
