## 1. Error／Exception／Message 架構待收斂

### 1.1 本輪發現背景

2026-08-10 弱掃 High 項目中，`PageNumber`／`PageSize` 傳入超出 `Int32` 範圍的 JSON 數值時，原始流程會在 JSON 反序列化階段發生 `FormatException`，並可能造成 500／502 類錯誤。

目前已先加入 `WCMSJsonException`／`IWCMSException` 與 JSON Converter 包裝處理，使測試案例可回應 HTTP 400 與 WCMS `ApiResponse`／`SysMessage`，例如：

```text
[PageNumber] 輸入格式不正確。
```

目前此修正可作為弱掃 High 的緊急處理基準，但完整 Error Architecture 尚未完成收斂。

> [!WARNING]
> 弱掃 High 是否正式結案仍需以原始掃描 Payload 複測確認；本文件不宣稱已 All Clear。

### 1.2 `IWCMSException` 的平台定位

目前傾向將 `IWCMSException` 定義為「WCMS 平台可辨識 Exception 的共通契約」，而不是「一定要被 `ErrorHandlingMiddleware` 捕捉的 Exception」。

目前核心契約方向：

```text
IWCMSException
├─ MessageCode
└─ MessageArgs
```

待後續確認：

- 哪些 Framework Exception 應包成 WCMS Exception。
- 哪些 WCMS Exception 可保留 Framework Exception 繼承。
- 哪些情況只保存原始 Exception 為 `InnerException`。
- `IWCMSException` 在 MVC、Authentication、RateLimit、Middleware 等不同 Handler 中的統一讀取方式。
- MessageArgs 是否應由 Exception 固定攜帶，或允許 Handler Context 補充更精確欄位資訊。

### 1.3 `WCMSJsonException` 與 MVC ModelState

目前 `WCMSJsonException : JsonException, IWCMSException` 在 ASP.NET Core MVC JSON Input Formatter 中會被當作 JSON Model Binding Failure 處理，進入 ModelState，而不是繼續拋到外層 `ErrorHandlingMiddleware`。

目前實測結果合理：

```text
JSON Int32 超界
→ FormatException
→ WCMSJsonException
→ MVC Input Formatter
→ ModelState
→ InvalidModelStateResponseFactory
→ HTTP 400 + SysMessage
```

但目前 ModelState Response 流程沒有直接使用 `IWCMSException.MessageCode`／`MessageArgs`，而是重新依 ModelState Key、`LibNumAttribute` 等資訊推導 MessageCode 與顯示名稱。

因此待後續評估：

- ModelState 是否應優先解析 `ModelError.Exception`／InnerException 中的 `IWCMSException`。
- `MessageCode` 是否由 Exception 提供，而欄位名稱等 Context 由 ModelState 補足。
- 是否建立共用 WCMS Exception Resolver，供 ModelState Handler 與 ErrorHandlingMiddleware 共用。

### 1.4 ModelState Error Handler

目前 `FeatureDriverApiSetup` 除了 Controller／Swagger／JSON／ApiBehavior 註冊之外，還包含：

- ModelState Error 分析。
- Property Reflection。
- `LibNumAttribute` 判斷。
- Required／MaxLength／格式錯誤 Mapping。
- MessageCode 決策。
- `ErrorHelper` 建立。
- `ApiResponse` 組裝。

此責任已超出 Setup 單純註冊用途。

目前較合理的待評估方向，是將這一串 Runtime 邏輯抽成 API／MVC Boundary 專用 Handler，例如：

```text
FeatureDriver/Api/Validation/ModelStateErrorHandler
```

定位：

```text
ASP.NET Core ModelState
→ WCMS Error／Message 契約
→ ApiResponse
```

此 Handler 不是 Middleware，也不取代 `ErrorHandlingMiddleware`。

### 1.5 `ErrorHandlingMiddleware` 的責任

目前仍應保留作為 HTTP Pipeline 中「未被其他 Framework Failure Handler 正常處理之 Exception」的主要處理入口。

待後續確認的分工方向：

```text
ModelState / Request Binding Failure
→ ModelState Handler

Runtime / System Exception
→ ErrorHandlingMiddleware

Biz Expected Failure
→ Message / SysMessage
→ HTTP 200 + IsSuccess=false
```

需避免把所有正常的 Validation／Framework Failure 強制轉成 Exception，只為了經過單一 Middleware。

## 2. Setup 與 Runtime Handler 責任邊界

本輪檢查發現，不是所有 Setup 都有問題，但部分 Setup 已開始承擔 Runtime Handler／Response Processor 的責任。

### 2.1 目前較明顯需回頭盤點的 Setup

#### `FeatureDriverApiSetup`

目前最明顯：Setup 內已包含完整 ModelState Error Processor。

待整理方向：Setup 只保留註冊，Runtime Error Processing 抽成正式 Handler。

#### `HardeningSetup`

RateLimit `OnRejected` 目前會直接建立 HTTP 429 Response，且訊息直接寫在 Setup Callback 中。

待確認：

- 是否抽成 RateLimit Failure Handler／Adapter。
- 是否統一使用 WCMS `ApiResponse`／`SysMessage`。
- 是否需要與 `IWCMSException`／Error Resolution 共用契約。

#### `XsrfProtectionSetup`

目前拒絕來源時直接回：

```text
HTTP 403
{ success = false, message = "Invalid Origin/Referer." }
```

此格式與 WCMS `ApiResponse`／`SysMessage` 主線不同。

待確認：是否抽成 XSRF Failure Handler／Adapter，統一 Failure Response。

#### `SecurityHeadersSetup`

目前除了安全標頭外，也實際攔截正式環境 Host 並直接回 403。

待確認：

- 類別名稱與實際 Middleware 職責是否應調整。
- Host 拒絕 Response 是否需統一 Error Contract。

#### `SwaggerAccessSetup`

正式環境會攔截 Swagger 存取並直接回 403 plain text。

待確認：此類工具端點是否需要與一般 API Error Contract 完全一致，或可保留特殊回應；目前尚未定案。

#### `IdentityAccessSetup`

目前 JWT Events 中包含 Request Runtime 邏輯，例如：

- Cookie Token 解析。
- Token JTI 撤銷檢查。
- `context.Fail(...)`。

待確認：是否應將 JWT Runtime Event Handler 與 Setup 註冊拆開，以維持 Setup 只做組態與掛載。

### 2.2 主要是檔案整理問題的 Setup

以下目前不一定是行為架構錯誤，但 Setup 與 Startup Runtime 類別放在同檔，後續可視可讀性整理：

- `PersistenceModuleSetup` + `PersistenceStartupInitializer`
- `CacheModuleSetup` + `PermanentOutputCacheStartupTask`
- `IamModuleSetup` + `IamStartupInitializer`
- `WebModuleSetup` + `WebStartupInitializer`
- `CommonModuleSetup` + `CalendarStartupInitializer`

目前不列為高優先級，避免在 Error Handling 尚未收斂前進行無必要大搬動。

## 3. Error Response 統一性待盤點

目前後端至少存在多個可以直接決定 HTTP Failure Response 的入口：

```text
ErrorHandlingMiddleware
ModelState InvalidModelStateResponseFactory
RateLimit OnRejected
XSRF Protection
Host Whitelist / Security Headers
Swagger Access
Authentication / Authorization Framework Events
Controller 直接 BadRequest / Forbid / NotFound
```

待後續逐項確認：

- 哪些是正常 Framework Failure，不應轉成 Exception。
- 哪些應透過 WCMS Failure Adapter 統一成 `ApiResponse`／`SysMessage`。
- 哪些屬工具頁／非 API Response，可保留特殊格式。
- HTTP Status、MessageCode、SysMessage、NLog、TraceId 的責任與一致性。
- `IWCMSException` 是否應作為跨 Handler 的平台 Exception Contract。

## 4. 暫時決策與目前不做的事情

現階段先維持：

```text
Biz Expected Failure
→ Message / SysMessage
→ HTTP 200 + IsSuccess=false

ModelState / Request Binding Failure
→ ASP.NET Core MVC ModelState 主線
→ HTTP 400

未處理 Runtime / System Exception
→ ErrorHandlingMiddleware
```

目前不急著：

- 把所有 ModelState Error 強制 throw 回 `ErrorHandlingMiddleware`。
- 一次重構所有 Setup。
- 一次統一所有 401／403／429／Swagger Response。
- 因架構尚未定案就大幅搬動既有安全流程。

先以弱掃 High 修正與既有功能穩定為優先，再安排獨立時間進行 Error／Message 架構收斂。

## 5. 後續建議處理順序

1. 先完成本輪弱掃 High 原始 Payload 複測。
2. 將 `FeatureDriverApiSetup` 中 ModelState Runtime 邏輯抽成正式 Handler。
3. 確認 `IWCMSException` 在 ModelState 與 ErrorHandlingMiddleware 的共用解析方式。
4. 定義 WCMS Error Resolution／Failure Response 共用規則。
5. 再逐一處理 XSRF、RateLimit、Host、Authentication／Authorization 等 Framework Failure Adapter。
6. 最後才整理純檔案層級的 Setup／StartupTask 分離。
7. 架構定案後回寫 `03_後端專案架構.md` 與對應後端開發規範。
