## 1. Error／Exception／Message 架構待收斂

### 1.1 本輪發現背景

2026-08-10 弱掃 High 項目中，`PageNumber`／`PageSize` 傳入超出 `Int32` 範圍的 JSON 數值時，原始流程會在 JSON 反序列化階段發生 `FormatException`，並可能造成 500／502 類錯誤。

目前已先加入 `WCMSJsonException`／`IWCMSException` 與 JSON Converter 包裝處理，使測試案例可回應 HTTP 400 與 WCMS `ApiResponse`／`SysMessage`，例如：

```text
[PageNumber] 輸入格式不正確。
```

目前此修正可作為弱掃 High 的緊急處理基準，但完整 Error Architecture 尚未完成收斂。

> [!WARNING]
> 弱掃 High 是否正式結案仍需以原始掃描 Payload 複測確認；本文件不宣稱已 All Clear。

### 1.2 `IWCMSException` 的平台定位

目前傾向將 `IWCMSException` 定義為「WCMS 平台可辨識 Exception 的共通契約」，而不是「一定要被 `ErrorHandlingMiddleware` 捕捉的 Exception」。

目前核心契約方向：

```text
IWCMSException
├─ MessageCode
└─ MessageArgs
```

待後續確認：

- 哪些 Framework Exception 應包成 WCMS Exception。
- 哪些 WCMS Exception 可保留 Framework Exception 繼承。
- 哪些情況只保存原始 Exception 為 `InnerException`。
- `IWCMSException` 在 MVC、Authentication、RateLimit、Middleware 等不同 Handler 中的統一讀取方式。
- MessageArgs 是否應由 Exception 固定攜帶，或允許 Handler Context 補充更精確欄位資訊。

### 1.3 `WCMSJsonException` 與 MVC ModelState

目前 `WCMSJsonException : JsonException, IWCMSException` 在 ASP.NET Core MVC JSON Input Formatter 中會被當作 JSON Model Binding Failure 處理，進入 ModelState，而不是繼續拋到外層 `ErrorHandlingMiddleware`。

目前實測結果合理：

```text
JSON Int32 超界
→ FormatException
→ WCMSJsonException
→ MVC Input Formatter
→ ModelState
→ InvalidModelStateResponseFactory
→ HTTP 400 + SysMessage
```

但目前 ModelState Response 流程沒有直接使用 `IWCMSException.MessageCode`／`MessageArgs`，而是重新依 ModelState Key、`LibNumAttribute` 等資訊推導 MessageCode 與顯示名稱。

因此待後續評估：

- ModelState 是否應優先解析 `ModelError.Exception`／InnerException 中的 `IWCMSException`。
- `MessageCode` 是否由 Exception 提供，而欄位名稱等 Context 由 ModelState 補足。
- 是否建立共用 WCMS Exception Resolver，供 ModelState Handler 與 ErrorHandlingMiddleware 共用。

### 1.4 ModelState Error Handler

目前 `FeatureDriverApiSetup` 除了 Controller／Swagger／JSON／ApiBehavior 註冊之外，還包含：

- ModelState Error 分析。
- Property Reflection。
- `LibNumAttribute` 判斷。
- Required／MaxLength／格式錯誤 Mapping。
- MessageCode 決策。
- `ErrorHelper` 建立。
- `ApiResponse` 組裝。

此責任已超出 Setup 單純註冊用途。

目前較合理的待評估方向，是將這一串 Runtime 邏輯抽成 API／MVC Boundary 專用 Handler，例如：

```text
FeatureDriver/Api/Validation/ModelStateErrorHandler
```

定位：

```text
ASP.NET Core ModelState
→ WCMS Error／Message 契約
→ ApiResponse
```

此 Handler 不是 Middleware，也不取代 `ErrorHandlingMiddleware`。

### 1.5 `ErrorHandlingMiddleware` 的責任

目前仍應保留作為 HTTP Pipeline 中「未被其他 Framework Failure Handler 正常處理之 Exception」的主要處理入口。

待後續確認的分工方向：

```text
ModelState / Request Binding Failure
→ ModelState Handler

Runtime / System Exception
→ ErrorHandlingMiddleware

Biz Expected Failure
→ Message / SysMessage
→ HTTP 200 + IsSuccess=false
```

需避免把所有正常的 Validation／Framework Failure 強制轉成 Exception，只為了經過單一 Middleware。

## 2. Setup 與 Runtime Handler 責任邊界

本輪檢查發現，不是所有 Setup 都有問題，但部分 Setup 已開始承擔 Runtime Handler／Response Processor 的責任。

### 2.1 目前較明顯需回頭盤點的 Setup

#### `FeatureDriverApiSetup`

目前最明顯：Setup 內已包含完整 ModelState Error Processor。

待整理方向：Setup 只保留註冊，Runtime Error Processing 抽成正式 Handler。

#### `HardeningSetup`

RateLimit `OnRejected` 目前會直接建立 HTTP 429 Response，且訊息直接寫在 Setup Callback 中。

待確認：

- 是否抽成 RateLimit Failure Handler／Adapter。
- 是否統一使用 WCMS `ApiResponse`／`SysMessage`。
- 是否需要與 `IWCMSException`／Error Resolution 共用契約。

#### `XsrfProtectionSetup`

目前拒絕來源時直接回：

```text
HTTP 403
{ success = false, message = "Invalid Origin/Referer." }
```

此格式與 WCMS `ApiResponse`／`SysMessage` 主線不同。

待確認：是否抽成 XSRF Failure Handler／Adapter，統一 Failure Response。

#### `SecurityHeadersSetup`

目前除了安全標頭外，也實際攔截正式環境 Host 並直接回 403。

待確認：

- 類別名稱與實際 Middleware 職責是否應調整。
- Host 拒絕 Response 是否需統一 Error Contract。

#### `SwaggerAccessSetup`

正式環境會攔截 Swagger 存取並直接回 403 plain text。

待確認：此類工具端點是否需要與一般 API Error Contract 完全一致，或可保留特殊回應；目前尚未定案。

#### `IdentityAccessSetup`

目前 JWT Events 中包含 Request Runtime 邏輯，例如：

- Cookie Token 解析。
- Token JTI 撤銷檢查。
- `context.Fail(...)`。

待確認：是否應將 JWT Runtime Event Handler 與 Setup 註冊拆開，以維持 Setup 只做組態與掛載。

### 2.2 主要是檔案整理問題的 Setup

以下目前不一定是行為架構錯誤，但 Setup 與 Startup Runtime 類別放在同檔，後續可視可讀性整理：

- `PersistenceModuleSetup` + `PersistenceStartupInitializer`
- `CacheModuleSetup` + `PermanentOutputCacheStartupTask`
- `IamModuleSetup` + `IamStartupInitializer`
- `WebModuleSetup` + `WebStartupInitializer`
- `CommonModuleSetup` + `CalendarStartupInitializer`

目前不列為高優先級，避免在 Error Handling 尚未收斂前進行無必要大搬動。

## 3. Error Response 統一性待盤點

目前後端至少存在多個可以直接決定 HTTP Failure Response 的入口：

```text
ErrorHandlingMiddleware
ModelState InvalidModelStateResponseFactory
RateLimit OnRejected
XSRF Protection
Host Whitelist / Security Headers
Swagger Access
Authentication / Authorization Framework Events
Controller 直接 BadRequest / Forbid / NotFound
```

待後續逐項確認：

- 哪些是正常 Framework Failure，不應轉成 Exception。
- 哪些應透過 WCMS Failure Adapter 統一成 `ApiResponse`／`SysMessage`。
- 哪些屬工具頁／非 API Response，可保留特殊格式。
- HTTP Status、MessageCode、SysMessage、NLog、TraceId 的責任與一致性。
- `IWCMSException` 是否應作為跨 Handler 的平台 Exception Contract。

## 4. FileManagement DB／實體檔案 Mapping 一致性待盤點

### 4.1 發現背景

2026-08-21 驗證 TinyMCE 檔案上傳流程時，發現新版 Backend FeatureDriver 的新增生命週期曾造成 FileManagement 的 `InternalId` 被產生兩次：

```text
CreateNewFileInfo()
→ 先產生 InternalId = A
→ Pending 實體檔案以 A 作為檔名

BizCreateDataAsync()
→ FormLifecycleFieldApplier.ApplyCreate()
→ 再產生 InternalId = B
→ FileManage DB 與 Server_UploadTemp 回傳 B
```

因此可能形成：

```text
實體檔案名稱 = A
FileManage.InternalId = B
Public_Download / Public_Preview URL = B
```

此狀況會破壞 WCMS FileManagement 最重要的識別 Mapping，造成 DB 可查到資料但無法依相同 `InternalId` 對應正確實體檔案。

目前判斷此 Regression 與 2026-07 Backend FeatureDriver 大升版期間的新增流程調整有關；歷史受影響範圍尚未正式盤點。

### 4.2 新資料已採取的修正

2026-08-21 已修正 `FormLifecycleFieldApplier.ApplyCreate()`：

```text
InternalId 已有值
→ 保留既有值

InternalId 為空
→ Framework 才產生新的 Guid
```

修正後新上傳資料應維持以下一致性契約：

```text
FileManage.InternalId
=
Pending / Permanent 實體檔案的檔名主體
=
Server_UploadTemp 回傳 InternalId
=
Public_Download / Public_Preview URL InternalId
=
前端 data-internalid（有使用時）
```

對應修正 Commit：`67cc36eeb1e899025a06f000675c27af4816090f`（`fix(backend): 保留預先建立的 InternalId`）。

> [!IMPORTANT]
> 此修正只防止後續新增資料再次產生錯配，不代表 2026-07 大升版後已存在的 FileManage／實體檔案資料已完成修復。

### 4.3 舊資料待盤點事項

後續需安排一次獨立的 FileManagement 一致性檢查，至少確認：

- DB `FileManage.InternalId` 是否存在對應實體檔案。
- Pending／Permanent 實體檔案檔名主體是否能反查同一筆 `FileManage.InternalId`。
- DB `Path`、`FileExtension` 與實體路徑／副檔名是否一致。
- DB `FileSize` 與實體檔案大小是否一致。
- DB `FileSHA256` 與實體檔案重新計算 SHA256 是否一致。
- `FileStatus` 與實體檔案所在 Pending／Permanent 區域是否一致。
- `IsPublic` 與公開 Preview／Download 行為是否符合資料狀態。
- 是否存在「DB 有資料但實體檔不存在」的孤兒 DB Record。
- 是否存在「實體檔存在但 DB 無對應 Record」的孤兒檔案。
- 是否存在因 InternalId 二次產生造成的 A（實體）／B（DB）可還原配對資料。

### 4.4 後續修復原則待定

在盤點完成前，不應直接批次重新命名或刪除實體檔案。

正式修復前至少需先定義：

1. 哪一側是 Source of Truth：DB、實體檔案或透過 SHA256／歷史 Log 交叉判定。
2. A／B 錯配資料是否可透過 `FileSHA256`、`FileSize`、副檔名、建立時間與 Path 安全配對。
3. 已被業務資料引用的 InternalId 應優先保留哪一個值。
4. 修復是否採「修 DB InternalId」、「重新命名實體檔案」或建立 Mapping／Migration Script。
5. 執行前是否需先完整備份 DB 與 `FileManage` 實體目錄。
6. 修復後需如何驗證 Announcement、FileArchive、圖片、TinyMCE Content 等既有引用仍可正常 Preview／Download。

此議題完成後，正式的 FileManagement 識別與 Mapping 契約應回寫 `03_後端專案架構.md`，必要時再補入後端開發規範，避免未來重構新增生命週期時再次破壞 FileManagement 的實體識別。

## 5. 暫時決策與目前不做的事情


## 8. FeatureDriver ReadOnly／System-owned 欄位 Update 保護待辦

### 8.1 發現背景

2026-08-21 追查 HCL AppScan 360 弱掃期間的 Spec1821 首頁異常時，確認客戶 DB 的首頁資料曾被改成：

```text
HomePageId = HomePageS20260625001
InternalId = ProbePhishing
```

原始 OperateLog 則可反查該筆資料正常的 `InternalId` 為：

```text
c2080823-a98b-4550-92d1-2fad373c5886
```

Spec1821 前台 Loader 會先依語系 QueryList 取得首頁資料的 `InternalId`，再使用該值 QueryData 載入完整 FormModel，因此 `InternalId` 被污染後會直接破壞前台首頁資料讀取鏈。

此問題目前不應視為單一 Spec1821 Bug，而應視為 FeatureDriver Generic Update 的 Overposting／Mass Assignment／資料完整性風險。

> [!WARNING]
> 此問題已確認有實際 DB 資料污染案例，優先級應列為高；目前尚未完成正式 Code 修正與弱掃複測。

### 8.2 目前確認的根因

`ApiDataController.Update()` 同時接收：

```text
request.InternalId
→ 用於查詢可信的 oldData

request.Data.InternalId
→ Client 傳入的新 FormModel 值
```

`BizService.UpdateInTransactionAsync()` 會先使用外層 `request.InternalId` 查詢既有資料，但目前新 FormModel 中的 `InternalId` 仍可保留 Client 傳入內容。

後續 `FormWriteOperations.UpdateAsync()` 雖然會執行：

```text
KeyCoordinator.PreserveExistingKeys(oldData, newData)
LifecycleFieldApplier.PreserveCreateInfo(oldData, newData)
```

但目前：

- `PreserveExistingKeys()` 只保護 Entity 上的 `[Key]` 欄位。
- Spec1821 的 Root Key 是 `HomePageId`，`InternalId` 不是 `[Key]`。
- `PreserveCreateInfo()` 只保護 `CreateUserId` 與 `CreateTime`。
- 因此 `InternalId` 可漏過保護並被 Client Request 覆寫。

### 8.3 `ApiFieldMode.ReadOnly` 語意尚未成為寫入安全邊界

目前 `HeaderModel` 已將系統欄位標記為 `ApiFieldMode.ReadOnly`，例如：

```text
InternalId
CreateTime / CreateUserId
ModifyTime / ModifyUserId
FormStatus / DataStatus
InvalidTime / InvalidUserId
DataVersion
IsIniData
```

`ApiFieldMode.ReadOnly` 的定義本身即為「API 可讀不可寫」，但目前 Generic Update 流程尚未完整 enforcement 此規則。

因此目前較合理的正式方向不是只針對 `InternalId` hardcode，而是讓 FeatureDriver 的 Update 流程真正落實既有 `ILibFieldAttr.ApiMode` metadata，將 ReadOnly／System-owned 欄位視為不可由外部 Request 覆寫的資料邊界。

### 8.4 建議修正方向

待實作時優先評估：

1. 在 `UpdateInTransactionAsync()` 查得可信 `oldData` 後、進入 `BeforeUpdate()` 前，即先將不可外部覆寫的欄位恢復為 DB 原值。
2. 共用邏輯應依 `ILibFieldAttr.ApiMode`／`ApiFieldMode.ReadOnly` metadata 判斷，不以 Spec1821 或欄位名稱建立特例。
3. `ModifyTime`／`ModifyUserId` 應持續由 Server 依本次操作重新產生，而非直接保留 Client 值或舊 DB 值。
4. `InternalId`、建立資訊、狀態資訊、初始化資訊等 Server-owned 欄位需明確定義 Update 行為。
5. `DataVersion` 屬 `[Timestamp]`／Concurrency Token，需另外確認現有樂觀鎖流程後再決定其 Request／Update 語意，不應直接與其他 ReadOnly 欄位一刀處理。
6. 必須確認 Root、Detail、SubDetail 是否都需要相同 ReadOnly Enforcement，避免只保護 Aggregate Root 後仍可竄改明細系統欄位。

建議資料流：

```text
Client Request
→ Model Binding
→ 依 request.InternalId 查可信 oldData
→ 套用 ReadOnly / System-owned Field Policy
→ Server 重建 ModifyInfo
→ BeforeUpdate
→ Biz / Repository
→ EF SaveChanges
```

### 8.5 驗證案例待補

正式修正後至少需驗證：

- `request.Data.InternalId = "ProbePhishing"` 時，DB `InternalId` 必須維持原值。
- `CreateTime`／`CreateUserId` 不可由 Client Update 覆寫。
- `ModifyTime`／`ModifyUserId` 必須由 Server 依本次操作產生。
- `FormStatus`／`DataStatus`／`InvalidTime`／`InvalidUserId` 不可藉一般 Update 越權修改，應只走既有專用生命週期。
- `IsIniData` 不可由一般 Update 改寫。
- `DataVersion` 仍可維持正確的 Concurrency Control 行為。
- 正常業務 `ReadWrite` 欄位仍可正常更新。
- Feature `BeforeUpdate()` 取得的資料已是套用安全欄位政策後的內容，不得看到遭竄改的 `InternalId`。
- Spec1821 首頁重新測試時，弱掃 Request 不得再造成首頁 `InternalId` 污染或前台資料鏈中斷。

此議題完成後，應將 `ApiFieldMode` 的 Runtime Enforcement 規則正式回寫 `03_後端專案架構.md` 與後端開發規範，並補上對應的弱掃／自動化回歸測試紀錄。
