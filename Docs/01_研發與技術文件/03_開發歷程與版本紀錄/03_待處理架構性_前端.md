## 0. 目前開發階段

2026-09-07 已完成一輪 `Feature/Dev` → `Feature/Release` 整合，Release 線已納入近期 Frontend Security、Login autocomplete、後台 Navigation／Sidebar 與 RWD 等修正。該輪 PR 的驗證說明仍保留 Runtime、QA 與正式弱掃複驗待辦，因此不能把「已合併 Release」解讀成「QA／弱掃已通過」。

目前開發主線調整為：

```text
既有 QA Issue / Release Regression
→ RD 修正
→ AI 白箱 Gate
→ Hotfix / Release
→ 部署 QA 環境
→ QA 原 Issue 複驗
```

因此前端架構性工作不再以舊 Word 的大項順序一次做完，而是：

1. 會阻塞 Bug、QA、Release、安全或資料契約的架構問題優先處理。
2. 與目前 Bug 無直接關係的大型重構保留在本文件，不搶 QA Bug 收斂優先級。
3. 個別 UI／RWD／功能 Bug 由 GitHub Issue 與 QA 流程追蹤，不重複寫成架構待辦。

## 2. P0－API／Schema／Error Contract

### 2.1 `ApiResponse` 泛型與 Data Contract

目前正式前端架構已確認：

```text
Frontend
ApiResponse<T>
→ Data: T | null

Backend
ApiResponse<T>
→ Data: IList<T>
```

因此仍存在：

- 單筆／陣列的泛型語意落差。
- `null`／空陣列／`undefined` 的責任不一致。
- OpenAPI Schema 與手寫 Type 並存。
- Query／Form／Grid／Loader 對 Data Shape 的假設不同。

此項不得標示完成。對應 Issue：[#21 統一 API 回傳格式與驗證訊息規則](https://github.com/iteasygo/WCMS/issues/21)。

待收斂：

1. 定義單筆、清單、空資料的唯一契約。
2. 對齊 OpenAPI 產生型別與前端 Adapter 的泛型語意。
3. 統一非 2xx、Biz `IsSuccess=false`、Validation Error 的前端分類。
4. 確認 Loader、FormTemplate、Grid、ModelDisplay 不再各自補相容判斷。

### 2.2 `RequireAuth` HTTP／網路錯誤分類

Browser Shared Idle、LastActivity、Refresh Single-flight／Cross-tab Coordination 與目前單 Backend Process Refresh Rotation 已完成一輪收斂；但 `RequireAuth` 仍有獨立 Follow-up：[#80 收斂 RequireAuth 驗證錯誤分類與前端導頁](https://github.com/iteasygo/WCMS/issues/80)。

待確認：

```text
401 / Token 無效
→ Login

403 / 已登入但無權限
→ Forbidden / 授權提示

5xx
→ 暫時性系統錯誤，不直接清空有效登入 Context

Network Error / Timeout
→ 可恢復錯誤，不放大成登出
```

focus／visibilitychange／route probe 必須使用一致分類契約，並補 Runtime／白箱驗證。

## 3. P1－I18n／Resx／Routing／Linking

對應 Issue：[#20 整理多語系 resx 資源與欄位說明來源](https://github.com/iteasygo/WCMS/issues/20)。

目前前端已有 `SysCore/i18n`、Lang Context、Lang Route、`LangLink`／`LangNavLink`、Accept-Language 等主線能力，但不能因此判定多語系已完成。QA 仍有多筆英文顯示、預覽、後台語系污染與文案未翻譯問題。

待盤點：

- Lang、Route、Link、SSR、API `Accept-Language` 是否都走單一入口。
- 前台／後台／Spec 是否仍自行組語系路徑或自行判斷語系。
- Label、欄位說明、placeholder、Error Message、Toast 的 Resx 來源與 fallback。
- Feature／SpecFeature 的多語系覆寫責任。
- 使用者輸入內容、多語內容與 AA／SEO／SSR 的責任交界。

此項在 QA Bug 收斂期採「先修共用根因、避免逐頁 hard-code」原則。

## 5. P1－SSR、AA、Freego 與 Browser Runtime 邊界

正式架構已建立 SSR、CSR、Security Hardening 與 AA 的責任，但仍有 Runtime 與專項驗證工作：

- SSR Loader、Hydration、CSR Fallback 與重複 Fetch。
- Browser API 使用時機與 SSR Guard。
- Promise／Request Race／Cleanup。
- Toast／Dialog／Dynamic Message 的 AA 報讀。
- Keyboard、Focus、ARIA、Zoom 與 CMS 動態內容。
- Trusted Types、COEP／COOP／CORP 對 TinyMCE、PDF、第三方 Script、Spec Assets 的 Runtime 相容性。
- IIS／ARR → Node SSR → Backend 最終 Header 一致性。

Security 的寬泛大項不再留在舊 Word；實際 Security Finding 必須使用「Finding → Code mitigation → Runtime → 正式複掃」的品質鏈追蹤，不能只以 Source Commit 判定 All Clear。

## 7. P1－Client Cache／Request Race 邊界

後端已有 Output Cache 與寫入後 Tag Eviction 主線；前端仍需在實際 Bug／Review 觸發時確認：

- SSR Initial Data 與 CSR Query 是否造成重複 Fetch。
- Loader／Hook 是否存在 stale data 或 request race。
- 返回頁面狀態、表單暫存與 API Cache 是否互相混淆。
- Cache 不得保存 Credential／Token，也不得跨 SSR Request 共用使用者資料。

Server-side Cache、Redis、LB／Distributed Atomicity 統一由 Backend 架構待辦追蹤，不在前端重複建立第二份主線。
