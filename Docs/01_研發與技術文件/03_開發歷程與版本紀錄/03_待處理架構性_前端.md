## 1. 目前待回頭盤點的前端架構主題

目前先建立追蹤入口，不在本次一次定義最終方案。

### 1.1 SSR、AA 與 Freego 檢測邊界

待後續重新盤點：

- React + Vite 前端在 SSR 啟用後的路由、資料取得與 Hydration 責任。
- SSR 與既有 CSR Component／Hook 的共存方式。
- AA／Freego 檢測需要的初始 HTML、鍵盤操作、焦點、ARIA 與動態內容呈現責任。
- 使用者可輸入內容、HTML、圖片替代文字等資料在 AA 規則中的前後端責任切分。

> [!NOTE]
> 此處只記錄「需要回頭做完整架構盤點」，不代表目前 SSR 或 AA 實作已有單一確定問題。

### 1.2 FormModel／共用 Form Template 邊界

待後續確認：

- Feature／Spec Form 是否都已收斂至目前共用 FormModel／FormTemplate 主線。
- 共用 Hook、Adapter、Template 與 Feature 專用邏輯的責任邊界。
- 是否仍有舊式頁面自行保存相同狀態、驗證或 API Mapping。
- 新增功能時是否能維持 `const`、`interface`、Hook 為主的實作方式。

### 1.3 多語系與 Routing／Linking

待後續確認：

- Lang、Route、Link、SSR 與 API Accept-Language 是否有單一一致入口。
- 前台／後台／Spec 是否仍存在自行組語系路徑或自行判斷語系的重複邏輯。
- 多語內容與使用者輸入資料在 AA、SEO、SSR 的交界責任。

### 1.4 REST → GraphQL 過渡架構

目前仍以 REST API 為初期主線；未來轉 GraphQL 前需再盤點：

- 現有 Adapter／Hook 是否能維持 UI 與傳輸協定解耦。
- FormModel 與 GraphQL Query／Mutation Contract 的轉換責任。
- Cache、Error／SysMessage、Pagination 與多語系 Context 是否能沿用。

> [!WARNING]
> 本節只保留未來架構風險，不代表現在應提前導入 GraphQL。

## 2. 後續整理原則

新增前端架構性待辦時，至少記錄：

1. 發現位置／Feature／元件。
2. 現況與為什麼可能形成架構問題。
3. 是否已有臨時修正。
4. 尚未定案的問題。
5. 預計回寫的正式架構或開發規範文件。
6. 若已完成，標記對應 Commit／PR／Issue 後再從本文件移出或標示完成。
